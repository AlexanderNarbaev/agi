# JAVA_NATIVE: GraalVM native-image, ограничения JMM и путь субстратов

**Статус: normative** · Дополнение к JAVA_STACK.md. Первая версия MATRIX собирается на Java с компиляцией GraalVM в native; документ фиксирует, что это меняет в правилах кода, и как учитываются ограничения модели памяти Java (JMM) и кучи — с расчётом на полный прототип и последующие субстраты (FPGA, квантовые).

## 1. Почему native-image

- Холодный старт модулей сигналов (DESIGN-06) как отдельных приложений: мс вместо сотен мс JVM; предсказуемая резидентная память; дистрибуция без JRE для агентских узлов.
- BIR-ядро — идеальный кандидат AOT: нет рефлексии, нет динамических прокси, горячие пути — циклы по long[].

## 2. Правила кода под GraalVM (нарушение = блокировка PR)

1. **Нет рефлексии** в рантайм-пути: ни `Class.forName`, ни прокси, ни аннотационного сканирования. Регистрация модулей и Capabilities — явная (`register(...)`, DESIGN-06 R4). Библиотеки с обязательной рефлексией — только через reachability-metadata в явном белом списке `META-INF/native-image/`, задокументированном в PR.
2. **Нет ServiceLoader/classpath-сканирования** (тот же пункт R4 — продублирован сознательно: это самая частая поломка native-сборок).
3. **Нет sun.misc.Unsafe и VarHandle-обходов** в прототипной линии; продакшн-доступ к off-heap — через FFM API (Java 25, `java.lang.foreign`, финальное с JDK 22).
4. **Ресурсы явно:** Avro-схемы, словари кодировщиков — в `resource-config.json`; тест native-сборки в CI обязателен для модулей, помеченных `native` (DESIGN-06 §8.6).
5. **Инициализация:** без статических блоков с wall-clock/ENV-зависимой логикой; `--initialize-at-build-time` только для перечисленных классов.
6. **Сериализация:** только Avro/ручные кодеки; Java-Serializable запрещён (уже в JAVA_STACK — здесь усилено: native-image его практически не поддерживает).

## 3. Ограничения JMM и кучи — как учитываем

BIR-артефакты плотные (TT k=20 = 128 КБ; CLAUSESET-реестры доменов — десятки МБ; VSA-словари D=8192 × тысячи атомов — единицы МБ). Проблемы и решения:

| Ограничение | Риск | Решение MATRIX |
|---|---|---|
| Размер кучи / GC-паузы | большие реестры → паузы G1 на сотнях МБ | крупные таблицы — off-heap: прототип direct ByteBuffer (замер §4), продакшн — FFM `Arena.ofShared()` + `MemorySegment`; on-heap остаются только горячие малые артефакты |
| Безопасная публикация | гонки при чтении артефактов из BRC-потоков | артефакты иммутабельны (final-поля + защитные копии) → publication через final-семантику JMM; реестр — freeze + volatile-флаг (прототип ModuleRegistry) |
| False sharing | соседние long[] счётчиков в одной кэш-линии | горячие разделяемые структуры запрещены: оценка — read-only; обучение — офлайн и однопоточное по артефакту (DESIGN-04); при необходимости — `@Contended`-аналог через padding в off-heap-макете |
| Атомарность смены версии | promote артефакта не должен рвать исполняющиеся BRC | ссылки на ACTIVE-версии — в одном volatile-holder'е; смена = одна volatile-запись (JMM гарантирует целостность ссылки); старые версии доживают в-flight запросы (DESIGN-05 INV-M1) |
| Векторизация | C2 автовекторизует не всегда | пакетные оценки — батчи (TtUnit.evalBatch); продакшн — Vector API (инкубатор→финал к Java 25) для CLAUSESET-popcount и Hamming-recall; критерий включения — JMH-замер, не эстетика |
| Память субстратного пути | FPGA требует DMA-буферы вне кучи | FFM-сегменты — те же структуры, что читает FpgaBackend (SPEC-002 FR-D2): макет BIR-памяти (DESIGN-01 §6) проектируется DMA-совместимым с первого дня |

## 4. Измеренная цена решений (прототип, Java 17, ноутбук)

`docs/research/prototype-java`, `bench_output.txt`, 20 млн оценок, k=16:

| Вариант | нс/оценка | Комментарий |
|---|---|---|
| on-heap long[] | **0,77** | базовый путь; C2 инлайнит gather+shift |
| off-heap direct ByteBuffer | **1,03** | +34% — цена обхода лимитов кучи; DMA-совместимо |

Вывод: off-heap дороже на треть, но снимает потолок кучи и открывает путь к FPGA-DMA; оба числа на 2 порядка ниже numpy-прототипа (65 нс) и в пределах оценки ANALYSIS §4.2.

## 5. Путь субстратов (связка с ARCHITECTURE §6)

1. **JVM (этапы 0–2):** on-heap + батчи; JMH-гейты METRICS.md.
2. **Native (этап 2):** модули сигналов и Guardrail как native-приложения; правила §2.
3. **FPGA (этап 4):** FFM-DMA макет; TT → LUT 1:1 (внешнее подтверждение чисел — ULEEN, SUBSTRATE-MODELS §2.2); CLAUSESET — конвейер сравнений.
4. **Квантовый (исследование):** только как QuantumBackend за тем же контрактом evaluate (SPEC-002 FR-D3); никакого квантового кода вне бэкенда.

Инвариант пути: смена субстрата не меняет BIR-артефакты и контракты — только бэкенд исполнения. Это проверяется тестом «один артефакт — два бэкенда — бит-в-бит одинаковый выход».
