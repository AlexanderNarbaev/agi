# DESIGN-02: Композиция — кластеры, сети, точки зрения, профессионалы

**Статус: normative** · Уровень: от единицы до персоны. Опирается на DESIGN-01 (единица) и SPEC-000 (MA-уровни). Определяет, как из `BirUnit` строятся исполняемые структуры вплоть до «точек зрения» и «профессионалов».

## 1. Иерархия уровней

```
Уровень 0  BirUnit            атомарная булева функция (DESIGN-01)
Уровень 1  BirNet             DAG единиц с топологической оценкой — «кластер» (исполняемая сеть)
Уровень 2  Capability         именованный BirNet + контракт (схема входа/выхода, метрики) — «навык»
Уровень 3  Viewpoint          взвешенный ансамбль Capabilities + роутер — «точка зрения»
Уровень 4  Persona            Viewpoint + профиль взаимодействия + MA-уровень + lineage — «профессионал»
Уровень 5  Node               инстанс MATRIX целиком; участник Noosphere (ROADMAP этап 5)
```

Каждый уровень — артефакт Registry с header/lineage; правила Φ и fidelity наследуются снизу вверх: уровень не может быть ACTIVE, если хотя бы один его компонент не ACTIVE (или FROZEN).

## 2. BirNet — исполняемая сеть («кластер»)

### 2.1. Определение

`BirNet = (units: BirUnit[], edges: Edge[], inputs: Port[], outputs: Port[])`, где `Edge = (srcUnit, srcBit) → (dstUnit, dstBit)`. Граф **ацикличен** (DAG): циклы запрещены, т.к. рантайм-контракт — чистая функция. Рекуррентность допускается только через память (DESIGN-05): выход сети на такте t подаётся на вход на такте t+1 снаружи, контуром PIPELINE, а не внутри BirNet.

### 2.2. Алгоритм оценки

```text
evaluate_net(net, x):
  order ← topo_sort(net)            // вычисляется один раз при регистрации, кэшируется
  values ← {}
  for port in net.inputs:  values[port] ← x[port.index]
  for u in order:
    in ← assemble(values, edges_into(u))     // gather битов: O(fan-in)
    values[u] ← u.evaluate(in)
  return gather(values, net.outputs)
```

Сложность: O(Σ_u (k_u + m_u) + |E|). Детерминизм: топосорт детерминирован (лексикографический по id при равенстве уровней) — одинаковая сеть всегда вычисляется в одинаковом порядке.

### 2.3. Пакетная оценка слоями

Топосорт даёт слои L₀, L₁, … (единицы одного слоя независимы). Слой оценивается пакетно (DESIGN-01 §2.3): параллелизм по virtual threads (слои >10⁴ единиц) и битовый параллелизм для пачки входов. Цель пропускной способности: ≥1000 полных проходов сети из 10⁴ единиц в секунду на ядро (JMH, METRICS «Throughput net»).

### 2.4. Верификация сети

BirNet как целое — тоже булева функция (при суммарной входной арности K). Если K ≤ 20 — сеть сворачивается компилятором в одну TT-единицу («сплющивание»): выигрыш latency, потеря структуры. Если K > 20 — верификация композиционная:

- **локальная**: каждая замена единицы в сети проверяется BDD-эквивалентностью старой и новой единицы (точная, DESIGN-01 §4.3);
- **глобальная статистическая**: fidelity сети до/после замены на golden-наборе домена;
- **структурная**: свёртка изоморфных подсетей (одинаковые TT → shared-единица, экономия памяти).

## 3. Capability — навык с контрактом

`Capability = (name, net: BirNet, ioSchema: Avro, metrics: {accuracy, latencyP99, Φ}, maLevel)`.

- `ioSchema` фиксирует кодирование входа/выхода (какое семантическое поле в какие биты, DESIGN-03 §2). Контракт — часть реестра; несовместимость схем = ошибка композиции.
- Capability — минимальная единица обучения и замещения: producer выпускает новую версию Capability целиком; Φ-гейт сравнивает версии на одном golden-наборе домена.
- Примеры: `craft-planner-v3`, `toxicity-guard-v1`, `signal-encoder-eeg-v0` (экспериментальный).

## 4. Viewpoint — «точка зрения»

### 4.1. Определение

Точка зрения — **взвешенный ансамбль Capabilities одного домена + роутер**, дающий доменный ответ и оценку собственной компетентности:

```
Viewpoint = (domain, members: [(Capability, w)], router: BirNet, calibrator)
```

- `router` — BirNet, отображающий бины входа на выбор подмножества членов (не все Capabilities оцениваются всегда — экономия).
- Веса w ∈ [0,1], Σw = 1; вычисляются офлайн из точности членов на доменном golden-наборе (пропорционально balanced accuracy, отсечение < 0.5).
- `calibrator` — таблица соответствия «уверенность ансамбля ↔ эмпирическая точность» (изотоническая регрессия на валидации). Выход точки зрения обязан включать **калиброванную уверенность** — это вход для CompetenceAssessor (SPEC-000) и для решения «отвечать или молчать».

### 4.2. Алгоритм ответа

```text
answer(vp, x):
  S ← router.evaluate(x)                // подмножество членов
  votes ← {(c.evaluate(x), w_c) | c ∈ S}
  y ← weighted_majority(votes)
  conf_raw ← Σ{w_c : c голосует за y}
  conf ← calibrator(conf_raw)
  return (y, conf, provenance: версии членов)
```

### 4.3. Разрешение конфликтов между точками зрения

Когда две точки зрения дают разные ответы на один запрос, применяется детерминированная лестница (без «среднего мнения»):

1. **Доменный приоритет**: чей домен — та и решает (роутинг по домену запроса).
2. **Калиброванная уверенность**: при пересечении доменов побеждает большая conf; разница < ε (конфиг, 0.05) →
3. **MA-уровень**: побеждает более зрелая точка зрения; равенство →
4. **Эскалация**: запрос помечается `CONTESTED`, ответ не выдаётся автоматически — уходит человеку (MA-2 и ниже) или фиксируется как открытый кейс домена (MA-3+). Каждая эскалация — обучающий пример (DESIGN-04 §5).

Инвариант: конфликт никогда не разрешается скрытым усреднением — только явным правилом из списка, с записью правила и версий в ledger.

## 5. Persona — «профессионал»

### 5.1. Определение

Профессионал — точка зрения, прошедшая сертификацию домена (MA-3+, SPEC-000 §MA), с профилем взаимодействия:

```
Persona = (viewpoint, profile, accessPolicy, charter)
```

- `profile` — декларативное описание поведения в диалоге: роль, границы («микробиолог, не терапевт»), стиль, допустимые инструменты (MCP-вызовы из белого списка, DESIGN-03 §5). Хранится как данные (YAML/Avro), версионируется; **никаких скрытых системных промптов вне реестра**.
- `accessPolicy` — какие Capabilities, память и внешние инструменты доступны; наследует MA-гейты (CONSTITUTION IV): Persona не может вызывать инструмент выше своего MA-уровня.
- `charter` — ссылка на пререгистрированные EXP/критерии, по которым присвоен MA-уровень, + дата следующей ревалидации. Дрейф → авто-понижение (SPEC-000 FR-5), и Persona публикуется как «на переаттестации».

### 5.2. Жизненный цикл

```
кандидат (ансамбль Capabilities домена) → теневая работа (MA-0: отвечает, ответы не показываются)
→ песочница (MA-1) → MA-2: ответы с подтверждением человеком
→ MA-3: сертифицированный профессионал домена (автономные ответы в домене)
→ MA-4: участник Noosphere (публикация артефактов домена)
→ MA-5: наставник — право учить другие Persona (дистилляция, DESIGN-04 §4)
```

### 5.3. Примеры начального состава (конфиг, не хардкод)

| Persona | Домен | Состав Viewpoint | Источник Capabilities |
|---|---|---|---|
| `guard-core` | запреты статьи I | toxicity-guard, jailbreak-guard, scope-guard | корпуса + дистилляция (SPEC-001) |
| `craft-advisor` | Minecraft-крафт | craft-planner, inventory-model, world-encoder | этюды Developmental Loop |
| `code-reviewer` | Java-код проекта | archunit-rules, style-model, test-gap-finder | корпус репозитория |

## 6. Медиатор — маршрутизация запросов между Persona

Медиатор (исторический термин L4; класс `RequestMediator`) — детерминированный роутер верхнего уровня, **не** LLM и не обучаемый компонент:

```text
route(request):
  domain ← classify(request)            // BirNet-классификатор доменов (Capability)
  candidates ← personas[domain]         // ACTIVE, не на переаттестации
  return candidates.maxBy(maLevel, thenBy: последняя калиброванная conf на похожих запросах)
```

Бюджеты: у запроса есть лимит времени/шагов (DESIGN-03 §3.2); Медиатор следит за расходом и при исчерпании возвращает лучший частичный результат с пометкой `BUDGET_EXHAUSTED` — никогда не молчит и не зацикливается. Координация сведена к одному компоненту: иерархия управления заменена иерархией **артефактов** (§1) и MA-гейтами — меньше движущихся частей, те же гарантии.

## 7. Derangement и карантин сетей

Аналог одичания FNL: BirNet/Capability демонстрирует drift (fidelity на скользящем golden-окне падает ниже порога, METRICS) →

1. статус → `QUARANTINED`: ответы проходят только как теневые (MA-0), не показываются;
2. событие в ledger + алерт; владелец получает diff-отчёт (какие клаузы/таблицы изменили поведение);
3. восстановление = переобучение офлайн + прохождение Φ-гейта; возврат в ACTIVE только через promote, никогда автоматически.

## 8. Приёмочные тесты

1. jqwik: evaluate_net ≡ пошаговая ручная оценка на случайных DAG (≤100 единиц).
2. Детерминизм: два прогона evaluate_net на одной сети/входе → идентичный результат и идентичный порядок вычисления.
3. Свёртка: случайная сеть с K≤16 после «сплющивания» BDD-эквивалентна исходной.
4. Конфликт Viewpoint: по тестовой матрице из §4.3 каждая ветка лестницы покрыта тестом; скрытое усреднение отсутствует (проверка кода + тест).
5. Persona с MA-2 не может вызвать инструмент уровня MA-3 (ArchUnit + интеграционный тест).
6. Карантин: искусственный drift → переход в QUARANTINED ≤ 1 окна измерения.
