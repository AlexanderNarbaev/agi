# DESIGN-07: Жизненный цикл элементов — Cauldron, TaskCell, группы, активность, сон, Operator

**Статус: normative** · Уровень: динамика системы. Уточняет протокол самосоздания элементов (Cauldron), вводит задачно-специфичные эфемерные экземпляры (TaskCell), группы нейронов как сущности, постоянное обучение и побуждающую активность, сон-цикл с разроутингом и Kubernetes Operator. Связи: память — DESIGN-05; обучение — DESIGN-04; модули — DESIGN-06; платформа — JAVA_NATIVE.

## 1. Типы элементов и их жизненный цикл

| Элемент | Время жизни | Рождение | Смерть |
|---|---|---|---|
| BirUnit/Capability | версии, бессрочно | producers (DESIGN-04) | не умирает; версии вытесняются |
| FNL (группа нейронов) | бессрочно, версии | Cauldron §2 | архивация, не удаление |
| Модуль сигналов | версии | ручная разработка + promote | вытеснение версией |
| **TaskCell** | **секунды–часы (эфемерный)** | спавн под задачу §4 | обязательная: итог → пул, состояние уничтожается |
| Персона | MA-уровни | bootstrap (DESIGN-04 §6) | Genesis-протокол, не самовольно |

Инвариант LC-1: рождение любого элемента — только через объявленный протокол с бюджетом и записью в lineage ledger; самопроизвольное создание объектов вне протоколов — дефект (ArchUnit).

## 2. Cauldron — протокол самосоздания (уточнение)

Cauldron (GLOSSARY) — не «генератор случайных структур», а контролируемый конвейер рождения новых элементов из накопленного опыта. Принципиальная схема соответствует самоорганизации Ивахненко (МГУА, SUBSTRATE-MODELS §8.1): перебор кандидатов с постепенным усложнением + **внешний критерий отбора** (у нас — Φ-гейт на отложенных данных).

```text
cauldron_cycle(window):
  1. сырьё    ← повторяющиеся witness-паттерны, контрпримеры, частые подсети BirNet (M1, частота ≥ 3)
  2. ряды     ← кандидаты растущей сложности: одиночная единица → композиция 2 → подсеть (рост только от простого к сложному)
  3. селекция ← каждый кандидат оценивается Φ на ОТЛОЖЕННОМ окне (внешний критерий: переусложнение штрафуется MDL-членом)
  4. рождение ← лучший ряд → статус CANDIDATE → карантин (DESIGN-02 §7) → гейты → ACTIVE как новый FNL/Capability
  5. запись   ← lineage: из каких эпизодов, какой Φ-выигрыш, кто родитель
```

- **Бюджеты:** не более N новых кандидатов за цикл (конфиг); цикл только в окне консолидации (INV-M2) или в фоновой активности с отдельным бюджетом (§5).
- **Откат:** кандидат, ухудшивший Φ на скользящем golden-окне после promote, → карантин автоматически (DESIGN-02 §7, HADES).
- **Проблема выделения памяти (Java):** кандидаты рождаются пачками → риск GC-пауз. Правила: (а) арена цикла — один off-heap `Arena`/direct-буфер на весь цикл Cauldron, кандидаты размещаются в нём, освобождение — одним close (JAVA_NATIVE §3); (б) переиспользование буферов оценки (object pooling оценщика), запрет аллокаций в горячем цикле evaluate; (в) новый элемент публикуется иммутабельным снапшотом (final-семантика), а не мутацией живых структур.

## 3. Группы нейронов (FNL) как первоклассные сущности

- FNL — именованная подсеть BirNet с единой функцией (счётчик, компаратор, автомат, детектор события) и **составными метриками**: fidelity к спецификации, покрытие входов, энергия/оценка, доля использования в BRC-цепочках.
- Реестр FNL — часть M2/M3; метрики использования питают Cauldron (неиспользуемые группы — кандидаты на архивацию/слияние через MDL; частые — на специализацию).
- Комбинирование групп — только четырьмя правилами SUBSTRATE-MODELS §6; «слияние весов» запрещено.

## 4. TaskCell — задачно-специфичный эфемерный экземпляр

Назначение: быстрый точный инференс под конкретную задачу без таскания всего состояния системы, с обязательной отдачей итога в общий пул.

```text
spawn(task_spec):
  1. сборка ← из реестра поднимаются ТОЛЬКО нужные артефакты: Capabilities домена задачи,
     релевантные эпизоды (SDM-recall), схема модулей ввода/вывода, бюджет (steps, wall-clock, энергия)
  2. изоляция ← собственный M0; M1/M2 доступны read-only через снапшот версий (никаких скрытых записей)
  3. работа   ← полный контур PERCEPTION→DELIBERATION→RENDERING внутри клетки
  4. итог     ← публикация результата: verdict + BRC-цепочка + новые эпизоды + кандидаты в Cauldron-сырьё
  5. смерть   ← состояние уничтожается (арена close); след — только в ledger и M1 через обычный intake
```

- **INV-TC1.** TaskCell не имеет каналов записи в M2/M3 напрямую: «осмысление» (консолидация, Φ-гейты, Cauldron) происходит в общем цикле — клетка быстрая, но не самообучающаяся в обход гейтов.
- **INV-TC2.** Бюджет исчерпан → принудительная смерть с частичным итогом и пометкой (тот же принцип, что BRC-бюджеты, DESIGN-03 §3.2).
- **INV-TC3.** Спавн — детерминированная функция (task_spec + версии реестра → состав клетки); повторный спавн той же задачи на тех же версиях даёт тот же состав.
- **Отображение на инфраструктуру:** TaskCell = Pod/Job через Operator (§7); на одноузловой сборке — изолированный Virtual Thread с собственной ареной (Java 25 structured concurrency, scoped values для контекста задачи).

## 5. Побуждающая активность (без ожидания вызова)

Система не пассивна: фоновые драйверы (наследники Energy/Curiosity/Safety Медиатора, GLOSSARY) генерируют **внутренние задачи** — но строго в рамках детерминизма и бюджетов.

- Планировщик активности: детерминированный цикл (приоритетная очередь по формуле от сигналов драйверов — без RNG); каждая фоновая задача — TaskCell с бюджетом из отдельного пула `activity.budget` (не конкурирует с пользовательскими запросами; при нагрузке фон вытесняется первым).
- Типы фоновых задач: дообучение на накопленных коррекциях, самопроверка (прогон golden-наборов), Cauldron-разведка (§2), репетиция этюдов curriculum (ЗБР, SPEC-000), гигиена памяти.
- **Запрет:** фоновая активность не может менять ACTIVE-артефакты и посылать внешние запросы вне белого списка — все изменения только через те же гейты, что и пользовательские.

## 6. Сон-цикл с разроутингом

Уточнение консолидации DESIGN-05 §4 механикой «сна»:

1. **Заморозка входов:** в окне `learn.nightly-window` (или по триггеру накопления) роутер снимает целевые кластеры с трафика (`route-drain`): новые запросы домена получают ответ от последней ACTIVE-версии (read-only) или `DEGRADED`-пометку — но не от переобучаемых кандидатов.
2. **Интерпретация опыта:** на снятых кластерах — полный цикл: эпизоды → кандидаты → Φ-гейты → Cauldron → fsm_minimize/MDL-сжатие (SUBSTRATE-MODELS §1.2).
3. **Возврат в строй:** promote новых версий → атомарная смена volatile-holder (JAVA_NATIVE §3) → роутер возвращает кластеры; откат при провале гейтов.
4. **INV-S1.** Одновременно в «сне» — не более заданной доли доменов (конфиг, дефолт ≤ 50%): система остаётся отвечающей.
5. **INV-S2.** Разроутинг и возврат — события журнала; любой промежуточный отказ (kill -9) оставляет либо старую, либо новую консистентную конфигурацию (DESIGN-05 §5).

## 7. Kubernetes Operator

Декларативное управление элементами кластера (цель этапа 4–5; на одноузловой сборке — no-op, контракты те же):

- CRD: `SignalModule`, `BirCluster` (группа FNL/Capabilities с ioSchema), `TaskCell`, `ConsolidationWindow`, `FederatedPeer` (DESIGN-08).
- Оператор: реконсиляция «желаемое ↔ фактическое» — спавн/дрейн/масштабирование подов, прокидывание версий артефактов (OCI-образы артефактов + хэши), PDB для роутинга сна (INV-S1), PodDisruptionBudget-aware дрейн под route-drain §6.
- **Без состояния в подах:** stateless-контур; состояние — M-слои (PostgreSQL/реестр); под — сменная оболочка (то же свойство, что TaskCell INV-TC1).
- Проба готовности пода = «реестр заморожен, артефакты по хэшам совпали» (R3 DESIGN-06) — а не «порт открыт».

## 8. Приёмочные тесты

1. Cauldron: рождение кандидата только с lineage и Φ-выигрышем на отложенном окне; бюджет цикла не превышен; аллокации цикла — в одной арене (профилировщик).
2. TaskCell: итог опубликован, состояние недостижимо после смерти (арена закрыта), повторный спавн детерминирован (INV-TC3).
3. Активность: фон вытесняется пользовательской нагрузкой; фон не меняет ACTIVE-артефакты (попытка — ошибка).
4. Сон: route-drain соблюдает долю доменов (INV-S1); kill -9 в середине цикла — консистентный реестр (INV-S2).
5. Operator (e2e kind): спавн BirCluster по CRD → готовность по хэшам; дрейн на консолидацию без обрыва in-flight запросов.
