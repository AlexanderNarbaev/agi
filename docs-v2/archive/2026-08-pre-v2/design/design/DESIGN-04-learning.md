# DESIGN-04: Обучение — предобучение, дистилляция, интерактивное взаимодействие

**Статус: normative** · Уровень: офлайн-контур producers (SPEC-002 §2) + интерактивные протоколы. Всё обучение вне рантайма (CONSTITUTION II.2): producer выпускает новый артефакт → Φ-гейт → promote (DESIGN-01 §1). Этот документ — алгоритмы producers и протоколы участия человека.

## 1. Карта способов обучения

| Способ | Когда | Выход | Главный риск | Защита |
|---|---|---|---|---|
| Корпусные данные (размеченные примеры) | всегда, если есть корпус | CLAUSESET/TT | смещение корпуса | golden-набор, разбор worst-case |
| Дистилляция LLM (SPEC-001 этап B) | нет корпуса, есть учитель | CLAUSESET | fidelity-иллюзия | BDD-экв. + golden-векторы + worst-case |
| Интерактивное обучение (учитель в цикле) | домен владельца | CLAUSESET, корпус пополняется | шумные коррекции | согласие 2 из 3, ledger коррекций |
| Эволюция топологий (ГА) | структура сети неизвестна | BirNet | дорого, нестабильно | бюджеты, EXP-003, superseded при проигрыше |
| Самонаблюдение (контрпримеры BRC) | постоянно | пополнение корпуса | петля самоусиления | человек утверждает вход в корпус |

## 2. Producer 1: TsetlinTrainer (первичный, SPEC-002 этап B)

### 2.1. Модель

Команда из C клауз (DNF, DESIGN-01 §3). Каждый литерал каждой клаузы — конечный автомат с 2N состояниями: состояния 1..N — литерал исключён, N+1..2N — включён. Гиперпараметры: число клауз C, специфичность s ≥ 1, порог голосования T, бюджет состояний N (дефолты: C=100, s=3.9, T=15, N=100 — подлежат EXP-002).

### 2.2. Алгоритм обучения (multiclass, обратная связь I/II)

```text
train(samples, epochs):
  for epoch, for (x, y) in shuffle(samples, seed):
    sum ← Σ_c clause_c(x) · sign_c            // голосование; sign_c = ±1 по паритету клаузы
    ŷ ← clip(sum, -T, T)
    for each clause c:
      if предположение клаузы верное для y:
        feedback I с вероятностью (T - ŷ)/2T:
          за true-литерал x_i=1: награда (s-1)/s, штраф 1/s   // автомат → включить
          за x_i=0: штраф (s-1)/s, награда 1/s                // автомат → исключить
          усиление «памяти»: награда исключённым литералам 1/s
      else (клауза поддерживает неверный класс):
        feedback II с вероятностью (T + ŷ)/2T:
          за x_i=0 у включённого литерала: награда 1          // борьба с ложными срабатываниями
  return ClauseSet(literals with state > N)
```

Тип I учит распознавать паттерн и забывать шум (исключённые литералы медленно «вспоминаются» — встроенная стохастическая регуляризация); тип II гасит ложноположительные срабатывания. Свойства, фиксируемые jqwik-тестами: состояния автоматов всегда в [1, 2N]; при фиксированном seed обучение воспроизводимо бит-в-бит; выученный ClauseSet детерминированно исполняется рантаймом (property-тест голосования, SPEC-002 FR-B2).

### 2.3. Φ-контур

Φ = MDL-рачет (CONSTITUTION III): `L = bits(ClauseSet) + bits(ошибки на валидации | ClauseSet)`. По эпохам L не возрастает; рост → откат к лучшему чекпоинту. Итоговая модель — минимум L, а не последняя эпоха.

## 3. Producer 2: Distiller (SPEC-001 этап B — здесь алгоритм)

### 3.1. Конвейер

```text
distill(teacher, domain_corpus):
  1. X ← доменные входы; A ← teacher_activations(X)      // DJL/ONNX из JVM, golden-векторы
  2. bin ← quantile_binarize(A, B бит/канал)             // границы — артефакт (INV-P1)
  3. S ← importance_select(bin, y_teacher)               // top-K бит по взаимной информации с целью;
                                                         // НЕ случайный выбор (запрещён, SPEC-001 §0)
  4. base ← TREPAN(teacher, S)                           // извлечение дерева:
     - best-first расширение узлов
     - в узле: сплит по признаку с макс. информационным выигрышем
     - оракул-запросы к teacher для недопредставленных областей (active querying)
     - критерий остановки: fidelity на валидации ≥ 0.9 ИЛИ бюджет запросов
  5. clauses ← path_to_clause(base)                      // путь корень→лист = клауза
  6. clauses ← TsetlinTrainer.refine(clauses, corpus)    // дообучение на реальных данных
  7. return ClauseSet + header{provenance, fidelity}
```

### 3.2. Гейты выпуска (все обязательны, SPEC-001 FR-B6/B7)

1. fidelity ≥ 0.9 на held-out (и ≥ 0.85 на каждом worst-case срезе домена);
2. BDD-эквивалентность там, где k ≤ 16 (точная), статистическая — иначе;
3. Φ: fidelity монотонна по итерациям корпуса; ухудшение — откат;
4. worst-case разбор: срезы домена, где fidelity минимальна, публикуются в отчёте EXP-001.

## 4. Producer 3: интерактивное обучение (учитель в цикле)

Протокол для доменов владельца (предобучение Persona, §4.3 — это и есть «предобучение» интерактивное).

### 4.1. Цикл коррекции

```text
loop:
  (y, conf, trace) ← persona.ask(x)                 // DESIGN-02 §4.2
  if conf < θ_say:                                   // «молчание компетентности»
    emit ASK_TEACHER(x, candidates)                  // система спрашивает, не угадывает
  teacher: подтвердить / исправить / запретить
  correction ← {x, y_was, y_new, teacher_id, ts} → ledger (append-only)
```

### 4.2. Правила включения коррекции в обучение

- Коррекция попадает в корпус только с подтверждением: либо повторной аналогичной коррекцией (2 из 3 похожих случаев), либо явным «включить в корпус» от владельца.
- Коррекция, противоречащая FROZEN-артефактам (статья I), отвергается автоматически и логируется как инцидент.
- Каждое переобучение по корпусу коррекций — обычный выпуск артефакта: Φ-гейт, fidelity, версия; **никакого онлайн-апдейта весов**.

### 4.3. Предобучение Persona (bootstrapping)

Порядок наполнения нового домена:

1. **Пассивный этап**: доменные тексты/логи → PERCEPTION-кодировка → накопление корпуса (без ответов пользователю, MA-0).
2. **Дистилляция** (§3) от внешнего учителя на корпусе → первый CANDIDATE-ансамбль.
3. **Интерактивный этап** (§4.1): владелец подтверждает/исправляет; метрика — доля подтверждений (растёт → готовность к MA-2).
4. **Экзамен домена**: preregistered golden-набор → MA-гейт (SPEC-000 FR-5) → сертификация.
5. **Наставничество** (MA-5): Persona-учитель дистиллирует свой домен в новые Persona — тот же конвейер §3, где «teacher» = внутренняя Persona (provenance фиксирует цепочку: LLM → Persona_A → Persona_B).

### 4.4. Fading подсказок (связь со SPEC-000)

Интерактивное обучение подчиняется scaffolding-расписанию SPEC-000 FR-4: доля запросов учителя с подсказкой снижается по заранее зафиксированному графику (линейно по эпизодам, дефолт 100%→0% за 20 эпизодов); обучение без fading недействительно для EXP (зависимость от подсказок = не компетенция).

## 5. Producer 4: самонаблюдение (контрпримеры как корпус)

Каждый `CONFLICT(witness)` и каждый отказ Guardrail — кандидат в корпус (DESIGN-03 §3.2). Пайплайн: кандидат → анонимизация → утверждение владельцем → корпус домена → §2/§3 переобучение. Запрещено: автоматическое включение без утверждения (петля самоусиления), включение сырых персональных данных (нарушение приватности, CONSTITUTION I/IV).

## 6. Producer 5: GATopologySearch (экспериментальный, EXP-003)

Поиск структуры BirNet: геном = список рёбер над фиксированным набором единиц; операторы: add/remove edge, replace unit (из реестра ACTIVE), split unit. Фитнес = Φ домена − λ·(узлы + рёбра). Правило решения о статусе механизма — SPEC-002 FR-C1 (зафиксировано до запуска EXP-003). Проигравшие механизмы — superseded, не удаляются.

## 7. Расписания и бюджеты

| Параметр | Дефолт | Где конфиг |
|---|---|---|
| Эпохи Tsetlin | 50, ранняя остановка по Φ | `tsetlin.epochs` |
| Бюджет запросов оракула (дистилляция) | 10⁵ | `distill.oracle-budget` |
| Порог молчания θ_say | 0.6 (калиброванная conf) | `persona.theta-say` |
| Fading: 100%→0% | 20 эпизодов | `scaffold.fading-episodes` |
| Окно переобучения по коррекциям | ночное, 1×/сутки | `learn.nightly-window` |

## 8. Приёмочные тесты

1. Воспроизводимость: train с фиксированным seed дважды → идентичный ClauseSet (байтовое равенство).
2. jqwik автоматов: границы состояний, монотонность feedback I/II на синтетике.
3. TREPAN на эталонной задаче (XOR-8 + шум): fidelity ≥ 0.95, бюджет оракула не превышен.
4. Коррекция, противоречащая FROZEN, отвергнута + инцидент в ledger.
5. Интерактивный цикл end-to-end (Testcontainers): ASK_TEACHER → коррекция → ночное переобучение → promote → доля подтверждений растёт на синтетическом учителе.
6. Fading: попытка сдать доменный экзамен с активными подсказками → эксперимент помечен недействительным.
