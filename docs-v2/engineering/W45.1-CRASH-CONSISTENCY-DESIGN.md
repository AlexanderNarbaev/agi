# W45.1 — CRASH-CONSISTENCY DESIGN

**Status:** implemented. **Scope:** the lifecycle of one cognitive request, the idempotency
mapping that names it, and the recovery of a request whose process was terminated.
**Prepared:** 2026-11-04.

This document states how MATRIX behaves when the JVM is killed at an arbitrary point between
accepting a request and durably completing its outcome.

---

## 1. The question this wave answers

W45.0 made the cognitive state durable. Durable is not the same as crash-consistent. W45.0 left
three questions open, and this wave closes them:

| the question | the W45.0 answer | the W45.1 answer |
|---|---|---|
| what happens when the process dies with a request claimed? | the key stayed `IN_PROGRESS` **forever**; the retry waited two seconds and reported "still running" | the owner is asked whether it is alive; a dead owner's request is classified from its last durable checkpoint and either recovered or declared indeterminate |
| what happens when the request fails **after** a committed observation? | the mapping was **DELETED**, so the next delivery started a second episode and committed the same observation **twice** | the mapping is never deleted; the failure is recorded with the classification that says whether the work may be repeated |
| what does the episode of a dead request look like? | it stayed **OPEN** — the store said the cycle was still running | the recovery closes it with a terminal `INTERRUPTED` event that names what had happened |

---

## 2. The request lifecycle

### 2.1 The states

`io.matrix.cognitive.RequestExecutionState` — nine states, of which six are non-terminal:

| state | meaning | may it be executed again? |
|---|---|---|
| `CLAIMED` | the key is claimed and the identities are allocated | — |
| `IN_PROGRESS` | the execution is running | — |
| `COMPLETED` | the request finished and its outcome is durable | **no** — the outcome is replayed |
| `FAILED_NO_EFFECT` | the execution failed before any durable or external effect | **yes** — this is the only failure that may be repeated |
| `INTERRUPTED_NO_EFFECT` | the process died before any durable effect | **yes** — in the SAME episode |
| `INTERRUPTED_PARTIAL` | the process died after partial durable work | **no** — the outcome is indeterminate |
| `INDETERMINATE` | an external effect may have happened and its result was not persisted | **no** |
| `RECOVERY_REFUSED` | a recovery was attempted and refused | **no** — it needs a human decision |

**The rule that makes the machine safe:** a request may be executed again only from a state that
**proves** nothing was written. Everything else is either replayed or declared indeterminate.

### 2.2 The checkpoints

`io.matrix.cognitive.RequestCheckpoint` — the durable checkpoints of one execution. Each is
written to the store **after** the work of its phase has been committed and **before** the next
phase starts, so a checkpoint never claims more than the store already holds.

```
CLAIMED → EPISODE_OPENED → PREDICTION_WRITTEN → EXPERIMENT_EXECUTED
        → OBSERVATION_COMMITTED → REGULATION_PERSISTED → EPISODE_CLOSED
        → OUTCOME_PERSISTED → IDEMPOTENCY_COMPLETED
```

The point of no return is `OBSERVATION_COMMITTED`: from that checkpoint on, a repeated
execution would commit the same observation again. `EPISODE_OPENED` is already a durable
effect for a second reason — the episode row exists, and an episode may be opened only once.

### 2.3 The identity of a request

The claim allocates the identities **before** the work starts and stores them:

| identity | where it lives | when it is allocated |
|---|---|---|
| the idempotency key | the caller's | by the caller |
| the request id | `cognitive_idempotency.request_id`, derived from the key | at the claim |
| the signal id | `cognitive_idempotency.signal_id` | at the claim |
| the episode id | `cognitive_idempotency.episode_id` | at the claim |
| the payload fingerprint | `cognitive_idempotency.fingerprint` | at the claim |
| the execution token | `cognitive_idempotency.owner_token` | at the claim |

**A request that is executed again keeps every one of them.** A retry after a crash continues
the same logical execution in the same episode; it is never given a second episode. The claim
statement is an UPSERT whose conflict clause updates only the owner, the state and the
checkpoint — never the episode id, the signal id or the request id.

## 3. The ownership of a claim

### 3.1 The token

`io.matrix.cognitive.OwnershipToken` — the pid of the owning process, the **start instant** of
that process and a random **instance token**.

The start instant is what makes the check correct against pid recycling: a pid that exists but
belongs to a process that started later is not the owner. The instance token distinguishes two
instances inside one JVM.

### 3.2 The classification

`OwnershipToken.classify(owner, mine)` returns one of three answers:

| the owner is | the answer | what the registry does |
|---|---|---|
| this very instance | `MINE` | the request is in progress; the work is not repeated |
| another instance of this process | `DEAD` | the old instance is gone; the request is recovered |
| another process, alive | `LIVE_OTHER` | the work is **not** stolen; the retry waits and then reports |
| another process, dead | `DEAD` | the request is recovered |

**A start-up rule that marked every `IN_PROGRESS` row as abandoned would be wrong in the
simplest way possible:** it would steal the work of a process that is alive and working. The
classification asks the operating system instead.

### 3.3 The topology this assumes, stated plainly

**MATRIX is one writer process per database file.** The liveness check is a check on the local
host. If two JVMs opened the same SQLite file from different containers, the pid of the other
process would not be visible and the claim would be wrongly considered dead. That is outside
the supported topology, and the rule below is what keeps the failure mode safe inside it:

> **When the liveness of an owner cannot be disproved, the claim is treated as OWNED.**

A claim that is wrongly considered alive is visible and recoverable by an operator. A claim
that is wrongly considered dead is a duplicated execution. The asymmetry is deliberate.

## 4. The recovery

### 4.1 When it runs

- **At start-up**, once, when the service builds its kernel: every unfinished request whose
  owner is gone is classified and its episode is closed.
- **At a claim**: a retry that finds a claim whose owner is gone recovers it immediately, so
  the caller is not left waiting for a process that will never answer.

### 4.2 What it decides

The classification is derived from the **last durable checkpoint**, never from a guess:

```
checkpoint is CLAIMED (or absent)   → INTERRUPTED_NO_EFFECT → the request may be executed again
checkpoint is at or after EPISODE_OPENED → INTERRUPTED_PARTIAL → the request may NOT be executed again
```

The decision is written to the store (`cognitive_idempotency.recovery`) and appended to the
append-only history (`cognitive_request_event`), so it can always be read back and explained.

### 4.3 What it does to the episode

An episode that a dead process left open is closed with a terminal event:

```
cognitive_event(id, episode_id, sequence, type='INTERRUPTED', actor='Recovery', detail)
```

The event is part of the append-only stream, so the history of the episode says exactly where
it stopped. The store must never say that a cycle is still running when it is not.

### 4.4 The recovery algorithm

```
for each request that is not in a terminal state:
    if the owner is MINE or LIVE_OTHER:      continue      # the work is not stolen
    checkpoint := the last durable checkpoint
    if checkpoint implies no durable effect:
        state := INTERRUPTED_NO_EFFECT
        the next delivery takes the request over, in the SAME episode
    else:
        state := INTERRUPTED_PARTIAL
        close the episode with an INTERRUPTED event
        the next delivery is told: INDETERMINATE
```

## 5. The failure of a running request

### 5.1 The distinction that matters

The W45.0 code caught `RuntimeException` and **deleted** the mapping. The deletion was the
defect: a failure is not the same thing as "nothing happened". An exception can arrive after an
episode was opened, after a prediction was written, after an experiment ran, after the
epistemic transaction committed, after a task or an error was recorded, after the regulatory
state moved, after some trace events were written.

**The mapping is never deleted.** There are two different terminal paths, and the difference
between them is the whole point:

| the failure | what the caller gets | what a retry does |
|---|---|---|
| a **controlled** failure inside the cycle | a `FAILED` outcome, durable and replayable | replays the `FAILED` outcome; no work is done |
| a **crash** of the process | nothing — the caller never got an answer | the recovery classifies it; either it executes again in the same episode, or it is `INDETERMINATE` |

### 5.2 The controlled failure

The kernel catches a runtime failure, writes a `FAILURE` step into the trace, closes the
episode, and returns a `FAILED` outcome whose notes say what had already happened — the same
truthfulness the W45.0 timeout path has. The service stores that outcome under the key, so the
request is **COMPLETED with a durable terminal outcome**.

A terminal failure is never converted into a normal answer: the HTTP status is `500`, the
outcome's status is `FAILED`, and the retry replays exactly that.

### 5.3 The fence

A process that lost its request to a recovery **cannot complete it**. The completion is
written with `WHERE key = ? AND owner_token = ?`, so a stale owner is refused with a conflict
rather than overwriting the outcome of the new owner.

## 6. The persistence boundaries

| what | where | atomic with what |
|---|---|---|
| the claim | `cognitive_idempotency` | the identities of the execution — one UPSERT |
| the checkpoint | `cognitive_idempotency.checkpoint` | its own write, after the phase it describes |
| the outcome + the completion | `cognitive_idempotency` | one UPDATE, fenced by the owner |
| the epistemic observation | the knowledge store | the source, the evidence, the case, the link and the disposition — **one transaction** |
| the regulatory state | `cognitive_regulatory_state` + `cognitive_regulatory_event` | one transaction, with the provenance of the change |
| the trace | `cognitive_event` | one row per step, append-only |

**The two stores are separate.** The knowledge-store observation transaction is on its own
JDBC connection; the cycle is **not** one SQLite transaction across both stores, and nothing
in this wave claims that it is. What exists instead is the **checkpoint protocol**: the
knowledge-store commit happens between two checkpoints, so a crash either side of it is
classifiable, and the request is never silently re-executed across that boundary.

### 6.1 The finalisation, and what is not atomic

The terminal sequence is: the trace is written, the episode is closed, the outcome snapshot is
persisted, the idempotency record is completed. These are separate writes, and the wave does
**not** claim they are one transaction. The consequence is stated in the recovery matrix: a
crash between them leaves the request `INTERRUPTED_PARTIAL`, and the outcome is not
reconstructed from the trace — an outcome that cannot be established is not invented.

What the wave DOES guarantee about the finalisation: **a failed JSON outcome encoding cannot
make a completed cycle executable again.** The encoding happens before the completion write,
and the completion is fenced by the owner, so a failure at the encoding leaves the request
`IN_PROGRESS` with its last checkpoint — never a deleted mapping and never a silent re-run.

## 7. The external side effects

### 7.1 What the micro-world's probe is

`LampEnvironment.probe(...)` is a **pure deterministic computation** of a two-variable truth
table. It touches nothing outside the process, it has no durable effect of its own, and
repeating it with the same input yields the same answer. That is why the wave may treat a
crash after the probe as a crash with no external effect.

### 7.2 What the wave does NOT claim

**No exactly-once guarantee is made for an external side effect.** The micro-world has none;
a future stateful environment would. The contract such an environment must satisfy, written
down before it is needed:

| the requirement | why |
|---|---|
| a stable action id | so that a replay can be recognised as the same action |
| a durable intent before the execution | so that a crash between the intent and the effect is classifiable |
| an idempotency requirement on the effect itself | so that repeating it is harmless |
| a recorded outcome | so that the effect is not repeated blindly |
| an explicit recovery after an uncertain interruption | the answer may be `INDETERMINATE` |

**A general action framework is NOT introduced.** The micro-world does not need one, and the
directive forbids a framework without evidence that one is required.

## 8. The fault injection

`io.matrix.cognitive.RequestFailpoint` — a deterministic injection point, configured by the
system property `w45.failpoint`, with the marker file named by `w45.failpoint.marker`.

- **There is no HTTP surface for it.** No request can make the production process stop.
- **The production behaviour does not depend on timing.** Without the property the failpoint
  does not exist.
- **It blocks rather than halts.** The process writes the marker and then stops making
  progress until it is killed from outside. That is what makes the death a **real
  `SIGKILL`**: a self-halt would run the shutdown hooks, and the difference between a graceful
  death and a killed one is precisely what this wave is about.

The two modes:

| mode | what it does | who uses it |
|---|---|---|
| `BLOCK` | writes the marker, then waits to be killed | the integration journey (`scripts/w45-cognitive-recovery-journey.sh`) |
| `THROW` | throws at the checkpoint | the unit tests, which inject a failure without killing anything |

## 9. The execution budget is unchanged

The W45.0 `CycleDeadline` is preserved exactly: a monotonic deadline, checked at the phase
boundaries, with no hard wall-clock bound claimed for the operations that cannot be
interrupted. W45.1 adds three things and changes nothing else:

- a timeout is a **terminal, replayable** outcome: the request is COMPLETED with the
  `RESOURCE_LIMITED` outcome, and a retry replays it without doing the work again;
- a timeout **after** an epistemic side effect does not cause the effect to be repeated: the
  checkpoint that follows the commit is `OBSERVATION_COMMITTED`, and the request is never
  re-executed across it;
- a timeout **before** any effect is a `FAILED_NO_EFFECT` failure and the request may be
  executed again.

**No strict 250 ms response guarantee is claimed.** The figure remains a configured
convention.

---

## 10. What is guaranteed, and what is not

| property | guarantee | how it is proved |
|---|---|---|
| a killed process cannot leave a request permanently claimed | the recovery classifies it at start-up and at the next claim | `CognitiveRequestLifecycleTest`, the journey script |
| the same key and the same payload never create a second logical request | the identities are allocated at the claim and kept | `CognitiveRequestLifecycleTest` |
| the same key with a different payload is still a conflict | the fingerprint is compared before anything else | `IdempotencyRegistryTest` |
| a partially committed request is never treated as never executed | the classification comes from the durable checkpoint | `CognitiveRequestLifecycleTest` |
| a retry cannot reset a completed result | the completion is fenced by the owner and the state is `COMPLETED` | `CognitiveRequestLifecycleTest` |
| a retry cannot duplicate an observation | the request is never re-executed across `OBSERVATION_COMMITTED` | `CognitiveRequestLifecycleTest`, the journey script |
| a process that lost the request cannot complete it | the completion is `WHERE owner_token = ?` | `CognitiveRequestLifecycleTest` |
| every terminal state and recovery decision is inspectable | `cognitive_request_event` is append-only | `CognitiveRequestLifecycleTest` |
| no false exactly-once claim is made for an external effect | the micro-world's probe is pure, and the contract for a stateful one is written down | the design document, §7 |

### What is NOT guaranteed

- **A request whose owner is alive is never recovered.** If a process hangs, its request stays
  claimed until the process dies. That is the price of not stealing work.
- **The finalisation is not one transaction.** A crash between the trace and the completion
  leaves an indeterminate request; the outcome is not reconstructed.
- **The liveness check is local.** A writer in another container or on another host would not
  be seen, and its claim would be wrongly considered dead. That is outside the supported
  topology (one writer process per database file) and is stated rather than hidden.
- **The recovery does not undo anything.** The side effects that already happened stay
  happened; a regulatory update is not rolled back, and an observation is not deleted.
