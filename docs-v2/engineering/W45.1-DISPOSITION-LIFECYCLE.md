# W45.1 — THE DISPOSITION LIFECYCLE

**Status:** implemented. **Scope:** the durable disposition of an observation, the adjudication
history behind it, and the two identities — the canonical case and the observation occurrence.
**Prepared:** 2026-11-04.

---

## 1. The defect, reproduced

The W45.0 store wrote a disposition with `INSERT OR REPLACE INTO observation_disposition(...)`,
and the micro-world derives a case id from the conditions and the observed outcome. The same
case id therefore occurs again in a later episode, and the sequence was:

1. a case is recorded with the disposition `UNRESOLVED`;
2. a review adjudicates it `ACCEPTED`;
3. a later cycle observes the same condition and outcome again;
4. `recordObservationAtomically` writes the disposition again;
5. **the adjudication is gone.**

The observation and its evidence survived; the DECISION about whether they may constrain the
model did not.

**The defect was reproduced against the pre-fix code**, not merely described. The
`KnowledgeStore` of the previous commit was extracted, compiled separately and put first on the
classpath; the same program was then run against both builds:

| the build | after the review | after the observation was repeated |
|---|---|---|
| the pre-fix build (schema v17) | `{case-lamp-on=ACCEPTED}` | `{case-lamp-on=ELIGIBLE}` — **the adjudication was reset** |
| this build (schema v18) | `{case-lamp-on=ACCEPTED}` | `{case-lamp-on=ACCEPTED}` — **the adjudication survived** |

## 2. Two identities, three records

The directive's requirement — *a canonical case identity must not be confused with an
individual observation occurrence* — is met by separating three things that W45.0 conflated
in one row.

| the record | what it is | the table |
|---|---|---|
| the **canonical case** | the FACT: "the lamp was on under power=1,switch=1". Its id is derived from the conditions and the outcome, so the same fact has the same id in every episode. | `epistemic_case` |
| the **observation occurrence** | one ACT of observing that fact, tied to the episode and the signal that produced it. Two independent observations of the same fact are two occurrences and two sources of evidence. | `observation_occurrence` (new) |
| the **current disposition** | what may be believed because of the case RIGHT NOW. | `observation_disposition` |
| the **adjudication history** | every decision that was ever made about the case, and why. | `observation_adjudication` (new, append-only) |

### 2.1 The two new tables

```sql
CREATE TABLE IF NOT EXISTS observation_occurrence (
    id TEXT PRIMARY KEY, workspace_id TEXT NOT NULL, case_id TEXT NOT NULL,
    episode_id TEXT, signal_id TEXT, source_id TEXT, evidence_id TEXT,
    observed_at TEXT NOT NULL, disposition TEXT NOT NULL, reason TEXT);

CREATE TABLE IF NOT EXISTS observation_adjudication (
    decision_id TEXT PRIMARY KEY, workspace_id TEXT NOT NULL, case_id TEXT NOT NULL,
    previous_disposition TEXT, disposition TEXT NOT NULL, reason TEXT,
    contradicted_prediction_id TEXT, resolved_by TEXT, resolved_at TEXT,
    model_revision_id TEXT, recorded_at TEXT NOT NULL, request_id TEXT);
```

Four indexes: `idx_occurrence_workspace`, `idx_occurrence_case`,
`idx_adjudication_workspace`, `idx_adjudication_case`.

**The disposition table is now a PROJECTION of the history**, not the only surviving record of
how the system got there. `KnowledgeStore.rebuildDispositionProjection(workspaceId)`
recomputes the projection from the history and reports whether the stored projection agreed
with it; when it did not, it repairs the projection and says so.

## 3. The transitions

The rule lives in code, in `ObservationDisposition.canTransitionTo(next)` and
`ObservationDisposition.canBeInitialDisposition(candidate)`. It is enforced in
`KnowledgeStore.adjudicateObservation` and on the first write of a case.

| from | to | legal? | why |
|---|---|---|---|
| (none) | `ELIGIBLE` | **yes** | the initial state of an ordinary observation |
| (none) | `UNRESOLVED` | **yes** | a contradiction whose cause is unknown |
| (none) | `ACCEPTED` / `REJECTED` | **no** on the occurrence path | *the birth of a case is not a review.* A review may be the first decision about a case — the store allows it, because a review of a case the store has not seen is a legitimate act of adjudication — but the observation path may not invent a decision |
| `ELIGIBLE` | `UNRESOLVED` | **yes** | a later observation contradicts a settled belief |
| `ELIGIBLE` | `ACCEPTED` / `REJECTED` | **yes** | a review decides |
| `UNRESOLVED` | `ACCEPTED` / `REJECTED` | **yes** | a review decides |
| `UNRESOLVED` | `ELIGIBLE` | **no** | an unresolved observation must not become model data without a review |
| `ACCEPTED` | `REJECTED` | **yes** | a review changes its mind — and the earlier acceptance survives in the history |
| `ACCEPTED` | `UNRESOLVED` | **yes** | a review re-opens it — and the earlier acceptance survives in the history |
| `REJECTED` | `ELIGIBLE` | **NO — never** | a rejected observation must not become eligible merely because it was observed again |
| `REJECTED` | `UNRESOLVED` | **yes** | a review re-opens it; it becomes pending again, and the transition is recorded |
| `REJECTED` | `ACCEPTED` | **yes** | a review overturns the rejection, and the rejection survives in the history |
| any | any **without a review** | **no** | re-observing never adjudicates |

A transition that is not legal raises `ObservationConflictException` with the kind `TRANSITION`
— never a silent overwrite.

## 4. The rules of a repeated observation

The production path — `recordObservationAtomically` → `recordObservationOccurrence` — obeys
three rules:

| the state of the case | what the repeated observation does |
|---|---|
| **no disposition** | the initial disposition is written (only `ELIGIBLE` or `UNRESOLVED`), a history row `adj-initial-<caseId>` is appended, and the occurrence is recorded |
| **`ELIGIBLE` or `UNRESOLVED`** | **the state does not change.** An occurrence row is added, and the reason for the repeated observation is kept there. The projection's `reason` and `recorded_at` are deliberately NOT refreshed: the projection must remain a pure function of the history, or the required rebuild would not be exact |
| **`ACCEPTED` or `REJECTED`** | **nothing is touched.** Not the state, not the projection, not the history. The occurrence records that the fact was observed again |

**A review never adjudicates by accident.** The only path that changes a disposition is
`KnowledgeStore.adjudicateObservation(...)`, and it is the only path that appends a decision.

---

## 5. The rules of a review

| the situation | what happens |
|---|---|
| the same `decisionId` with the **same** content | an **idempotent no-op**: no second history row, no change |
| the same `decisionId` with **different** content | `ObservationConflictException` (kind `DECISION`) — the first decision stands and is never overwritten |
| a legal transition | a history row **and** the projection update, in **one transaction** |
| an illegal transition | `ObservationConflictException` (kind `TRANSITION`) |
| two reviews at the same time | the decision is written FIRST (taking the write lock before the state is read), the state is re-read under the lock and compared; a mismatch is a conflict |

The history row carries everything the directive asks for: the case, the previous disposition,
the new disposition, the reason, the actor, the instant, the contradicted prediction, the
resulting model revision, the stable decision id and the originating request id.

## 6. The review queue and the terminal rejection

`ObservationDisposition.isHeld()` answers a MODEL question — "may this observation constrain
the active model?" — and it is true for `UNRESOLVED` and `REJECTED` alike. That is the right
answer for the question, and it is the only use of the method in the repository.

The workflow question is different: "is this waiting for a review?" That is
`awaitingAdjudication()`, which is true **only** for `UNRESOLVED`. A terminal `REJECTED` is
not pending review, and the new `KnowledgeStore.casesAwaitingAdjudication(workspaceId)`
asks exactly that — so a rejected observation never enters a review queue as though it were
waiting for one.

| the predicate | the question |
|---|---|
| `constrainsModel()` | may this observation constrain the active model? (`ELIGIBLE`, `ACCEPTED`) |
| `isHeld()` | may this observation NOT constrain the active model? (`UNRESOLVED`, `REJECTED`) |
| `awaitingAdjudication()` | is this observation still waiting for a review? (`UNRESOLVED` only) |
| `terminallyExcluded()` | has this observation been rejected, and does the rejection stand? (`REJECTED` only) |

## 7. The session honours a reviewed decision

**W45.1.** `MicroWorldSession.dispositionOf(observation)` used to collapse everything into
"eligible" or "held". It now returns the observation's OWN disposition when that disposition is
`ACCEPTED` or `REJECTED` — a decision a review made — and falls back to the session's own
classification otherwise.

Without this, a restored observation that a review had accepted would be written back as
`ELIGIBLE` in the next occurrence, and the occurrence would contradict the projection: the
session would be erasing the adjudication in the very place the W45.1 history is supposed to
preserve it.

The model's behaviour is unchanged — an accepted observation and an eligible one both
constrain the model — but the record is now truthful.

---

## 8. What was NOT changed

- **The case id derivation is unchanged.** A case is still identified by the conditions and the
  outcome. That is what makes the canonical fact a canonical fact.
- **The knowledge store is still the only epistemic store.** The occurrences and the
  adjudications live beside the cases, in the same database, in the same transaction.
- **Nothing is deleted.** The adjudication path adds records; it never removes them. The
  rebuild repairs a projection but does not delete a row.
- **The owner decision about the destructive workspace reload is untouched.** The endpoint can
  still delete the history — which is why it remains the highest-severity open item.

## 9. The known limits

| the limit | why |
|---|---|
| `observation_occurrence` grows without bound | one row per act of observation. It is a history, and no retention policy was asked for or written. |
| the projection's `reason` and `recorded_at` are not refreshed by a repeated observation | deliberate: the projection must be a pure function of the history, or the rebuild could not be exact. The reason for the repeated observation is kept in the occurrence. |
| a review of a case the store has never seen is allowed | a review is a legitimate first decision about a fact; the occurrence path may not invent one, but a reviewer may. |
| the backfill of a v16 database cannot see the cognitive tables from the knowledge store | the knowledge store reads the `cognitive_error` and `cognitive_prediction` rows when they are in the SAME database file, and degrades to the conservative relation-only rule when they are not. See `W45.1-LEGACY-DISPOSITION-REPORT.md`. |
| two writers in one process are serialised by the store's monitor; two writers in two processes rely on SQLite's write lock | there is no retry for `SQLITE_BUSY`; the error surfaces as an `IllegalStateException`. The supported topology is one writer process per database file. |
