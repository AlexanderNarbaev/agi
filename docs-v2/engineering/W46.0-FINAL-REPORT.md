## B. What was discovered

### B.1 The architecture

- **Two serving chains, and chain A is ONE process with THREE serving paths** — the workbench
  (57 routes), the cognitive kernel (11), and the chat surface (6), plus 136 routes over 36
  more resources: **210 routes** on the Quarkus app, **28** on the brain runtime's JDK
  `HttpServer`.
- **Six cycles, not five.** The sixth — `io.matrix.reasoning.BrainLoopService` — is the only
  cycle behind the chat surface. The W44 map was not wrong when it was written.
- **The two `BrainLoopService` classes are different things**: the `consciousness` one is a
  framework-free **measurement** loop with 25 callers, none of them in a serving path; the
  `reasoning` one is the **served** nine-stage loop with exactly one caller.
- **The isolation holds.** Over **2909 classes and 76 858 constant-pool edges**, chain B
  reaches **0** classes of `io.matrix.cognitive.**`, **0** of the epistemic store, **0** of the
  classes that name the epistemic database, and **0** of the chain A surface. The 179 shared
  classes are a library (`bir`, `neuron`, `tsetlin`, `compression`), not a path to the store.
- **No module-level cycle** — verified by Tarjan over the 8 dependency edges. But **two
  class-level cycles** inside `matrix-core` (one of them inside the **FROZEN**
  `ethics/frozen/` zone) and a **42-package SCC**.

### B.2 The persistence

**One SQLite file** (`data/knowledge/workbench.sqlite`), **two classes over it** — the
knowledge store (v19, 27 tables) and the cognitive store (v4, 12 tables) — with **two
connections**, so the kernel's write **crosses two connections and is not one transaction**.
The third SQLite file, `data/mind/mind.sqlite`, belongs to **chain B**. **No second store
duplicates the canonical knowledge store, and none is needed.**

### B.3 The GPU — the claim was false, and the fix is one environment variable

The hardware is healthy and the CUDA provider is compiled in, but `addCUDA` **fails** and the
exception is swallowed: the library path is set as the JVM system property `java.library.path`,
while a native `dlopen` consults the **`LD_LIBRARY_PATH` environment variable**. The loader
therefore finds the distro's `libcudart.so.12` (12.4), which lacks `cudaLibraryGetKernel`.

**With one environment variable exported, the same model on the same machine runs 12.6×
faster: 191.367 ms → 15.190 ms per forward.** And the diagnostic that reports the active
provider is a **hardcoded `CPUExecutionProvider` string** — it cannot report the truth.

- **Five non-existent paths in `AGENTS.md`** and a **`WAL.md` that was renamed** in 2026 to

- **Two capability registries with two different vocabularies**, and both predate W45.0.

- **`SESSION.md` and `state.yaml` are dead** — September's body and an August `status: init`.
- **`constitution.md` is an unfilled template** duplicating `CONSTITUTION.md`; on a

is a hardcoded string that says "CPU" either way.
