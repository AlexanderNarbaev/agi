## 2. The decisions, and what was implemented

The four questions were put to the owner as a questionnaire with every option the evidence
supported. **The first answer chose the heavier options**; the owner **re-answered** and took
the recommended option on all four. The re-answer is the decision; the first answer is
recorded in `W45.2-OWNER-DECISIONS.md` §0, because the difference between the two is the
difference between a refactor and a boundary.

### Decision 1 — the canonical entry point per application

**The five cycles are kept. Each serving application names its canonical entry point, and the
naming is a CLASS, not a sentence** — so a test can check it.

| the application | the canonical entry point | the routes | the cycles it runs |
|---|---|---|---|
| the epistemic and workbench application | `io.matrix.knowledge.LearningWorkbenchResource` | `/v1/workbench/**` | `io.matrix.cognitive.CognitiveKernel` |
| | `io.matrix.api.OpenAIChatResource` | `/v1/chat/completions` | `io.matrix.reasoning.BrainLoopService` |
| the brain runtime | `io.matrix.api.MinimalHttpServer` | `POST /v1/analyze` | `io.matrix.brain.runtime.TrueMindCycle` |

The implementation: `io.matrix.api.CanonicalEntryPoint`, checked by
`CanonicalEntryPointTest` (7 tests) and `CanonicalEntryPointChainBTest` (3 tests, on the
gateway's own side). The ADR is reconciled by a **superseding** document,
`ADR-W45.2-01-canonical-entry-point.md`; the two historical ADRs carry a one-line status
annotation pointing at it, and **neither was rewritten**.

**What was found while implementing it:** the epistemic application runs **two** loops, not
one — the W44 learning kernel and the nine-stage loop behind the chat resource. The W44
cycle map listed five cycles and did not mention the sixth (`io.matrix.reasoning.BrainLoopService`,
which `OpenAIChatResource` drives). Naming only the kernel would have repeated the original
error in the other direction, so the declaration names both.

### Decision 2 — the two chains stay isolated and fail closed

**No bridge, no implicit write path, no new network surface. The isolation is PROVED.**

The gate resolves the compiled call edges from the constant pool (`javap -p -c`) — the same
method the archaeology used — over a universe of **2908 classes and 76 815 edges**, and
asserts that **no class reachable from chain B's entry points reaches the cognitive store, the
epistemic store, or the chain A surface**.

| the entry point | the classes it reaches |
|---|---|
| `io.matrix.api.MinimalHttpServer` | 331 |
| `io.matrix.api.brain.ProductionBrainClient` | 193 |
| `io.matrix.brain.runtime.TrueMindCycle` | 182 |
| `io.matrix.api.llm_quarantine.BrainProduction` | 94 |
| **the union** | **356** |

**At runtime**, the real chain B server answers `404` for `/v1/cognitive/summary`,
`/v1/workbench/workspaces` and `POST /v1/cognitive/observe`, serves its own `/v1/status`
with `200`, and **leaves the owner's epistemic database byte-identical** (the SHA-256 is the
same before and after).

**The gate can go red, and has been seen going red:** the negative control breaks the
isolation in a private copy of the compiled classes and runs the real gate against it — a
chain B class that calls `KnowledgeStore` produces `FAIL 78 class(es) of the epistemic store
are reachable from chain B`, and a chain B class that declares `@Path("/v1/cognitive")`
produces `FAIL 1 route(s) of chain B belong to the chain A surface`.

**The contract for a future bridge** is written down as ten requirements (BRIDGE-1…10) and
the gate asserts that the contract exists and names every one of them.

**The full boundary and its honest limits:** `W45.2-CHAIN-BOUNDARY.md`.

### Decision 3 — the destructive reload fails closed and leaves a snapshot

**The load refuses to replace a non-empty workspace unless the caller says `replace=true`,
and it takes a recoverable snapshot before the replacement.**

| the call | what happens |
|---|---|
| an **empty** workspace, no flag | the load proceeds — a first load is not a replacement |
| a **non-empty** workspace, no flag | **HTTP 409**, and **nothing is deleted**: the refusal happens before the transaction that erases anything |
| a **non-empty** workspace, `replace=true` | a snapshot is taken **in the same transaction** as the replacement, and the response carries its id |

The snapshot is a durable row (`workspace_snapshot`, the knowledge schema **v18 → v19**)
holding the exported workspace, and it restores through
`POST /v1/workbench/workspaces/{id}/restore/{snapshotId}`. **It preserves everything the
replacement erases** — including the `contradiction` and `revision` rows, which the
pre-W45.1 snapshot did not carry at all.

**What it does not preserve, stated plainly:** the workspace row's `created_at` and `version`
(a restored workspace is a new instance of the same content), and everything the replacement
**does not** erase — the cases, the dispositions, the W45.1 adjudication history, the
assessment items and the whole cognitive store.

### Decision 4 — one writer per database, enforced and documented

**A second PROCESS opening the same database file is REFUSED at start-up.** The guard is a
lock file next to the database holding the owner's pid, the start instant and the instance
token, plus the operating system's lock on that file.

**The lock belongs to the PROCESS, not to a store instance** — an implementation detail that
the first draft got wrong and that the implementation corrected: the cognitive store and the
epistemic store open the **same** file, so a second store of the same process must **join**
the lock it already holds, and what is refused is a second **process**.

**A lock left behind by a killed process does not block the next one** — the same primitives
`OwnershipToken` carries tell a dead owner from a live one, and the operating system
releases its lock when the process dies whatever it was doing.

## 4. The unresolved items

| what | why |
|---|---|
| the **evidence of an observation does not survive a workspace load** | the erasure set of a workspace replacement erases the `evidence` table but not `epistemic_case`, `observation_disposition`, `observation_occurrence` or `observation_adjudication` — the set predates the observation tables. A load therefore leaves a case and a disposition whose evidence rows are gone. Taking the observation tables out of the erasure set is the smaller fix, and it is **not** made here: it changes what a workspace replacement means, which is the owner's call. |
| the **legacy in-process door** `KnowledgeWorkbench.loadBundledPackage(String)` | it still replaces without the flag, because `KnowledgeWorkbenchTest.reloadingIsIdempotent` loads the package three times into one workspace and the owner's decision requires a refusal on the second. **It is no longer a silent erase** — it leaves a recoverable snapshot. The HTTP surface, which is the door the owner named, fails closed ✓. Declaring the one-argument method deprecated and moving its callers is the next step. |
| the **snapshot payload is not bounded** | it is the JSON of the whole workspace; a bigger workspace gives a bigger payload. There is no compression and no limit. |
| the **snapshot table grows without bound** | there is no retention policy. The owner asked for recoverability, not for storage. |
| **the guard is per host** | the operating system's lock protects the file against another writer on the same host, and against another host only when the shared filesystem implements cross-host locks. A network volume whose filesystem does not coordinate locks degrades the guard to a per-host guard. The deployment must keep one writer per file. |
| a **container with its own PID namespace** | its pid is invisible to the host process, so the record alone would judge it dead; the operating system's lock on the shared inode is what protects that case. |
| a **crashed store instance inside a live JVM** | keeps the lock for the life of that JVM. Deliberate: a leaked instance may still hold an open connection. |
| the **destructive workspace reload** | **the decision is implemented** — the fail-closed contract and the snapshot are in place. What remains is the owner's call on the legacy in-process door above. |
| the **three architecture decisions** | the other two are implemented; the canonical conductor is **implemented and documented**, and the chain boundary is **implemented and proved**. |
