## 1. The formats

The mission's §5.1 names TXT, Markdown, HTML, PDF, EPUB and knowledge
packages, and it says: *"Use appropriate established libraries instead of
developing PDF parsing, EPUB decoding, or document extraction from
scratch."*

**What the code uses:**

| the format | the library | what is extracted |
|---|---|---|
| TXT, Markdown | the standard library | the text, segmented by the blank lines |
| HTML | **jsoup 1.17.2** | the visible text; the markup and the scripts are not |
| PDF | **Apache PDFBox 3.0.3** | the text layer — a PDF without one yields nothing, and the import says so |
| EPUB | the JDK's ZIP reader + **jsoup** for the XHTML inside | the chapters in order |
| JSON | Jackson | the knowledge package, as the workspace's own format |

Nothing here parses PDF or decodes EPUB from scratch. PDFBox was already
pinned in `matrix-audit` and was added to `matrix-core`; jsoup was already
in the stack.

## 2. The pipeline

The mission's §5.3 names the stages:
`SOURCE → EXTRACTION → NORMALIZATION → SEGMENTATION → CONCEPT DISCOVERY →
CLAIM EXTRACTION → EVIDENCE LINKING → VALIDATION → KNOWLEDGE INTEGRATION`.

**What the implementation covers, and what it does not:**

| the stage | the state |
|---|---|
| SOURCE | ✅ `SourceRecord`: the content hash, the format, the language, the author, the publication date, the extraction quality |
| EXTRACTION | ✅ `DocumentExtractor` per format, `DocumentExtractorRegistry` over them |
| NORMALIZATION | ✅ the text layer's folding and the language detection |
| SEGMENTATION | ✅ the segments carry their own text and their position |
| CONCEPT DISCOVERY | ✅ the subjects of the extracted claims become the concepts |
| CLAIM EXTRACTION | ✅ `ClaimExtractor` — the declarative sentences with a subject and a verb |
| EVIDENCE LINKING | ✅ each claim carries its source and the excerpt it came from |
| **VALIDATION** | ✅ since W42.7 — `ClaimValidator` groups the claims by their proposition, measures the group by the **distinct content hashes** of the sources behind it, promotes a group with two independent sources and supersedes the duplicates |
| KNOWLEDGE INTEGRATION | ✅ `DocumentImporter` → `KnowledgeStore.applyChanges` |

**The validation stage was the honest gap of this wave, and W42.7 closed
it.** The promotion stages (`RAW → EXTRACTED → CANDIDATE → SUPPORTED →
VERIFIED → DISPUTED → SUPERSEDED`) and the policy that guards the
transitions existed and were not wired to anything. `ClaimValidator` now
runs them: a document that states what the package states promotes the
package's claim from `SUPPORTED` to `VERIFIED`, and the imported duplicate
is superseded by it. **The mission's `INVALIDATED` stage is still not
implemented** — the seven stages that exist are the seven that the code
names. An imported claim therefore stays
`CANDIDATE`, and its support score is what it is — 0.0 for the imported
claims — which is the correct thing for an unvalidated claim.

## 3. The promotion policy

The mission's §5.5 says: *"Ten documents copying the same source do not
constitute ten independent confirmations."*

`PromotionPolicy.independentSources(List<String> sourceHashes)` counts the
**distinct content hashes**, not the documents. Ten copies of the same
source contribute one independent confirmation. A promotion that claims
more independent support than it has is refused, and
`refusalReason(...)` says why.

## 4. The corpus record

`SourceRecord` is the corpus manager's entry for a source: its id, the
content hash, the format, the declared and detected language, the author,
the publication date, the extraction quality, the import time, and the
workspace it was imported into. The store's `source` table holds them, and
`GET /workspaces/{id}/sources` returns them.

**CORRECTION (W42.7).** This report said the corpus manager "does not
deduplicate imports by content hash (the same document imported twice
creates two source records)". **That was wrong, and it was checked rather
than assumed:** the same document imported twice is ONE source — the
source id is derived from the content hash, the claims and the evidence
are not duplicated, and the import is idempotent. The dedup was already
there; the *registry* was missing.

Since W42.7 the registry exists: `GET /workspaces/{id}/corpus` returns
every source with its language, its format, its content hash, how many
claims it supports, and how many **independent confirmations** the
workspace holds — counted by the distinct content hashes of the sources
behind a claim, so ten copies of one source are one confirmation.

**What the corpus manager still does NOT do:** it does not track the
versions of a source, and it does not rank the sources. The versions are
named in `RECON-W42-BACKLOG.md`; the ranking is deliberately absent, because
a ranking nobody could check would not be information.

## 5. The import

```
POST /v1/workbench/workspaces/{id}/documents   (multipart)
→ { workspace, sourceId, filename, format, contentHash, language, author,
    publicationDate, extractionQuality, segments, claimsProposed, conceptsCreated,
    representationsCreated, skipped }
```

The importer is **atomic**: `KnowledgeStore.applyChanges` turns the
autocommit off, writes the sources, the claims, the evidence, the
representations and the revision, commits, and **rolls back on any
failure** — so a failed import leaves nothing half-written. The store's own `applyChanges` enforces the referential
integrity — a claim that names an unknown concept is refused, and a
representation that refines an unknown one is refused.

**A note on the `skipped` list:** it names what the importer did not take —
a segment that carried no declarative sentence, a sentence with no subject.
A document that yields nothing says so, and the import still records the
source.

## 6. What W42.2 did NOT do

1. **The validation stage was closed in W42.7** — but the confidence is
   still authored, not computed: the promotion raises the status and the
   evidence, and the system's support score still reflects the authored
   confidence.
2. **The corpus registry does not track the versions of a source.** The
   deduplication by content hash was verified in W42.7 — this report had
   claimed it was missing, and it was not.
3. **The imported concepts had no authored representation** until W42.4 —
   the `RepresentationComposer` wrote them.
4. **A PDF without a text layer yields nothing.** This is a property of
   PDFs, not a defect of the extractor, and the import says so rather than
   pretending to have read the page.
5. **The imported claims are unvalidated**, so the answer that uses them
   carries a support score of 0.0 — honest, and the reason the W42.4
   representation is written from the document's own sentences rather than
   from the claims' authority.
6. **The full repository test suite was not re-run**; the targeted packages
   were.
