## 1. The verdict

**REPRODUCED as a claim. NOT REPRODUCED as the digit 12.6×.** Both halves are stated here
because both are true, and neither replaces the other.

The historical claim is *"the CUDA execution provider makes MATRIX's transformer forward pass
about 12.6× faster on this machine"* — 191.367 ms on the CPU against 15.190 ms on the CUDA
(`docs-v2/engineering/W46-HARDWARE-AND-RESOURCE-REPORT.md` §6.1, item 5, and
`docs-v2/engineering/W46-FINAL-REPORT.md:76`).

This wave measured that quantity again, three times, under a committed protocol, and got:

| the run | the CPU median | the CUDA median | the ratio | the deviation from 12.6× |
|---|---|---|---|---|
| the record run | 160.995 ms | 13.345 ms | **12.06×** | −4.3 % |
| the first repetition | 144.900 ms | 12.404 ms | **11.68×** | −7.3 % |
| the second repetition | 140.053 ms | 12.212 ms | **11.47×** | −9.0 % |
| **the historical claim** | **191.367 ms** | **15.190 ms** | **12.6×** | — |

**What reproduces — the claim.** On the same machine, the same model
(`models/onnx/qwen05b/model.onnx`), the same sequence length (32), the same warm-up and
iteration protocol and the same JVM, the CUDA execution provider makes MATRIX's transformer
forward pass **≈12× faster**: 12.06×, 11.68× and 11.47× over three independent runs, all
within 5 % of 12.0. The claim is now backed by a committed script, a committed harness and
preserved raw samples.

**What does not reproduce — the digit 12.6×.** All three re-measurements land **below** it,
by 4.3 %, 7.3 % and 9.0 %. The historical figure was a single ad-hoc probe's number, the
probe was never preserved, and the two absolute figures it quoted are 12–27 % higher than the
same machine measures today: the historical CPU 191.367 ms against today's 140–161 ms, and
the historical CUDA 15.190 ms against today's 12.2–13.3 ms. The shift is common-mode, which
is why the ratio survives at ≈12× while the digit does not.

**The 12.6× stays a HISTORICAL figure.** It is not replaced by this report; it is *bounded*
by it. The W46 report remains the record of what was measured on 2026-11-04, and this report
is the record of what is measured today, by a script anyone can re-run.

**The qualification:** the ≈12× holds for the forward pass **as MATRIX calls it**. The bare
compute, without the logits readback that MATRIX's own call performs, is **≈20–24×** faster.
Those are two different measurements of two different costs, and §5 keeps them apart.
Whichever definition the W46 probe used was never recorded; the fact that MATRIX's own call
reproduces ≈12× while the raw call does not is evidence — not proof — that the W46 probe
measured the MATRIX path. *[inference, ~85 % confidence]*

**What is NOT reproduced, and was never claimed to be:** the GPU does **not** accelerate a
point call. It makes one **four times slower** (§5, third row).

`addCUDA()` throws. With the variable it finds the virtualenv's CUDA-12 runtime, which does.
This is the same mechanism the W46 report recorded, and it still holds.

## 3. The method

### 3.1 The three configurations

The benchmark runs the **same** harness three times. The only thing that differs between the
two cases that are compared is the execution provider the session is configured with.

| the configuration | the provider | `LD_LIBRARY_PATH` | what it is |
|---|---|---|---|
| `cpu-default` | CPU | **not exported** | MATRIX's configuration as it ships today |
| `cpu` | CPU | exported | the CPU baseline, in the CUDA run's environment |
| `cuda` | CUDA | exported | the GPU case |

**The `cpu` and the `cuda` runs are the comparison.** `LD_LIBRARY_PATH` is exported for
**both**, so the CUDA provider is loadable in both and the *provider* is the only variable. The
`cpu-default` run is reported separately, because it is the configuration MATRIX actually runs
in and it is the one the W46 report compared against.

### 3.2 The identical conditions

| the condition | the value, in every configuration |
|---|---|
| the model | `models/onnx/qwen05b/model.onnx` + `models/onnx/qwen05b/model.onnx_data` |
| the sequence length | 32 |
| the warm-up iterations | 5 (untimed) |
| the measured iterations | 20 (timed) |
| the JVM | `<repo>/../jdk25/bin/java`, openjdk 25.0.4.1 |
| the JVM flags | `--enable-native-access=ALL-UNNAMED -Xms1g -Xmx4g -XX:+UseG1GC` |
| the classpath | the compiled `matrix-core` classes, the ONNX Runtime **GPU** jar first, the ONNX Runtime CPU jar, slf4j-api |
| the machine | the same, minutes apart, one GPU, no other GPU work |
| the prompt and the token budget | `The GPU benchmark measures the ONNX execution path.` + 16 generated tokens |

**The token budget is fixed and the EOS stop is disabled** (`setEosToken(-1)`), so the
end-to-end path performs the same number of forward passes in the CPU run and in the CUDA run.
A CPU run and a CUDA run may pick different tokens from the same logits; fixing the step
count removes that difference from the comparison.

### 3.3 The CUDA execution proof — and the hard failure

**The benchmark fails if the CUDA execution provider did not execute.** The proof is the
session's **execution profile**, which names the provider that ran every node. It is the only
ground truth in the ONNX Runtime Java binding; the session's own configuration says only what
it was *asked* to do, and the adapter's `activeProviders` field is a hardcoded string
(`matrix-core/src/main/java/io/matrix/api/OnnxRuntimeAdapter.java:118-123`).

The proof is taken from a **separate, profiled session**, so the timed sessions carry no
profiling overhead and the CPU and CUDA timings stay comparable.

The observed split, from the preserved profiles:

| the configuration | the execution profile names |
|---|---|
| `cpu-default` | `CPUExecutionProvider` × 2600 — and nothing else |
| `cpu` | `CPUExecutionProvider` × 2600 — and nothing else |
| `cuda` | **`CUDAExecutionProvider` × 1431** and `CPUExecutionProvider` × 1170 |

Two facts follow, and both matter:

1. **The CUDA provider really executed.** The profile names it for 1431 nodes.
2. **It did not take the whole graph.** 1170 of the 2600 nodes still ran on the CPU in the
   CUDA session. ONNX Runtime says so itself:
   *"1 Memcpy nodes are added to the graph main_graph for CUDAExecutionProvider. It might have
   negative impact on performance"* and *"Some nodes were not assigned to the preferred
   execution providers … e.g. ORT explicitly assigns shape related ops to CPU to improve
   perf."* The GPU figure below is therefore **the figure of a partially-offloaded graph**, not
   of a wholly offloaded one.

### 3.4 The three costs, kept apart

They are different costs and they are never averaged into one number.

| the measurement | what it is |
|---|---|
| the transformer forward pass (the raw `session.run`) | one forward of the exported graph at sequence length 32, measured with `OrtSession.run` and nothing else — **the cost of the compute** |
| the transformer forward pass (MATRIX's own call) | the same forward measured through `OnnxRuntimeAdapter.greedyNextToken`, which additionally reads the whole logits tensor back from the device and takes the argmax of its last position — **the cost of the compute as the serving path pays it** |
| the ONNX point call | one forward of the teacher FFN graph (`models/teacher/teacher_ffn16.onnx`, `x[1,16] → y[1,1]`) with a batch of one — **the smallest unit of GPU work** |
| the BIR point call | one evaluation of MATRIX's own boolean runtime, `BooleanRuntime.evaluate` — **the CPU counterpart of the point call**; it is pure Java and has **no GPU implementation** |
| the end-to-end path | tokenise → generate autoregressively through `QwenOnnxBridge` → detokenise — **the serving path** |

## 5. The median and the dispersion, per measurement kind

The record run. The **median** is the reported central value — the series is a set of timed
iterations, not a distribution, and one slow iteration must not define the result. The **p95**
is the nearest-rank percentile, so it is always an observed sample and never an interpolation.
The **standard deviation** is the sample one (the n−1 denominator).

| the measurement | the unit | the CPU median | the CPU min / p95 / max | the CPU sd | the CUDA median | the CUDA min / p95 / max | the CUDA sd | the CPU / CUDA |
|---|---|---|---|---|---|---|---|---|

| the transformer forward pass (MATRIX's own call) | ms | 160.995 | 132.674 / 183.403 / 191.229 | 14.490 | 13.345 | 10.389 / 14.753 / 20.795 | 2.127 | **12.06×** |
| the ONNX point call (the teacher FFN, batch 1) | ms | 0.008 | 0.008 / 0.019 / 0.224 | 0.048 | 0.034 | 0.032 / 0.049 / 0.280 | 0.055 | **0.24×** |
| the BIR point call (MATRIX's own boolean runtime) | µs | 0.075 | 0.070 / 0.281 / 14.988 | 3.330 | 0.080 | 0.070 / 0.251 / 14.768 | 3.281 | 0.94× |
| the end-to-end path (tokenise, generate, detokenise) | ms | 2220.734 | 2112.603 / 2369.610 / 2377.860 | 79.158 | 174.952 | 162.117 / 183.795 / 189.725 | 5.987 | **12.69×** |

### 5.1 How to read the dispersion

- **The CPU transformer forward is noisy**: a median of 173.8 ms with a standard deviation of
  26.5 ms and a spread from 113.7 ms to 204.2 ms. The CPU path uses all 32 threads and it is
  the one that feels the machine's other load. This is why the report gives a median and a
  dispersion and not a single number — the W46 figure had neither.
- **The BIR point call's standard deviation is dominated by ONE sample.** The median is
  0.075 µs and 19 of the 20 samples are between 0.070 and 0.281 µs; the twentieth is
  14.988 µs, a garbage-collection pause. The standard deviation (3.330 µs) is therefore
  **larger than the median** and must not be read as the cost of an evaluation — the median
  is the honest statistic for that row.
- **The CUDA series are tight**: 0.824 ms of standard deviation on a 7.325 ms median (11 %),
  5.987 ms on 174.952 ms (3.4 %).
- **The point call is the one case where the GPU loses**, and it loses by a factor of four:
  0.008 ms on the CPU against 0.034 ms on the CUDA. The launch overhead dominates the
  arithmetic — exactly the conclusion the historical EXP-009C reached on the torch path
  (`docs-v2/research/reports/EXP-009-report.md`, "GPU per-call одиночный 17.25 µs" against
  "MATRIX BIR CPU ~62 нс/eval"), now reproduced on the ONNX path.
- **The BIR point call is unchanged by the GPU** (0.075 µs against 0.080 µs). It is pure Java
  and it has no GPU implementation; the GPU cannot make it faster, and the run says so
  instead of leaving the reader to assume otherwise.

## 6. The CPU-versus-CUDA comparison

The comparison is the `cpu` row against the `cuda` row: the same environment, the same JVM,
the same classpath, the same model, the same sequence length, the same warm-up and iteration
counts, the same machine — **only the execution provider differs**.

| the kind of measurement | the CPU median | the CUDA median | the ratio | the direction |
|---|---|---|---|---|
| the transformer forward pass (the raw `session.run`) | 173.846 ms | 7.325 ms | **23.73×** | the GPU wins |
| the transformer forward pass (MATRIX's own call) | 160.995 ms | 13.345 ms | **12.06×** | the GPU wins |
| the ONNX point call | 0.008 ms | 0.034 ms | **0.24×** | **the GPU loses** |
| the BIR point call | 0.075 µs | 0.080 µs | 0.94× | **no difference — there is no GPU path** |
| the end-to-end path | 2220.734 ms | 174.952 ms | **12.69×** | the GPU wins |

**The end-to-end ratio is 12.69×, not 23.73×, and that is the honest headline for the serving
path.** The end-to-end cost is not only the forward pass: the prompt is 10 tokens and the path
makes **16 forward passes** over a sequence that grows from 10 to 25 tokens, each one reading
the logits tensor back from the device (6–15 MB per step at those lengths), and the whole
thing is wrapped in tokenisation and detokenisation — and all of that is CPU work the GPU does
not touch. A reader who took the 23.73× as "the speed-up of MATRIX's chat path" would be wrong
by a factor of two.

## 8. The defects this run found

### 8.1 A JVM-level SIGSEGV with a long classpath on this machine

**This is a new finding and it is not specific to this benchmark.** When the ONNX Runtime
native library is loaded by a JVM whose classpath is long and is delivered **on the command
line**, the JVM dies with SIGSEGV (exit code 139) inside
`OrtEnvironment.getEnvironment()` — with no `hs_err` file and no message. The same classpath
delivered through a **JVM argument file** works.

The reproduction, with the classpath the Gradle build resolves for `matrix-core`
(258 entries, 44 987 bytes):

```bash
java --enable-native-access=ALL-UNNAMED -cp "<the matrix-core runtime classpath>" Probe.java
→ Segmentation fault (core dumped), exit 139

java --enable-native-access=ALL-UNNAMED @args.txt Probe.java     # the same classpath, in a file
→ the program runs
```

The threshold behaviour, measured by bisecting the classpath:

| the classpath | the result |
|---|---|
| the ONNX Runtime jars alone | runs |
| 23 repetitions of one jar path (2 967 bytes) | runs |
| 24 repetitions of one jar path (3 096 bytes) | **SIGSEGV** |
| 300 short paths (4 500 bytes) | **SIGSEGV** |
| 30 distinct real jars with short paths | runs |
| one 3 072-byte path | runs |

**The mechanism is not established** and this report does not claim one. What is established:
the crash is reproducible, it is in the native-library load, and **a minimal classpath avoids
it**. `scripts/gpu-benchmark.sh` therefore uses a five-entry explicit classpath (the compiled
`matrix-core` classes, the ONNX Runtime GPU jar first, the ONNX Runtime CPU jar, slf4j-api)
rather than the whole runtime classpath. **This defect belongs to the environment, not to the
benchmark, and it is reported here for the coordinator** — anyone who runs the ONNX path with
a long classpath on this machine can hit it.

### 8.2 The adapter's provider diagnostic is still a hardcoded string

`matrix-core/src/main/java/io/matrix/api/OnnxRuntimeAdapter.java:118-123` assigns
`activeProviders = {"CPUExecutionProvider"}` unconditionally. This wave did not change
production code, so the defect stands — but the benchmark now demonstrates both the fact and
the cure: the **execution profile** names the provider that actually ran the nodes, and the
harness reads it.

### 8.3 The CUDA provider does not take the whole graph

1170 of 2600 nodes still run on the CPU in the CUDA session, and ONNX Runtime adds a Memcpy
node to the graph. Any future claim about "the GPU path" must say *which* graph and *how
much* of it.

**What the script does when the GPU is not usable** — it exits non-zero and says so; it never
reports a CPU number as a GPU number:

| the situation | the exit code | the message |
|---|---|---|

## 10. What this report does NOT claim

- **It does not claim the GPU should be in MATRIX's serving path.** Whether it should is the
  owner's question `Q-W46-07` (`docs-v2/governance/OPEN-QUESTIONS.md`), and it is still open.
  This report answers the measurement half of it; the decision half is not the benchmark's to
  make.
- **It does not claim the GPU is faster everywhere.** The point call is 4× slower, and the BIR
  evaluation has no GPU path at all.
- **It does not claim the whole graph runs on the GPU.** 45 % of the nodes did not.
- **It does not claim the historical 12.6× was wrong.** It claims that it was **not a
  measurement** — an ad-hoc probe with no preserved artefact — and that the quantity it
  describes now has a committed measurement behind it.
- **It does not claim the logits readback (19.5 MB per forward at sequence length 32) is the
  right design.** It is measured, and
  it is the reason the raw compute and MATRIX's own call differ by a factor of two.
