# W45.2 — THE BOUNDARY BETWEEN THE TWO CHAINS

**Status:** the isolation is PROVED, not asserted. The proof is a gate that can go red, and
that has been seen going red on a deliberately broken tree.
**Date:** 2026-11-04.
**Gate:** `scripts/w45-chain-isolation-check.sh` (the census and the verdicts).
**Negative control:** `scripts/w45-chain-isolation-selftest.sh` (the proof that the gate fails
when the isolation is broken).
**Reachability analyser:** `scripts/w45-chain-isolation-reachability.py`.

---

## 1. The two chains

### Chain A — the epistemic and workbench application

`matrix-core` → Quarkus → `/v1/workbench/**` and `/v1/cognitive/**` → the SQLite-backed
knowledge store (`io.matrix.knowledge.KnowledgeStore`, opened by
`io.matrix.knowledge.KnowledgeWorkbench`) and the cognitive store
(`io.matrix.cognitive.CognitiveStore`). The canonical entry point of this application is the
Quarkus workbench and the cognitive kernel.

The epistemic database is **one SQLite file**, named by the system property
`matrix.knowledge.path` (the default is `data/knowledge/workbench.sqlite`). It holds the
claims, the evidence, the cases, the goals, the learning state — the model of the world.

### Chain B — the brain runtime

`matrix-api-gateway` → `io.matrix.api.MinimalHttpServer` (a JDK `HttpServer`, not Quarkus) →
`io.matrix.api.brain.ProductionBrainClient` → `io.matrix.brain.runtime.TrueMindCycle` and the
runtime stages in `matrix-brain-runtime`. A second entry point is
`io.matrix.api.llm_quarantine.BrainProduction`.

**The gateway's JAX-RS facade is NOT the brain runtime.** The resources in
`io.matrix.api.resource` are declared but **not mounted** (the module applies no Quarkus
plugin), and the gateway constructs a **stub** cycle (`io.matrix.api.brain.StubBrainCycle`).
Anything that says "the gateway serves the brain" confuses the two.

The two chains share a **classpath** (`matrix-brain-runtime` and `matrix-api-gateway` both
depend on `matrix-core`), and therefore share the substrate libraries. What they do not
share is a **call**.

---

## 2. The owner's decision (W45.2, decision 2)

> **Keep the two chains isolated and fail closed.**
> No bridge, no implicit write path, no automatic trust, no new network surface. Chain B
> cannot alter claims, confidence, goals or safety policy. The contract for any FUTURE
> bridge is written down: explicit, versioned, authenticated, provenance-carrying, with its
> own safety boundary. The isolation is PROVED, not only asserted.

The owner was asked four times and answered with the isolation (the first answer had chosen
an authenticated write bridge; the owner re-answered and took the isolation).

This document records **what the decision buys, how it is proved, what the proof does not
cover, and what any future bridge must satisfy.**

---

## 3. What the isolation guarantees

1. **Chain B cannot alter the epistemic model.** No class reachable from any chain B entry
   point can reach the cognitive store, the epistemic store's own classes, or any class that
   names the epistemic database.
2. **Chain B cannot open the epistemic database.** The classes of `io.matrix.knowledge.**`
   that chain B reaches cannot reach the persistence stack (`java.sql`, `javax.sql`,
   `org.sqlite`), so they cannot open a SQLite file at all.
3. **Chain B does not serve the chain A surface.** No route of chain B is a route of chain
   A, and at runtime the chain B server answers `404` for the chain A surface.
4. **Chain B cannot serve the chain A surface by accident.** The classes that serve
   `/v1/cognitive/**` and `/v1/workbench/**` are not reachable from chain B.
5. **Nothing new is exposed.** The gate adds no network surface: the chain B server it
   starts binds a free loopback port for the duration of the check and is killed by pid.

---

## 4. How it is proved

### 4.1 The method — reachability over the COMPILED classes

The edges are resolved from the **constant pool** through `javap -p -c`, not from a textual
search. A textual search mistakes a mention for a call: a comment, a log message or an
import says nothing about whether the code can reach a class. Every `invoke*` instruction
names the owner of the callee in the compiler's own constant pool, and every `new`,
`checkcast` and `instanceof` names the class it operates on. The edges are therefore what
the **compiler** saw.

The **universe** of the proof is the union of the compiled classes of every module on chain
B's classpath: `matrix-core` (2621 classes), `matrix-brain-runtime` (208),
`matrix-api-gateway` (67) and `matrix-audit` (12) — 2908 classes, 76 813 resolved edges.
A class of chain B may call a class of `matrix-core` (the modules share a classpath), and
the proof follows that call into `matrix-core`; a proof that stopped at the module boundary
would be worth nothing.

The analyser runs over a **private copy** of the compiled classes, so the proof is made over
one build even when another process builds the repository at the same time.

### 4.3 The rules of the gate

| rule | what it asserts | how it goes red |
|---|---|---|
| **G0** | the contract of §6 exists and names every requirement | the document is missing a requirement label |
| **G1** | chain B reaches no class of `io.matrix.cognitive.**` | a chain B class calls the cognitive store |
| **G2** | chain B reaches no class of the epistemic store's own classes, and no class that names the epistemic database | a chain B class calls `KnowledgeStore`/`KnowledgeWorkbench`/`CognitiveStore`, or names the database path |
| **G3** | no class of `io.matrix.knowledge.**` reachable from chain B can open a database | one of them reaches `java.sql`/`org.sqlite` |
| **G4** | chain B reaches no class that serves the chain A surface | a chain B class calls `CognitiveResource` or `LearningWorkbenchResource` |
| **G5** | no route of chain B is a route of chain A | a chain B class declares `@Path("/v1/cognitive…")` or `/v1/workbench…` |
| **G6** | at runtime: the chain B server answers `404` for the chain A surface, serves its own routes, and leaves the epistemic database of the owner byte-identical | the server answers `200` for a chain A route, or the digest of the owner's database changes |

The store's "own classes" are **derived**, not written down: they are the classes of the
store subsystem (the closure of `KnowledgeStore`, `KnowledgeWorkbench` and `CognitiveStore`)
that live in the two store packages. The shared substrate — the truth tables, the Tsetlin
automaton, the HDC encoding — is **not** part of the store: both chains use it, and its
presence says nothing about the isolation.

### 4.4 The three classes of `io.matrix.knowledge.**` that chain B DOES reach

```
io.matrix.knowledge.SimpleKnowledgeBase
io.matrix.knowledge.SimpleKnowledgeBase$Document
io.matrix.knowledge.SimpleKnowledgeBase$RetrievalResult
```

**This is not the epistemic store.** `SimpleKnowledgeBase` is a read-only RAG index: it
lists the markdown and text files of `data/knowledge/` and answers keyword queries over
them. It holds no connection, it writes nothing, it reaches no persistence stack, and it is
not reachable from the store's own closure. The gate asserts exactly that (G3) and prints
the three classes, so that a reader sees the exception instead of a summary that hides it.

### 4.5 The runtime part

The gate starts the real chain B server (`io.matrix.api.MinimalHttpServer`, from the
`installDist` distribution) with its working directory inside the private temporary
directory, on a free loopback port, and asserts:

* `GET /health/live` → `200` (the server is up);
* `GET /v1/cognitive/summary` → `404`;
* `GET /v1/workbench/workspaces` → `404`;
* `POST /v1/cognitive/observe` → `404`;
* `GET /v1/status` → `200` (a chain B route works: the server is functional, not merely
  alive);
* the SHA-256 of the owner's `data/knowledge/workbench.sqlite` is **identical** before and
  after the run.

The run of 2026-11-04: the digest was
`bb8c05700be48bf122118a37d4736d3bc143beae6368ca38123397a53ad2619b` before and after.

### 4.6 The negative control — the gate CAN go red

`scripts/w45-chain-isolation-selftest.sh` breaks the isolation **on purpose**, in a private
copy of the compiled classes, and runs the real gate against the broken tree:

* **control 1** — a class of chain B that *calls* `io.matrix.knowledge.KnowledgeStore`
  → the gate reports `FAIL 4 class(es) of io.matrix.cognitive.** are reachable from chain B`,
  `FAIL 78 class(es) of the epistemic store are reachable from chain B`,
  `FAIL 1 class(es) of io.matrix.knowledge.** reach the persistence stack`, and exits `1`;
* **control 2** — a class of chain B that declares `@Path("/v1/cognitive")` → the gate reports
  `FAIL 1 route(s) of chain B belong to the chain A surface`, and exits `1`.

Nothing is touched in the repository: the broken classes are compiled into the copy.

## 5. What the proof does NOT guarantee

The honest limits, in the order they matter:

1. **The proof covers the COMPILED CLASSES OF THIS BUILD** — the four modules named in §4.1,
   as they are compiled at the moment the gate runs. A module that chain B starts to
   depend on, and that is not in the gate's universe, is **not covered**: the gate would
   have to be extended before such a module is added.
2. **The proof is static.** It resolves the calls the compiler emitted. It does not cover
   **reflection** (`Class.forName`, a service loader, a script engine), **JNI**, a **native
   image** built from a different class set, or a class loaded by name at runtime. A bridge
   built out of reflection would not appear as an edge.
3. **The runtime part is a probe, not a fuzzing.** It exercises three representative chain A
   routes and one chain B route. It does not enumerate the whole HTTP surface of chain B at
   runtime; the route census covers the surface statically.
4. **The gate proves the CURRENT build.** A change that adds a crossing is caught when the
   gate runs — not before. The gate belongs in the merge path, not in a report that is read
   once.
5. **The annotated routes of chain B are not mounted.** The gate censuses them anyway
   (they are code that exists and could be mounted), but the runtime part sees only the
   routes the compiled server actually serves.
6. **The shared substrate is not a bridge.** `io.matrix.bir`, `io.matrix.neuron`,
   `io.matrix.tsetlin` and `io.matrix.compression` are reachable from both chains. They are
   libraries, not a path to the store: the store's own classes and the database are still
   unreachable from chain B.
7. **The proof says nothing about the brain runtime's own state.** Chain B keeps its own
   files (its own mind database, its own indexes) in its own directories. The isolation is
   about the epistemic model, not about the two processes being unaware of each other.

## 6. The contract a future bridge must satisfy

A bridge is **not forbidden** by the decision; a bridge that is **not** this is forbidden.
Every requirement below is checked by the gate of §4.3 (rule **G0** requires this section to
exist and to name every requirement).

### BRIDGE-1 — EXPLICIT

A bridge is an explicit, named, opt-in component with one owner. There is no implicit write
path: nothing in chain A may write to the epistemic store on behalf of chain B without
passing through the bridge, and nothing in chain B may reach the store by another route. The
gate of §4.3 must know the bridge by name.

### BRIDGE-2 — VERSIONED

The bridge protocol carries a version in every message, and the reader refuses a version it
does not know. A change of the protocol is a new version, never a silent change of the
meaning of an old one.

### BRIDGE-3 — AUTHENTICATED

Every call is authenticated (mutual TLS or a signed token), and the chain A side verifies
it. An unauthenticated call is refused, not served in a degraded mode. The chain B side is
the client and holds no ambient trust: the trust of a call is established per call, not by
the fact that the process happens to run on the same host.

### BRIDGE-4 — PROVENANCE-CARRYING

Every message carries the provenance of what it carries: the source of the observation, the
instant, the identity of the sender, the episode or session it belongs to, and the raw
observation itself. The chain A side records that provenance verbatim and does not
reconstruct it. A message without provenance is refused.

### BRIDGE-5 — SAFETY-BOUNDED

The bridge may **add** an observation, a candidate or an evidence link, and nothing else.
It may **not** alter claims, confidence, goals, safety policy, dispositions or
adjudications. The write surface that changes what the system believes stays inside chain
A, and the bridge's input is treated as what it is: an unverified observation, held in the
disposition the epistemic store gives it.

### BRIDGE-6 — FAIL-CLOSED

Every failure of the bridge — an unknown version, a failed authentication, a missing
provenance, an exhausted quota, a timeout, a malformed message — results in a refusal and
in an audit record. The default is "no". The bridge never degrades into a best-effort write
path, and a bridge that cannot decide does not write.

### BRIDGE-7 — AUDITED

Every call the bridge makes or refuses is written to the append-only audit chain with its
request id, its decision, and the reason for the decision. The refusal is recorded as
carefully as the acceptance: a bridge that silently drops traffic is indistinguishable from
a bridge that never existed.

### BRIDGE-8 — REPLAYABLE

The bridge is idempotent per request id: a repeated delivery of the same request id does
not duplicate the observation, and the effect is recorded once. A caller that retries after
a timeout gets the outcome of the first attempt, not a second observation. The idempotency
is durable, so it survives the death of either process.

### BRIDGE-9 — BOUNDED

The bridge has a budget: a rate, a size, a batch size and a per-day ceiling, and the
budget is enforced before the store is touched. A bridge that can flood the epistemic store
is a bridge that has changed the system it was supposed to observe.

### BRIDGE-10 — GATED

The isolation gate of this document is extended to the bridge before the bridge is merged:
the bridge is the **only** class allowed to reach both chains, it is named in the census the
gate prints, and any other crossing is a failure of the gate. The negative control of §4.6
is re-run against the tree that contains the bridge, so that "the bridge is the only
crossing" is a tested statement rather than a promise.

## 7. How to reproduce

```
export JAVA_HOME=/home/alexandr-narbaev/jdk25
bash scripts/w45-chain-isolation-check.sh        # the gate: exit 0 when the isolation holds
bash scripts/w45-chain-isolation-selftest.sh     # the negative control: exit 0 when the gate goes red
```

The gate builds the four modules and the distribution of the chain B server itself
(`./gradlew :matrix-core:classes :matrix-brain-runtime:classes :matrix-api-gateway:classes
:matrix-audit:classes` and `./gradlew :matrix-api-gateway:installDist`); `W45_SKIP_BUILD=1`
skips the build when the classes are already there. The gate writes only into its own
private temporary directory, kills only the pid it started, and reads the owner's database
without writing it.
