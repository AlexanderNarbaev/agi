# W45.1 — THE LEGACY DISPOSITION REPORT

**Status:** the v16 → v17 semantics, verified against the actual W44 implementation rather than
against a summary, with a synthetic fixture.
**Prepared:** 2026-11-04.

W45.0 shipped a backfill that classified a legacy record from the EVIDENCE RELATION alone, and
recorded one unresolved limitation: "a v16 database cannot distinguish an observation that
contradicted a prediction from an observation a hypothesis explained". This report checks that
statement against the code and finds **both a better answer and an error in the rule W45.0
shipped**.

---

## 1. The W44 rules, taken from the history

The W44 implementation is in the commits `9eb0d4b1`, `471bfdd9` and `81f08478`. The three
facts that matter were read out of `81f08478`.

### 1.1 When W44 held an observation out of the model

`81f08478:matrix-core/src/main/java/io/matrix/cognitive/microworld/MicroWorldSession.java`,
lines 187-191:

```java
HypothesisPrediction prediction = latestPredictionByAssignment.get(observation.assignmentKey());
if (prediction != null && prediction.value() != observation.lamp()) {
    recordPredictionError(prediction, observation);
    return;
}
applied.add(observation);
```

**W44 held an observation whenever it disagreed with ANY prediction** — settled or unsettled.
That is the obsolete rule. Under W45.0's D3 decision a contradiction is a disagreement with a
**BELIEF**, so a W44 observation that was held because it disagreed with an *unsettled*
prediction is, under the current policy, **ordinary learning**.

### 1.2 When W44 wrote `CONTRADICTS` and when `EXEMPLIFIES`

`81f08478:matrix-core/src/main/java/io/matrix/knowledge/KnowledgeWorkbench.java`, lines 759-762:

```java
contradicts ? EvidenceRelation.CONTRADICTS : EvidenceRelation.EXEMPLIFIES
```

and the value of `contradicts` was computed by the kernel,
`81f08478:matrix-core/src/main/java/io/matrix/cognitive/CognitiveKernel.java` (the OBSERVE
phase):

```java
workbench.recordObservation(..., !explained, caseId);
```

**`CONTRADICTS` ⇔ no surviving hypothesis explains the observation.** It does NOT mean "the
observation disagrees with a prediction". The two are different questions, and the relation
answers the first.

### 1.3 The confidence of a prediction, and the error records

The same kernel file:

```java
Prediction prediction = new Prediction("prd-" + episodeId, WORKSPACE_ID, episodeId, ...,
        forecast.unanimous() ? 1.0 : 0.0, false, forecast.supportingCaseIds(), now);
```

```java
boolean confidentlyWrong = probedForecast.unanimous() && probedForecast.value() != observed.lamp();
boolean unexplained = !explained;
if (confidentlyWrong || unexplained) {
    error = new ErrorSignal(..., confidentlyWrong
            ? ErrorSignal.Disposition.UNRESOLVED : ErrorSignal.Disposition.MISSING_CONDITION, ...);
    store.recordError(error);
}
```

**The confidence is 1.0 for a unanimous prediction and 0.0 for an unsettled one — so the two
ARE distinguishable in a v16 database.** The error record is written only when the prediction
was confidently wrong or the observation was unexplained, and its `disposition` says which:
`UNRESOLVED` (confidently wrong) or `MISSING_CONDITION` (no hypothesis explains it). Its
`case_ids` point at the case.

The shape of `cognitive_prediction` in v16 is: id, workspace_id, episode_id, subject,
predicted_value, basis, basis_version, **confidence REAL**, observed_only, case_ids, made_at —
identical in `81f08478` and `eae6003f`.

## 2. The four-way question

What can a v16 database tell apart?

| | what the v16 rows hold | what is missing | the conclusion |
|---|---|---|---|
| **(a)** a disagreement with an **UNSETTLED** tie-break prediction | `evidence.relation = EXEMPLIFIES` (a hypothesis explained it), `cognitive_prediction.confidence = 0.0`, **no** error row | no sign of "held" in the knowledge tables | distinguishable by the relation → **`ELIGIBLE`** |
| **(b)** a disagreement with a **UNANIMOUS** model prediction | `relation = CONTRADICTS`, `cognitive_error.disposition = UNRESOLVED`, `confidence = 1.0` | — | distinguishable by the error record → **`UNRESOLVED`** |
| **(c)** an observation **unexplained by every** surviving hypothesis | `relation = CONTRADICTS`, `cognitive_error.disposition = MISSING_CONDITION`, `confidence = 0.0` (when the model was not unanimous) | the knowledge tables alone cannot tell (b) from (c): both are `CONTRADICTS` | distinguishable **only** by the `cognitive_error` row → **`ELIGIBLE`** |
| **(d)** an ordinary supporting observation | `relation = EXEMPLIFIES`, no error row | — | → **`ELIGIBLE`** |

**Without the cognitive tables** — a knowledge-only database — (b) and (c) merge, and the
conservative answer `UNRESOLVED` is the only honest one.

## 3. The rule W45.0 shipped, and why it was wrong

The W45.0 backfill read the relation alone:

| the relation | the W45.0 backfill |
|---|---|
| `CONTRADICTS` | `UNRESOLVED` |
| `SUPPORTS` / `EXEMPLIFIES` / `QUALIFIES` | `ELIGIBLE` |
| anything else, or no evidence link | `UNRESOLVED` |

**The W45.0 rule was wrong for case (c).** An observation that no surviving hypothesis
explains was classified `UNRESOLVED` — held out of the model — while the LIVE kernel applies
it. The restored session therefore contradicted the live session about the same observation:
**exactly the class of defect W45.0 exists to fix**, reproduced inside the migration itself.

The reason the rule was wrong is visible in the W44 code: the relation `CONTRADICTS` means
"no hypothesis explains this", not "this contradicts a belief". Holding every unexplained
observation preserved the obsolete W44 rule (W44 held on disagreement with ANY prediction) in
the one place where the current policy says otherwise.

**The W45.1 rule** consults the cognitive error records first, and the relation only as a
fallback:

| the durable evidence | the classification |
|---|---|
| the case is named by an error whose prediction was **unanimous** (`confidence ≥ 1.0`) | **`UNRESOLVED`** — it contradicted a belief |
| the case is named by an error with `disposition = MISSING_CONDITION` and a non-unanimous prediction | **`ELIGIBLE`** — the model had no account of it; under W45 this is learning, not a conflict with a belief |
| the case is named by an error with any other disposition | **`UNRESOLVED`** — conservatively |
| **no** error row and `relation = CONTRADICTS` | **`UNRESOLVED`** — conservatively |
| **no** error row and `relation ∈ {SUPPORTS, EXEMPLIFIES, QUALIFIES}` | **`ELIGIBLE`** |
| **no** evidence link at all | **`UNRESOLVED`** — it cannot be classified, and an unclassifiable record must not become model data |

When a case is named by SEVERAL errors, the most conservative classification wins.

**The records affected** are exactly those that (i) have a `cognitive_error` and (ii) whose
error carries `disposition = MISSING_CONDITION` with a non-unanimous prediction. Every other
case is classified as before.

**What is safe to do automatically:** the rule above — it is derived from durable evidence and
it agrees with the current kernel's own behaviour.

**What requires explicit adjudication:** a case whose records contradict each other (an error
that names a case and a relation that says the opposite), and a case that several errors name
with different dispositions. Those are held and wait for a human.

## 4. The synthetic fixture

`matrix-core/src/test/java/io/matrix/knowledge/ObservationLegacyBackfillTest.java` writes a
**v16 database by hand** — both the knowledge tables and the cognitive tables, in the v16
shape — inside a `@TempDir`, and then asserts the migrated dispositions.

| the case | the relation | the cognitive error | the confidence | the expected disposition | the result |
|---|---|---|---|---|---|
| `case-unsettled` | `EXEMPLIFIES` | none | 0.0 | `ELIGIBLE` | **`ELIGIBLE`** ✓ |
| `case-unanimous` | `CONTRADICTS` | `UNRESOLVED` | 1.0 | `UNRESOLVED` | **`UNRESOLVED`** ✓ |
| `case-unexplained` | `CONTRADICTS` | `MISSING_CONDITION` | 0.0 | `ELIGIBLE` | **`ELIGIBLE`** ✓ — it was `UNRESOLVED` under the W45.0 rule |
| `case-supporting` | `EXEMPLIFIES` | none | 1.0 | `ELIGIBLE` | **`ELIGIBLE`** ✓ |
| `case-orphan` | no evidence | none | — | `UNRESOLVED` | **`UNRESOLVED`** ✓ |
| `case-unexplained-conflict` | `CONTRADICTS` | none | — | `UNRESOLVED` | **`UNRESOLVED`** ✓ |

Two further checks in the same file:

- a **knowledge-only** database (no cognitive tables) → the fallback gives
  `case-unexplained = UNRESOLVED`, conservatively ✓;
- after the backfill the adjudication history holds one row per case, every
  `previous_disposition` is `NULL`, and `rebuildDispositionProjection` reports `true` ✓.

**The owner's production database was never touched.** Every fixture is written by hand inside
a temporary directory.

## 5. The migration, and its interruption

The v16 → v17 → v18 chain is additive and re-runnable:

- the tables are created with `CREATE TABLE IF NOT EXISTS`;
- the backfills are `INSERT OR IGNORE ... SELECT`;
- **the schema version is written LAST**, so an interrupted migration leaves the database
  claiming the old version with the new tables already in place — and running the migration
  again completes it.

The interruption is proved, not argued: `ObservationHistoryMigrationTest` writes a v17
database by hand, migrates it, **forces `schema_meta` back to 17** — exactly the state a
process killed before the version write leaves behind — opens the store again and lets the
migration run a second time. The assertions: the version is 18 again, the history holds
**exactly the same rows** (the backfill did not copy twice), and the projection rebuilds
identically.

Additivity is proved separately (`theMigrationLeavesEveryExistingTableExactlyAsItWas`): the
DDL of every existing table is compared before and after the migration, and it matches.

A fresh database is built at the current version by the same chain.

## 6. What remains unresolved

| the record | what cannot be inferred | what is safe |
|---|---|---|
| a v16 case with `relation = CONTRADICTS` and **no** error row | whether it contradicted a belief or was merely unexplained | hold it (`UNRESOLVED`) and adjudicate it once, explicitly |
| a v16 case named by **several** errors with different dispositions | which one is the current truth | the most conservative classification, and the review queue shows it |
| a v16 case in a **knowledge-only** database | cases (b) and (c) are indistinguishable | hold it (`UNRESOLVED`) |
| a v16 case whose conditions cannot be parsed | nothing | the observation is skipped, and the gap shows up as a missing observation rather than a wrong one |

**The honest summary:** the W45.0 limitation was stated as "a v16 database cannot distinguish
a contradiction from an unexplained observation". That is **true of the knowledge tables
alone** and **false of the database as a whole**, because the cognitive error records carry the
confidence and the disposition that tell the two apart. The corrected rule uses them, and it
changes the classification of one class of records: the unexplained observations that W44
recorded as `CONTRADICTS` are now `ELIGIBLE` — which is what the live kernel has been doing
all along.
