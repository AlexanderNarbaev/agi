# DESIGN-06: Модули входящих и исходящих сигналов — контракт, реестр, медиа

**Статус: normative** · Уровень: периферия контура. Заменяет размытое «кодировщики/декодировщики» из DESIGN-03 §2/§4 полноценной модульной архитектурой: каждый преобразователь «мысль ⇄ медиа» — отдельный, самостоятельно версионируемый и деплоющийся блок, внутри использующий BIR-алгоритмы, снаружи видимый только по контракту. Правила разработки — `docs/agents/AGENTS-MODULES.md`; JVM/GraalVM-ограничения — `docs/engineering/JAVA_NATIVE.md`.

## 1. Принципы

1. **Изоляция.** Модуль сигналов не знает о BRC, памяти и Persona; DELIBERATION не знает о медиа-форматах. Стык — только битовые вектора фиксированной схемы и контрактные метаданные (INV-P1..P4, DESIGN-03 §2).
2. **BIR внутри, контракт снаружи.** Модуль может внутренне применять TT/CLAUSESET/BDD (напр., аудио-модуль — CLAUSESET-классификатор ударных событий), но наружу отдаёт биты + witness; обратно — вердикт + witness оформляет в медиа.
3. **Модуль = артефакт.** Версия, схема битов, словари/пороги — единый загружаемый артефакт с хэшем (как BIR-артефакт, DESIGN-01 §6). Смена битовой схемы = major-версия.
4. **Отдельная деплоюемость.** Модуль может быть (а) классом в монолите, (б) отдельным GraalVM native-приложением с REST/MCP-фасадом (тяжёлые медиа: аудио/видео), (в) внешним сервисом по контракту. Смена формы деплоя не меняет контур.

## 2. Контракт SignalModule

```java
interface SignalModule {
    enum Direction { IN, OUT }                       // PERCEPTION / RENDERING
    enum MediaType { TEXT, NUMERIC, AUDIO, VIDEO, GRID, BINARY }
    String id();             // "text-lexicon"
    String version();        // semver; смена битовой схемы = major
    Direction direction();
    MediaType mediaType();
    int bitWidth();          // ширина выходного (IN) / входного (OUT) вектора
    String bitMeaning(int);  // INV-P3: обратимая диагностика каждого бита
}
```

- **IN-контракт:** `EncodedInput encode(media)` → `{bits, moduleId, moduleVersion, activeBits}`; `activeBits` — смыслы выставленных битов (witness на стадии восприятия).
- **OUT-контракт:** `media render(verdict, witness, refused)`; INV-R1 — вердикт неизменяем декодером.
- Операции кодирования/рендера — **чистые функции** при фиксированной версии (INV-P1); никакого wall-clock, RNG без seed, внешних вызовов вне явного `external`-помеченного адаптера.

## 3. Реестр модулей (ModuleRegistry)

Правила (реализованы в прототипе, см. §7):

- **R1.** Пара `(id, version)` уникальна; повторная регистрация — ошибка сборки контура.
- **R2.** `resolve(id, version)` детерминирован: точная версия, иначе максимальный semver. Запросы всегда резолвят явно; «магического» автообновления нет.
- **R3.** После сборки контура реестр `freeze()` → иммутабелен; публикация потокам — через final/volatile-семантику JMM (JAVA_NATIVE §2), без синхронизации на горячем пути.
- **R4.** Регистрация только явная из кода (`registry.register(...)`). ServiceLoader и classpath-сканирование запрещены: недетерминированный обход + рефлексия ломают native-image (JAVA_NATIVE §2).
- **R5.** Внешний модуль (отдельное приложение/сервис) регистрируется через адаптер `RemoteSignalModule` с тем же контрактом; таймаут и деградация — по DESIGN-03 §6 (`DEGRADED`-пометка).

## 4. Медиа-линейки

### 4.1. Текст
- `text-lexicon` (реализован): bag-of-words + биграммы по версионируемому словарю домена. Плотность кода контролируется (INV-P4).
- `text-embed-hash` (DESIGN-03 §2.1): LSH-подпись внешнего эмбеддинга; внешняя зависимость изолируется.
- OUT: `text-template` (реализован), `llm-render` (внешний, Guardrail-повтор, INV-R1).

### 4.2. Аудио
- `audio-bands` (реализован, прототип): PCM-окно → энергии полос + zero-crossing rate → термометрические биты. Продакшн-путь: FFT на Vector API (JAVA_NATIVE §3), окно/шаг/полосы — параметры версии артефакта.
- Перспектива (этап 3): `audio-events` — CLAUSESET-детектор событий поверх полос (ReflexLayer-кандидат, SUBSTRATE-MODELS §5).

### 4.3. Видео
- `video-grid`: кадр → даунскейл в квантованную сетку (аналог world-grid DESIGN-03 §2.1), каналы = квантованный цвет/движение; термометр по яркости. Ключевой кадр/шаг дискретизации — в версии.
- Честная граница: фотографическое качество — не ниша BIR (ANALYSIS §2, G-D); цель — доменные перцепты (состояние сцены, телеметрия экрана, SCADA-индикация).

### 4.4. Числа и сетки
- `numeric-thermometer` (реализован): quantile+термометр; границы — офлайн, в артефакте (INV-P1).
- `world-grid`: битмап дискретных каналов среды (без изменений из DESIGN-03).

### 4.5. Составная семантика
- `vsa-role` (DESIGN-03 §2, SUBSTRATE-MODELS §4.2): структурированный вход → гипервектор D=8192 (bundle(bind(роль, наполнитель))); версионируемый словарь ролей.

## 5. Сборка контура и ioSchema

- Биты разных модулей **не смешиваются** в одном векторе без ioSchema (INV-P2): сборщик контура выделяет каждому модулю диапазон битов рабочего состояния M0 и фиксирует отображение в ioSchema Capability; несогласованность — контрактный тест сборки.
- Политика делиберации обращается к битам через ioSchema, не через знание внутренностей модуля. В прототипе (§7) показан минимальный контур: 3 IN-модуля (текст/число/аудио) → CLAUSESET-политика → OUT-рендер с witness.

## 6. Развёртывание

| Форма | Когда | Контракт |
|---|---|---|
| Класс в монолите | текст, числа, сетки | прямой вызов, zero-copy |
| Native-приложение (GraalVM) | аудио/видео, DSP-тяжёлые | REST/MCP-фасад, тот же SignalModule-контракт; сборка — JAVA_NATIVE §2 |
| Внешний сервис | сторонние эмбеддинги, LLM-рендер | `RemoteSignalModule`, DEGRADED-режим |

## 7. Прототип и измерения

Код: `docs/research/prototype-java/` (Java 17, `javac`, без зависимостей). Результаты прогона (`demo_output.txt`, `bench_output.txt`):

| Измерение | Значение |
|---|---|
| Контур 3 IN + политика + OUT | детерминированный вердикт с witness по всем трём модальностям |
| Hamming-близость текстовых кодов | подмножество фраз = измеримое расстояние (4 бита на демо-паре) — основа M1 recall |
| TT eval on-heap (long[], k=16) | **0,77 нс/оценка** (20 млн оценок, прогрев C2) |
| TT eval off-heap (direct ByteBuffer) | **1,03 нс/оценка** — цена обхода лимитов кучи JMM ≈ +34%, приемлемо для крупных таблиц и DMA-пути |

JVM-числа подтверждают оценку ANALYSIS §4.2 (1–5 нс) и прототипные numpy-числа (65 нс) с запасом на два порядка.

## 8. Приёмочные тесты

1. Контрактный тест каждого модуля: `bitMeaning(i)` определён для всех i < bitWidth (INV-P3).
2. Детерминизм: два прогона encode на одном входе — бит-в-бит одинаковые bits (INV-P1).
3. Реестр: дубликат (id, version) отвергается; resolve без версии — детерминирован.
4. Сборка: попытка обратиться к биту вне диапазона ioSchema модуля — ошибка сборки (контрактный тест).
5. Плотность: для разреженных модулей доля единиц на репрезентативном корпусе в [0.1, 0.3] (INV-P4) — метрика в отчёте модуля.
6. Native-сборка: `native-image` собирается без `--initialize-at-run-time`-костылей и рефлексивных конфигов сверх явного белого списка (JAVA_NATIVE §2).
