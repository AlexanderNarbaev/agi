Boolean Intermediate Representation

A deterministic compute platform for safe AI

MATRIX runs deterministic Boolean functions instead of large language models. Every decision is a verifiable chain of bitwise operations. A FROZEN ethics layer rejects destructive commands at compile time, before they reach your application.

The system stores each Boolean function in three equivalent forms — TT (truth table), CLAUSESET (Tsetlin DNF), and BDD (reduced ordered binary decision diagram). Forms compile into each other and equivalence is verified by exhaustive enumeration.

Introduction

Modern AI deployment faces three problems: determinism (LLMs sample non-deterministically), verification (decisions can't be traced to a proof), and energy cost (one LLM token is roughly 10⁶× more expensive than one Boolean evaluation).

MATRIX addresses all three by replacing language model inference with Boolean function evaluation. The runtime is a single Java 25 process. There is no warm-up, no model loading, no GPU. The hot path is a few nanoseconds per decision.

The trade-off is scope: Boolean functions cannot generate open-ended language. For that workload, MATRIX treats an LLM as an untrusted peripheral service — verified at the boundary, never allowed to make the final call.

The BIR paradigm

The core data structure is the BIR unit:

BirUnit = (id, k, m, form, payload, header)

where:
  id      — unique identifier
  k       — number of input bits (k ≤ K_MAX = 20)
  m       — number of output bits
  form    — TT | CLAUSESET | BDD
  payload — function-specific data (truth table bytes, clauses, BDD nodes)
  header  — metadata: owner, FROZEN flag, version, signature

Every BIR unit declares its form at build time. The runtime picks the form that matches the operating context:

FormStorageEvaluationBest for
TT2^k bits2^k byte lookupk ≤ 20, hot-path decisions
CLAUSESETC clauses × k bitsThreshold test per clauseSparse rules, large k
BDDO(f) nodesGraph traversalFormal verification, Model Checking

Forms compile into each other through BirCompiler (SPEC-002). Equivalence is verified by enumerating all 2^k inputs and comparing outputs.

Three equivalent forms

Each form encodes the same Boolean function but optimizes a different property:

TT — Truth Table

The exhaustive table of all 2^k input combinations. A single byte lookup returns the output. At k=20 the table is 128 KB and holds any of the 22²⁰ ≈ 10⁶ Boolean functions.

// Evaluate a TT-form BIR
boolean f(long[] input) {
    int index = packBits(input);   // 0..2^k-1
    return tt[index >>> 3] & (1 << (index & 7)) != 0;
}

CLAUSESET — Disjunctive Normal Form with Tsetlin automata

A disjunction of clauses, each a conjunction of literals. Trained interactively by Tsetlin automata that include/exclude literals based on positive and negative feedback. Scales to k=784 (MNIST) without flattening to a table.

// Tsetlin training step
for each clause c in C:
    for each literal ℓ in c:
        automaton[c, ℓ].update(reward(ℓ, example))

BDD — Reduced Ordered Binary Decision Diagram

A canonical directed acyclic graph that compacts common sub-functions. Two BDDs are equivalent if and only if they have the same graph (cheap equality check). Parity-k functions need exactly 2k−1 ROBDD nodes — the theoretical ceiling that drove the multi-form architecture.

// Reduce a BDD
bdd = orderShannonExpansion(f, variableOrder)
bdd = reduce(bdd)   // merge equivalent sub-graphs
return bdd

FROZEN ethics layer

Three prohibitions sit at compile time, not runtime:

  • Don't kill. Any action that causes death is rejected.
  • Don't torture. Any action that inflicts suffering is rejected.
  • Don't enslave. Any action that removes freedom of choice is rejected.

The prohibitions are encoded as BIR units with the FROZEN flag set. The compiler refuses to emit bytecode that mutates them. The runtime refuses to evaluate a request that violates them. There is no runtime override path.

This is different from RLHF or system prompts. Those are advisory. The FROZEN layer is structural — the code cannot be the wrong thing, even by accident.

Quick start

Build, test, run the demo in three commands:

$ git clone https://github.com/AlexanderNarbaev/agi.git
$ cd agi
$ ./gradlew test                               # 1055+ tests
$ ./gradlew :matrix-core:quarkusBuild -Dquarkus.package.jar.type=uber-jar
$ java -jar matrix-core/build/*-runner.jar demo

Run a GridWorld simulation — a small agent evolves BIR-based rules to navigate an environment:

$ java -jar matrix-core/build/*-runner.jar simulate -g 20 -p 10 -k 16 --seed 42

Distill a HuggingFace model into BIR weights:

$ bash scripts/train_local.sh --model HuggingFaceTB/SmolLM2-135M
$ python scripts/pretrain_neurons.py --architecture llama --layers 6

Architecture

MATRIX is a single-process Java 25 runtime built on Quarkus 3.37.3. The application code at matrix-core is organized in eight layers, each consuming only the layer beneath it:

Layer 1: Boolean Compute (BIR)

The foundation. Three forms — bir.TtForm, bir.ClauseSetForm, bir.BddForm — compiled by bir.BirCompiler and evaluated by bir.BooleanRuntime. Two backends: bir.JvmSimdBackend (production) and bir.FpgaBackend (bitstream, no hardware yet).

Layer 2: Memory & RAG

rag.HybridBooleanRag combines four retrieval strategies in one RRF fusion:

StrategyBackendDistanceUse case
DenseBooleanIndexHammingBoolean queries
EmbeddingFloatEmbeddingIndexCosineSemantic search (ONNX runtime)
SparseKnowledgeIndexBM25-like scoringKeyword queries
GraphKnowledgeGraphStoreDegree centralityEntity relationships

Layer 3: Neural Compute

neuron.TruthTable, neuron.BatchEvaluator for SIMD-style batch evaluation, neuron.BatchMemoryAdapter for chunked dispatch (H-008 throughput ≥ 10³ ops/tick).

Layer 4: Lifecycle & Federation

lifecycle.TaskCell for ephemeral compute instances (DESIGN-12). noosphere.MeshFederation for distributed CRDT sync via Kafka + WebSocket with QuorumChecker 3/5 Byzantine fault tolerance.

Layer 5: Evolution & Cauldron

evolution.EvolutionLoop with genetic operators. cauldron.CauldronProtocol for new FNL generation. cauldron.GuhaCandidateGenerator (H-018, Hájek-Havránek) + cauldron.LevinSchedule (H-019, 2⁻ˡ Levin budget).

Layer 6: Pilots

pilot.NaiveMinecraftPilot for baseline random actions, pilot.LearnedMinecraftPilot for agents trained via Developmental Loop (H-005). Both implement pilot.MinecraftPilot.

Layer 7: FROZEN Ethics

ethics.EthicalFilter + guardrail.GuardrailEngine. Verified FPR 0%, TPR 100%, P99 latency 0 ms on the 30-input benchmark (H-006).

Layer 8: API

Quarkus REST + WebSocket + Model Context Protocol (MCP). One jar, one process.

Implemented algorithms

Ten core algorithms implemented in Java, with preregistered experimental hypotheses tracking validation status:

H-009

BIR-classifier

Binary classifier on BIR. Targets parity with LLM ≤3B at ±3 p.p. balanced accuracy with ≥10⁴× less energy on laptop hardware.

H-010

WNN/WiSARD

Single-pass ensemble of TT-units with address-RAM storage. Targets ±2 p.p. accuracy vs TsetlinTrainer at ≥10× faster training.

H-011

SDM/Kanerva

Sparse Distributed Memory: counters + threshold + Kanerva radius. Targets precision@5 ≥+5 p.p. vs flat top-K Hamming at same memory budget.

H-015

intESN Reservoir

VSA state + permutation recurrence + TT/WNN readout. Targets ±3 p.p. accuracy vs float-ESN at ≥10× less energy per decision.

H-016

MonotoneDecoder

Identification of monotone Boolean functions by maximal upper zero circuit. Targets ≥5× less corpus vs TsetlinTrainer on monotone domains.

H-017

LTL Model Checker

Formalization of DESIGN-07/08 in LTL with bounded model checking. Detects violations that AT-* acceptance tests miss. Pnueli school.

H-018

GUHA Candidate Generator

Systematic candidate generation via Hájek-Havránek enumeration. Targets ≥90% coverage of rule space at ≤30% of random-sampling budget.

H-019

Levin Schedule

Optimal budget allocation proportional to 2⁻ˡ. Targets ≥+15% coverage per joule vs uniform schedule.

H-005

LearnedMinecraftPilot

Minecraft pilot via Developmental Loop. Trains from episode history using BIR classification.

H-006

Guardrail

Verified: FPR 0%, TPR 100%, P99 latency 0 ms. Targets (≤5%, ≥95%, ≤50 ms) all exceeded.

One Boolean evaluation vs one LLM token on consumer hardware:

Per-decision ratio: ~10⁶× less energy, ~10⁴× faster. MATRIX does not generate language; for that scope a verification layer wraps an external model.

How it compares

MATRIX is not a language model. It does not generate text. For non-language scopes (classification, retrieval, rule-based decisions, safety filters, deterministic controllers) it offers trade-offs an LLM cannot match:
