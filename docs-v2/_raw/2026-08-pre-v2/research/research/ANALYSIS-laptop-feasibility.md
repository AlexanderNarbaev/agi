# Анализ: пробелы, возможности и расчёт ноутбучной реализуемости MATRIX vs маленькие LLM

**Статус: living** · Дата: 2026-08-01 · Основание: измерения прототипа (`prototype/RESULTS.md`) + аналитические расчёты этого документа. Целевое железо: Ryzen 9 9955HX (16C/32T), RTX 5070 (8 ГБ, в рантайме MATRIX не используется), 64 ГБ RAM.

## 1. Постановка вопроса

Может ли система на BIR-примитивах (TT/CLAUSESET/BDD), реализованная на уровне ноутбука, давать ответы, сопоставимые с LLM, запускаемыми на том же ноутбуке (класс 1–8B параметров)? Ответ зависит от класса задач — поэтому сначала честное разбиение.

## 2. Пробелы (где BIR-система принципиально уступает LLM)

| # | Пробел | Природа | Что с этим делать |

## 3. Возможности (где BIR-система сопоставима или превосходит)

| # | Возможность | Основание |
|---|---|---|
| O-1 | **Классификация/верификация структурированных входов**: точность сопоставима с маленькими LLM при на 5–6 порядков меньшей энергии и памяти | расчёт §4–§5 |
| O-2 | **Точная верификация**: эквивалентность, выполнимость, контрпримеры — LLM не дают вообще | измерено: MUX-11 эквивалентность True (RESULTS §3) |

| O-7 | **Энергетическая и юридическая чистота**: нет «чёрного ящика» в контуре решений | §5.3, CONSTITUTION I |

## 4. Теоретический расчёт ёмкости и сложности

### 4.1. Ёмкость представлений

| Форма | Число представимых функций | Память на функцию | Предел |
|---|---|---|---|
| TT, k входов | **2^(2ᵏ)** — все функции | 2ᵏ бит | k=20: 2^1 048 576 функций по 128 КБ |
| CLAUSESET (DNF, ≤C клауз, k переменных) | ≤ (3ᵏ+1)ᶜ (каждая переменная: +/−/отсутствует) | C·2k бит | паритет-k: C = 2ᵏ⁻¹ (измерено: 128 при k=8, RESULTS §4) |
| BDD | все функции; размер зависит от порядка π | от k до 2ᵏ/k узлов | умножение n×n — экспонента при любом π (Bryant 1986) |

Длина описания DNF: log₂(3ᵏ+1)ᶜ ≈ **C·k·1,58 бит** → выборка обучения (PAC): n ≳ (C·k·ln3 + ln(1/δ))/ε. Пример: C=100, k=784, ε=0,05, δ=0,01 → n ≳ (100·784·1,1 + 4,6)/0,05 ≈ **1,7 млн примеров** — верхняя PAC-оценка; практика (TM, деревья) обучается на десятках тысяч за счёт индуктивного сдвига (разреженность клауз). Вывод: для доменов владельца (корпуса 10³–10⁵ примеров) — C держать ≤ 50–100 на класс, контроль через Φ (MDL-рачет сам штрафует избыточные клаузы).

### 4.2. Latency (расчёт + измерения)

| Операция | Измерено (numpy) | Оценка JVM (Vector API) | Основание оценки |
|---|---|---|---|
| TT eval k=16 | 65,3 нс | **1–5 нс** | gather из 8 КБ (L1/L2) + сдвиг: 3–5 тактов плюс доступ к кэшу ~1–4 нс |
| CLAUSESET eval, C=54, k=784 (MNIST-прототип) | 425 мкс | **≈3 мкс** | 54 клаузы × (784/64=13 слов × 4 ops) ≈ 2 800 word-ops ≈ 2 800 × ~1 нс |
| BDD-эквивалентность двух артефактов | — | O(1) после построения; построение O(2ᵏ) из TT | DESIGN-01 §4.3 |
| LLM 3B, 1 токен (CPU, 4-bit) | — | **30–70 мс** (15–30 ток/с) | порядок величины для Ryzen 9 мобильного; точные числа — бенчмарк при пилоте |

Итог: элементарное булево решение **на 4–5 порядков быстрее** одного токена LLM. Полный BRC-ответ (≤5 шагов × ~3 мкс) ≈ 15 мкс против 2–10 с ответа LLM.

### 4.3. Память (ноутбук 64 ГБ)

| Система | Резидентная память | Что влезает |
|---|---|---|
| LLM 3B (4-bit) | ~2 ГБ веса + KV-кэш | одна модель, общего назначения |
| LLM 8B (4-bit) | ~5 ГБ | одна модель |
| MATRIX (целевая конфигурация) | 10⁶ TT-единиц k=16 (8 КБ) = 8 ГБ; **или** 10⁷ CLAUSESET-единиц (3 КБ) = 30 ГБ; или смешанно | целая экосистема Persona: при 10⁴ единиц на Persona — сотни профессионалов одновременно активны |

### 4.4. Пропускная способность обучения (ноутбук)

Конвейер «дерево → клаузы» (измерено): MNIST 10k примеров, k=784 → обучение+извлечение ≈ **14 с** (RESULTS §2). TM-обучение (оценка по каноническим результатам): MNIST-эпоха на CPU ≈ 10–60 с → полноценное доменное переобучение — **ночное окно DESIGN-05 §4 достаточно с запасом** (десятки доменов за ночь).

## 5. Энергия

| Уровень | Расчёт | Значение |
|---|---|---|
| Теоретический пол (Ландауэр, 300 K) | kT·ln2 = 2,87·10⁻²¹ Дж/бит | CLAUSESET-оценка ≈ 3·10³ бит-оп → ~10⁻¹⁷ Дж |
| Практический CPU (~1 нДж/оп, порядок) | 2 800 ops × 1 нДж | **~3 мкДж/оценка** |
| LLM 3B, 1 токен | 2·3·10⁹ FLOP × ~0,5–2 пДж/FLOP (GPU) | **~3–12 Дж/токен** |

Разница на элементарное решение: **~10⁶×**. Ответ LLM (100–500 токенов) стоит как 10⁸–10⁹ булевых оценок. Это и есть количественное обоснование целей G1/G2: guardrail на каждый токен LLM энергетически «бесплатен» относительно самого LLM.

## 6. Сопоставимость с LLM на ноутбуке — итоговая матрица

| Класс задач | BIR-система | LLM 1–8B (локально) | Вердикт |
|---|---|---|---|
| Классификация структурированная (токсичность, домен, intent) | сопоставимо: 0,8–0,95 по домену, мкс | сопоставимо, секунды | **BIR: паритет по качеству, выигрыш 10⁴–10⁶× по стоимости** |
| Верификация/доказательство (эквивалентность, запреты) | точно | невозможно | **BIR единственный вариант** |
| Ответ по корпусу с цитатой и witness | да (Knowledge Stack) | да, но без гарантии цитаты | **BIR сильнее по аудиту, LLM сильнее по языку** → гибрид: LLM на краях, BIR в сердцевине |
| Свободный диалог | нет (G-A) | да | **LLM; MATRIX молчит или делегирует** |
| SCADA/real-time | нс–мкс, FPGA | неприменимо | **BIR единственный вариант** |

**Общий ответ на вопрос §1:** на структурированных задачах ноутбучная BIR-система сопоставима с локальными LLM 1–8B по качеству и превосходит их на 4–6 порядков по latency, памяти и энергии; на открытом языке — принципиально не конкурент, и архитектура это честно фиксирует (LLM — недоверенный периферийный сервис, DESIGN-03 §6).
