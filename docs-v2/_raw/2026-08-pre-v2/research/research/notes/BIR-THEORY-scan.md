## 1. Минимизация булевых функций: Espresso и Quine–McCluskey

### 1.1 Выжимка из литературы

- Двухуровневая минимизация (минимальное SOP/покрытие) — NP-трудная задача; точные методы (QM с решением покрытия) практичны только при малом числе простых импликант. Это зафиксировано во всех учебных линиях, включая диссертации и курсы Berkeley/Columbia [L2].
- **Quine–McCluskey**: порождает *все* простые импликанты (их может быть экспоненциально много — до ~3ᵏ/√k для k переменных), затем решает точное покрытие (set covering, само NP-трудное). При k≤12–16 выполним для многих функций, но деградирует резко при плотных таблицах.
- **Espresso (Espresso-II, Brayton–Hachtel–McMullen–Sangiovanni-Vincentelli, книга 1984)** [L1]: не порождает все простые импликанты. Итеративный цикл `EXPAND → IRREDUNDANT → REDUCE` над текущим покрытием, плюс выделение существенных импликант и (опционально) `LAST_GASP`. Ключевые приёмы:
  - дополнение функции вычисляется рекурсивно (по Шеннону), с быстрым спецслучаем для **унатных** функций;
  - `EXPAND` делает каждый куб максимальным (импликантом), удаляя покрытые кубы;
  - `REDUCE` уменьшает кубы до минимальных, сохраняющих покрытие, — расширяет пространство для следующего `EXPAND`;
  - `IRREDUNDANT` удаляет избыточные кубы через относительно-эссенциальный анализ.
- **Espresso-MV** (Rudell & Sangiovanni-Vincentelli, 1986/1987) [L1]: переформулировка через многозначную логику; та же книга-алгоритмы, но компактнее; из этих же эвристик строится точный минимизатор (ESPRESSO-EXACT), где при неоднозначности делается ветвление. Важный вывод Rudell'а: результат точного минимизатора — лучший индикатор качества эвристики; на практических бенчмарках эвристика Espresso **обычно даёт минимум или отличается на единицы кубов** [L1/L2].
- Практическая сложность при k≤20: таблица истинности 2²⁰ = 1M бит — сама по себе тривиальна для памяти; узкое место — число импликант. Для разреженных функций (мало minterm'ов, что типично для дистиллированных правил) эвристика Espresso работает за миллисекунды–секунды; точный QM имеет смысл как *эталон качества* на бенчмарке, а не как продакшн-путь.
- **Java-библиотеки:** зрелой поддерживаемой Java-реализации Espresso не найдено (есть старые учебные порты и C-оригинал из Berkeley) [L3, проверено поиском]. Вывод соответствует решению проекта: своя реализация эвристик, без новой зависимости.

### 1.2 Применимость к SPEC-002 (этап A, FR-A1: TT→CLAUSESET «минимизация эспрессо-типа»)

- Прямое попадание: TT→CLAUSESET для k≤20 — это и есть двухуровневая минимизация. Реализуем **Espresso-lite** (expand/reduce/irredundant + essentials), без `LAST_GASP` на первой итерации.
- Конверсия точная по построению (покрытие ON-set'а); дополнительно каждая конверсия проверяется BDD-эквивалентностью в CI (INV-5) — эвристика не обязана быть минимальной, обязана быть **правильной**.
- Для мультивыходных функций (m>1) использовать MV-формулировку Rudell'а (общие кубы между выходами) — это удешевляет CLAUSESET-артефакты.
- Бенчмарк качества: на подмножестве функций k≤12 прогнать точный минимизатор (QM + точное покрытие через перебор/ILP в офлайн-скрипте) и опубликовать зазор эвристики в отчёте — число как «прототипное», не «литературное».

### 1.3 Рекомендуемый псевдокод (ядро цикла)

```
minimize(F, D):                     // ON-set F, don't-care D (кубы над k литералами)
    R  = complement(F ∪ D)          // рекурсивно по Шеннону; быстрый путь для унатных
    F' = F ∪ D
    C  = expand(F', R, F)           // каждый куб → импликант; перекрытые кубы удаляются
    C  = irredundant(C, D)          // удалить покрытые другими кубы
    E  = essentials(C, D)           // существенные импликанты — в ответ навсегда
    loop до сходимости (|C| не уменьшается):
        C = reduce(C ∪ E, D)  \ E   // минимальные кубы, сохраняющие покрытие
        C = expand(C ∪ E, R, D) \ E
        C = irredundant(C, D)
    return C ∪ E                    // CLAUSESET (DNF); BDD-check: C∪E ≡ F (мод. D)
```

Представление куба — пара бит-масок `(value, mask)` (в проекте уже соответствует идиоме TT/CLAUSESET); операции покрытия — целочисленные, SIMD-дружественные.

## 2. BDD: классика Bryant и границы

### 2.1 Выжимка из литературы

- **Bryant 1986** [L1]: ROBDD — каноническая форма при фиксированном порядке переменных и редукции (слияние изоморфных подграфов, удаление узлов с совпадающими ветвями). Каноничность → проверка эквивалентности `f ≡ g` сводится к сравнению указателей корней после построения в одном менеджере. Все логические операции — полиномиальны от *размеров операндов*.
- **Brace–Rudell–Bryant 1990 (DAC)** [L1] — промышленный рецепт пакета:
  - **unique table**: хеш-таблица по тройке `(var, low, high)` → каждая подфункция существует в единственном экземпляре (структурное хеширование);
  - **computed table (cache)**: кеш по `(op, f, g)` → `apply` становится полиномиальным вместо экспоненциального;
  - **ITE-форма**: все двуместные операции выражаются через `ite(f,g,h) = f·g + ¬f·h`; терминальные случаи и симметрии (стандартные тройки) режут кеш-промахи;
  - garbage collection по ссылочным счётчикам + динамическое расширение таблиц.
- **Известные границы** [L1]:
  - умножение целых: BDD средних битов произведения экспоненциальны при *любом* порядке переменных (Bryant 1991, IEEE TC 40(2));
  - hidden weighted bit (HWB): экспоненциальный размер при любом порядке (Bryant 1991; обзоры Bollig/Wegener) — классический контрпример «BDD сжимает всё разумное»;
  - оптимальный порядок переменных — NP-complete (Bollig & Wegener 1996);
  - размер критично зависит от порядка: от линейного до экспоненциального на одной функции.
- **Sifting (Rudell, ICCAD 1993)** [L1]: динамическое переупорядочивание перемещением каждой переменной по всем позициям с локальным swap соседних уровней (swap — локальная операция над unique table, O(узлы двух уровней)). Стандарт в CUDD/BuDDy. Стоимость — периодические квадратичные проходы; окупается на больших схемах при плохом начальном порядке.
- **Java-реализации:** JavaBDD (Whaley) — 100%-Java движок + JNI-мосты к CUDD/BuDDy/CAL [L3]; проект давно малоподдерживается. Собственный пакет (FR-A2) — обоснованный выбор: k умеренный, нужен контроль детерминизма и хешей (audit), а JNI в рантайм-контуре — лишний риск.

### 2.2 Применимость к SPEC-002 (этап A, FR-A2; INV-5)

- Роль BDD в проекте — **верификация и аудит**, не основное исполнение: эквивалентность артефактов после конверсий, проверка «намеренно битого компилятора». Для этого достаточно одного разделяемого менеджера с фиксированным порядком переменных — каноничность бесплатна.
- **Sifting не нужен на этапе A** (спека уже откладывает — литература подтверждает): reordering окупается, когда строятся большие BDD неизвестной структуры (model checking, синтез). Наш кейс — k≤20 для TT-сравнений и умеренные CLAUSESET; оба операнда строятся в одном порядке, эквивалентность не зависит от качества порядка (зависит только размер/время). Риск-функции (умножение, HWB-подобные) в домене правил и guardrail'ов не ожидаются; если появятся — TT-форма для k≤20 всегда служит запасным эталоном.
- Рекомендации по реализации (соответствуют FR-A2, детализируют):
  - менеджер: `long[]`-узлы (var:32 | low:32 | high:32 в двух слотах), unique table — open-addressing хеш по тройке; computed cache — хеш по `(op, f, g)` с политикой перезаписи;
  - все операции через ITE; отдельный `apply` не писать — ITE строго общее (Brace–Rudell–Bryant);
  - complemented edges — **отложить** (экономия памяти ~2×, но усложняет каноничность и отладку; для наших размеров не критично);
  - jqwik-свойства из FR-A2 (каноничность, eval(BDD)=eval(TT)) + дополнительно: `ite(f,1,0)=f`, `build(f) == build(f')` для семантически равных покрытий из минимизатора §1 — это замыкает этап A в единый контур самопроверки.

### 2.3 Псевдокод ITE (по Brace–Rudell–Bryant)

```
ite(f, g, h):
    if f == 1: return g
    if f == 0: return h
    if g == h: return g
    if g == 1 && h == 0: return f
    if (r = computedCache[f, g, h]) != null: return r
    v = min(topVar(f), topVar(g), topVar(h))
    t = ite(cofactor(f,v,1), cofactor(g,v,1), cofactor(h,v,1))
    e = ite(cofactor(f,v,0), cofactor(g,v,0), cofactor(h,v,0))
    if t == e: r = t
    else:      r = uniqueTable.findOrAdd(v, t, e)
    computedCache[f, g, h] = r
    return r
```

## 3. Машина Цетлина как producer (этап B)

### 3.1 Выжимка из литературы

- **Структура (Granmo 2018, arXiv:1804.01508)** [L1]: каждому входному признаку xᵢ соответствуют два литерала (xᵢ, ¬xᵢ), каждым литералом в каждой клаузе управляет двухдейственный автомат Цетлина с **2N состояниями**; состояния 1..N → действие Exclude, N+1..2N → Include. Клауза — конъюнкция включённых литералов; класс решается суммой голосов клауз положительной и отрицательной полярности с порогом T (клиппинг суммы в ±T).
- **Feedback Type I** (борьба с false negatives, запоминает частые паттерны): при y=1 для положительных клауз — Include награда/Exclude штраф с вероятностями, зависящими от s (параметр стохастичности) и от значения литерала; при y=0 — зеркально для отрицательных клауз. **Feedback Type II** (борьба с false positives, дискриминация): срабатывает при ошибочной полярности клаузы и подталкивает к включению 0-значных литералов, делающих клаузу ложной. Вероятность обновления клаузы модулируется голосованием: (T − clip(v))/2T.
- **Теоретический результат Granmo 2018**: равновесия Нэша игры автоматов совпадают с клаузами оптимальной точности — т.е. обучение «без локальных оптимумов» в терминах этой игры. Осторожно: это свойство игровой постановки, не гарантия оптимума по данным [L1].
- **Конвергенция**: есть вероятностный анализ сходимости (arXiv:2310.02005) [L1-preprint] — почти наверняка правильное обучение на «простых» концептах; честная граница — шумные данные требуют настройки s и T.
- **Масштабирование/варианты**: Convolutional TM (arXiv:1905.09688) — конкурентоспособна на MNIST/K-MNIST/F-MNIST/CIFAR-2 в своём классе; Weighted TM (arXiv:1911.12607) — сжатие представления взвешенными клаузами; аппаратные ускорители (65-nm ASIC, 8.6 нДж/кадр MNIST, arXiv:2501.19347) — подтверждение FPGA/ASIC-пригодности клауз-плюс-голосование (релевантно FR-D2).
- **Сравнение с BNN**: ETHEREAL (arXiv:2502.05640) [L1-preprint] заявляет на порядок меньшие latency/энергию против BNN на сжатой TM — но это числа авторов на их установке; для EXP-002 используем их только как внешний ориентир с пометкой «литература», сравнение делаем своим JMH-прогоном (критерий H-002).
- **Типичные ловушки** (обзор 360° TM, TechRxiv [L2]; Berge et al. 2019 [L1]):
  - **бинаризация доминирует над качеством** — выбор порогов/кодирования входа влияет сильнее, чем гиперпараметры TM; фиксировать метод бинаризации до эксперимента (EXP-002 уже требует);
  - чувствительность к шуму меток и смещённым классам; s управляет компромиссом шум/запоминание;
  - рост числа клауз и T улучшает точность ценой памяти/времени — есть рабочая область, за ней плато;
  - наивная реализация без эталонного воспроизведения даёт расходящиеся результаты — в проекте уже зафиксировано (prototype/RESULTS §5, предэтап EXP-002: MUX, noisy-XOR до доменов).

### 3.2 Применимость к SPEC-002 (этап B, FR-B1/B2)

- Реализация строго по Granmo 2018, таблицы feedback I/II — как в Berge et al. 2019 (таблицы наград/штрафов в явном виде, проверяемо глазами). jqwik-свойства из FR-B1 (границы состояний 1..2N, монотонность feedback) напрямую следуют из структуры автомата.
- Детерминизм (CONSTITUTION II): все стохастические решения (вероятности s, обновления по голосованию) — через фиксированный `SplittableRandom(seed)` в конфиге обучения; рантайм CLAUSESET после экспорта стохастичности не содержит вообще (INV-1).
- Экспорт TM→CLAUSESET: клауза = включённые литералы; голосование = взвешенная сумма (Weighted TM оставить как опцию за конфигом, базово — унимодальные веса ±1). Property-тест FR-B2: `eval(CLAUSESET)(x) == sign(Σ votes)` на одних входах.
- Обязательный предэтап EXP-002 (воспроизведение эталонных чисел на MUX/noisy-XOR) поддержан литературой: без него доменные результаты недействительны.

## 4. Проверка эквивалентности булевых схем и мутационное тестирование компилятора форм

### 4.1 Выжимка из литературы

- **Промышленный стандарт CEC** (combinational equivalence checking): **miter** — две схемы соединяются XOR по выходам, выходы XOR объединяются OR; эквивалентность ⇔ miter ≡ 0. Движки: **SAT-sweeping** над AIG (структурное хеширование + битовая симуляция случайными векторами для кандидатов + SAT-опровержение/подтверждение пар, слияние доказанно-эквивалентных узлов) — основной метод де-факто (линия ABC/Berkeley; свежие обзоры arXiv:2507.02008, arXiv:2501.14740 [L1-preprint/L2]).
- **BDD-sweeping**: построение BDD для узлов, слияние узлов с одинаковым корнем; исторически конкурент SAT-sweeping, страдает взрывом на умножителях (§2). Классическая интеграция — Paruthi & Kuehlmann (IBM): SAT + BDD + случайная симуляция в одном контуре [L1].
- Для нашего контура (k≤20, три формы): BDD-сравнение корней в общем менеджере — исчерпывающая и самая дешёвая проверка; SAT-sweeping становится актуален только если появятся высокоарные CLAUSESET-артефакты (k≫20), где TT-эталон невозможен. Тогда: симуляция случайными векторами (быстрый отлов неэквивалентности) + SAT-запрос на miter — внешний шаг CI, не рантайм.
- **Мутационное тестирование компиляторов / «намеренно битый компилятор»** (INV-5, CONSTITUTION VI.4):
  - Классика тестирования компиляторов: **дифференциальное тестирование** (Csmith, Yang et al. PLDI 2011 — случайные программы, оракул = сравнение выходов разных компиляторов) и **метаморфное тестирование** (эквивалентные преобразования входа; обзор Chen et al., ACM CSUR 2020) [L1].
  - Перенос на BIR-компилятор: оракул у нас есть точный (BDD-эквивалентность), значит схема проще Csmith — не нужно дифференциальное сравнение, достаточно:
    1. **генератор случайных функций** (k≤16, фиксированный seed) → round-trip TT→BDD→TT, TT→CLAUSESET→eval — свойство «эквивалентно»;
    2. **библиотека мутантов компилятора**: детерминированные сломы каждого шага (пропуск куба в expand, неверный порядок переменных в BDD, потеря don't-care, перепутанная полярность клаузы) — каждый мутант **обязан** ловиться BDD-проверкой; мутант, прошедший незамеченным, = дыра в верификации, фиксируется как баг CI-гейта;
    3. **метаморфные пары**: семантически равные входы (перестановка кубов в покрытии, перенумерация переменных с согласованным reorder) должны давать эквивалентные артефакты.
- Готовых Java-инструментов именно для «мутационного теста компиляторов булевых форм» не найдено — конструкция своя, но методология прямая из линии compiler testing [L1/L2]. Часть конкретных мутантов — инженерная рекомендация, помечена [speculative] как не покрытая источниками дословно.

### 4.2 Применимость к SPEC-002 (INV-5, CI-контур)

- Этап A: BDD-проверка эквивалентности в CI для всех точных конверсий (INV-5) + набор мутантов компилятора как отдельный тест-класс (каждый мутант — красный без верификатора).
- Этап B: property-тест FR-B2 — тот же оракул; мутация экспорта (сдвиг порога T, потеря клаузы) должна ловиться.
- Этап D: iverilog-симуляция Verilog против BIR-эталона (FR-D2) — это ровно схема miter-дифференцирования с симуляцией; SAT-шаг не нужен при k≤20 (исчерпывающая симуляция 2^k дешевле).

## 6. Сводка рекомендаций (приоритет для реализации)

1. **TT→CLAUSESET — свой Espresso-lite** (expand/reduce/irredundant + essentials, куб = пара бит-масок; MV-вариант для мультивыходных). Точный QM — только офлайн-эталон качества на k≤12, не продакшн-путь. Java-зависимость не добавлять (зрелых нет).
2. **BDD-пакет минимального промышленного состава**: один менеджер, unique table + computed cache, всё через ITE; complemented edges и sifting — отложить с обоснованием из литературы (роль BDD — верификация при умеренном k, оба операнда в одном порядке; reordering не влияет на корректность эквивалентности, только на размер).
3. **TM реализовать строго по Granmo 2018 / Berge 2019** (таблицы feedback I/II дословно), все стохастические решения — фиксированный seed в конфиге; до доменов — обязательное воспроизведение эталонных чисел на MUX/noisy-XOR (уже в EXP-002; литература подтверждает риск наивной реализации). Главный риск — бинаризация входа, не гиперпараметры: метод бинаризации фиксировать до запуска.
4. **Верификационный контур = BDD-сравнение корней** (исчерпывающе для k≤20); SAT-sweeping и miter-поток держать как задокументированный путь для будущих высокоарных артефактов; для FPGA (этап D) — исчерпывающая симуляция 2^k вместо SAT.
5. **Мутационный гейт компилятора форм**: библиотека детерминированных мутантов (пропуск куба, неверный порядок переменных, потеря don't-care, полярность клаузы), каждый обязан ловиться BDD-проверкой в CI; непойманный мутант = баг гейта (INV-5). Методология — линия Csmith/metamorphic testing [L1], конкретный набор мутантов — наша конструкция [speculative в части состава].

*Численные claims из препринтов (ETHEREAL vs BNN, ASIC-ускорители TM) — «литература» с пометкой; свои замеры — только через EXP-002/003 по протоколу.*
