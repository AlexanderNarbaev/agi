## 1. Цели (по убыванию ценности)

## 2. Этапы и критерии выхода

### Этап 0 — Порядок (текущий)
Архивация устаревших документов (docs/archive/), карантин pretrain_neurons.py, синхронизация статусов репозиториев (README).
**Выход:** дерево документации соответствует INDEX.md; агенты работают по AGENTS.md без ориентационных ошибок; pretrain_neurons.py изолирован (SPEC-001 этап A).

### Этап 1 — Честная база (месяцы 0–3)
- BIR-ядро (SPEC-002 этап A): три формы, компилятор, BDD-верификатор; адаптеры существующего ядра (strangler-fig — см. §3).
- Долг: пропуск эмбеддинга в HybridBooleanRag (H-007); пакетный режим памяти MPDT (H-008); тесты api/cli/cluster/events/R2dbcEventJournal; контрактные тесты JSON↔Avro.
- Воспроизводимость: golden-векторы DJL/ONNX в CI (CONSTITUTION VII.2); бюджеты времени агента (ротация контекста, публикация hit-rate); Obsidian-агент на тонком MCP-клиенте.
**Выход:** G3 достигнута; старый API deprecated; CI зелёный на каждом шаге миграции.

### Этап 2 — Guardrail MVP (месяцы 3–9)
Модуль matrix-guardrail: BIR-композиции запретов (статья I), SAT-доказательства противоречий, BRC-контрпримеры, EXP-006. Публикация как сервиса через прокси/MCP (DESIGN-03 §5); интеграция с внешним retrieval (напр. rag-system) — по контракту ADR-001.
**Выход:** G1 достигнута на JVM; 2 пилотных пользователя.

### Этап 3 — Developmental Loop (месяцы 6–12, параллельно)
SPEC-000 полностью + EXP-005; matrix-ricci MVP + EXP-004 (SPEC-003); этюдная система (этюд = автоматическая проверка трансфера).
**Выход:** G4 достигнута или честно опровергнута (публикация в обоих случаях).

### Этап 4 — FPGA Safety Core (месяцы 12–24)
FpgaBackend (SPEC-002 этап D): TT→LUT, CLAUSESET→Verilog; демо-полигон: логика безопасности учебного стенда (уровень формальной верификации IEC 61508 — не сертификация); измерения latency/энергии.
**Выход:** G2-демо; внешний аудит кода и верификационного контура.

### Этап 5 — Noosphere, узел-клиент (месяцы 18–30, спек-гейт)
Фаза A (после G1): mesh справочников/проверенных фактов — CRDT-репликация (G-set факты, OR-set теги, PN-counters), подписанная личным ключом владельца, согласование слияний.
Фаза B (спек, только после пилотов): mesh форм BIR (k≤12), консенсус-кворум 3 из 5 узлов.
**Выход:** фаза A работает между ≥2 реальными узлами; политика доверия (модель Лумана, FOUNDATIONS §7.3) опубликована.

## 3. Стратегия миграции кодовой базы (strangler-fig)

Новые модули (`matrix-bir`, `matrix-runtime`, `matrix-learn`, `matrix-substrate`, `matrix-developmental`, `matrix-ricci`, `matrix-guardrail`) создаются **рядом** с существующими; адаптеры заворачивают старые компоненты в новые контракты; старые API помечаются deprecated и удаляются только после полного перехода потребителей. Правила:

1. CI зелёный на каждом шаге; ни одного «большого переписывания».
2. Каждый адаптер — с property-тестом эквивалентности поведения (jqwik).
3. Переход потребителя на новый модуль = отдельный коммит с записью в WAL.md.
4. Карта модулей и владение границами — ARCHITECTURE.md §2; нарушение границ ловит ArchUnit.

## 4. Чего не делать (по приоритету)

1. Не расширять scope: никаких новых продуктовых линий до закрытия G1–G4.
2. Не писать «AGI» в маркетинг и не обещать свойств вне доказанных (CONSTITUTION VI.1).
3. Не внедрять Python/DL4J/TensorNEAT/GPU-зависимость в продакшн-контур (CONSTITUTION VII; JAVA_STACK.md).
4. Не обучать в рантайме; не менять пороги метрик post hoc (CONSTITUTION II.2, VI.2).
5. Не строить Noosphere-фазу B до пилотов G1/G3 (спек-гейт этапа 5).
6. Не удалять устаревшие документы без архивации (процесс INSTALL.md).

| Риск | Сигнал | Митигация |

| Дистилляция не достигает fidelity (H-001 отклонена) | EXP-001 отрицателен | ADR: закрыть линию, знания из корпусов/Tsetlin; вывод → OP-3 |

| Один разработчик — бутылочное горлышко | этапы ползут | жёсткий приоритет G3→G1→G4; отказ от G2/G5 без ущерба ядру |
| Дрейф компетенций в долгих сессиях | рост drift-events (METRICS) | авто-понижение MA, ротация контекста, бюджеты времени |
