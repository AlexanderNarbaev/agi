# DESIGN-13. Реестр действий с ioSchema (контракты Хоара / доменный слой PDDL)

- **Статус:** proposed (детализация STRIPS-контрактов из DESIGN-12/§52; двойное основание волн 20)
- **Уровень:** жизненный цикл и контур (L7/L6 в SYSTEM-SYNTHESIS; компиляторный слой L2 — верификация контрактов)
- **Трассировка:** DESIGN-12 (TaskCell), DESIGN-03 (BRC-контур), DESIGN-05 (журнал M4), DESIGN-11 (бюджеты), ADR-005 (четыре класса отказов); основания: атлас §52 (STRIPS — оператор как контракт, PLANEX — мониторинг исполнения), §69 (процедурная семантика SHRDLU — ioSchema как единственная форма «языка»), §80 (Хоар 1969 — триплеты P{Q}R, композициональная проверка, инвариант+вариант), §81 (PDDL — доменный язык отделён от исполнителей, три хэша, grounding как строка бюджета), §82 (Милнер CCS — бисимуляция как критерий свопа), §68 (уровни с контрактами)
- **Зависимости:** DESIGN-01/02 (BIR-артефакты, композиция), DESIGN-05 (M-слои, журнал, tombstone), DESIGN-11 (BudgetEnvelope), DESIGN-12 (TaskCell как исполнитель планов)

## 1. Назначение

Единый реестр действий контура, в котором **действие есть проверяемый контракт**, а не вызываемая процедура. Три исторических основания сходятся в одном механизме:

1. **Форма контракта (§80, Хоар):** действие специфицируется триплетом P{Q}R — предусловие P (трёхзначный предикат над типизированным состоянием), тело Q (ссылка на исполнителя), постусловие R (декларируемая дельта состояния). Композиция триплетов по синтаксису плана даёт **проверку плана до исполнения**: цепочка P₁{Q₁}R₁, P₂{Q₂}R₂ корректна, если R₁ ⟹ P₂ доказуемо на домене. Разрыв цепочки — не сбой исполнения, а вердикт UNDECIDED с типизированным остатком (каких свидетельств/условий не хватает) — вход средне-целевого анализа (§52).
2. **Доменный слой (§81, PDDL):** реестр действий (домен) отделён от задачи (цель с акцептором результата, §41) и от исполнителя (планировщик/BRC-контур). Три версионируемых артефакта с тремя хэшами: domainHash, problemHash, plannerHash — журнал M4 фиксирует все три на каждый BRC-акт (полная воспроизводимость трасс, §45). Grounding параметризованных действий на малом пространстве (k≤20, потолок §38) — **явная строка бюджета** бюджетера, не скрытая экспонента.
3. **Критерий замещения (§82, Милнер):** смена версии действия в реестре — атомарный своп с проверкой наблюдаемой эквивалентности на объявленном классе взаимодействий; у нас критерий усилен до **BDD-эквивалентности** таблиц контракта на валидированном классе (проверяемая, не выборочная). Эквивалентность на корпусе трасс — слабая, только ранжирование (хартия измерителей §73).

Реестр — единственная точка, через которую контур получает право действия: ни BRC-ветка, ни REFLEX-ветка, ни TaskCell не исполняют ничего вне реестра.

## 2. Структуры данных

```
ActionContract              // единица реестра (BIR-артефакт, DESIGN-01)
  name: Symbol              // референтное имя (B72, §24)
  ioSchema:                 // типизированные входы/выходы (§69)
    inputs:  Param[]        // (имя, тип ioSchema, роль)
    outputs: Param[]
  pre:  ClauseSet           // предусловие P: трёхзначный предикат над срезом M1
                            // (accept / reject / undecided — Клини, §10/§52)
  delta:                    // постусловие R: декларируемая дельта (add/delete, §52)
    add: ClauseSet
    del: ClauseSet
  variant: BudgetTerm       // вариант цикла ≡ бюджет (физический, не математический, §80)
  executor:                 // тело Q: кто исполняет
    kind: enum {BRC_PLAN, REFLEX_TABLE, TOOL, SUBGOAL_SPAWN}
    ref:  ArtifactRef       // TT/BDD-таблица, планировщик, инструмент
  validatedClass: ClassSpec // объявленный класс взаимодействий (для свопа, §82)
  versionHash, provenance

ActionRegistry              // доменный слой (§81)
  domainHash                // configHash домена: типы + действия + инварианты
  actions: Map<Symbol, ActionContract>
  invariants: ClauseSet[]   // конституционные инварианты домена (уровень §68)
  groundingBudget: long     // потолок стоимости конкретизации (k≤20)

PlanCheck                   // результат проверки плана до исполнения (§80)
  verdict: accept | reject | undecided
  residue: Residue?         // при undecided: типизированный остаток
                            // (индекс разрыва, недостающие конъюнкты Pᵢ, класс импасса §42)
  certificate: BDD?         // при accept: сертификат цепочки импликаций Rᵢ₋₁ ⟹ Pᵢ

ActEvent                    // запись журнала M4 на каждый BRC-акт (§45)
  domainHash, problemHash, plannerHash     // три хэша (§81)
  planCertificate, spentBudget, verdict, witness
```

## 3. Псевдокод

### 3.1 Проверка плана до исполнения (композиция триплетов, §80)

```
function checkPlan(plan: ActionContract[], ctx: Slice) -> PlanCheck:
    chainOk = true; cert = emptyBDD
    for i in 1..len(plan):
        link = imply(plan[i-1].delta, plan[i].pre)   // Rᵢ₋₁ ⟹ Pᵢ на домене
        v = bddProve(link, ctx.domainHash)           // O(1)-проверка через BDD (L2)
        if v == reject:
            return PlanCheck(reject, residue=null)   // reject-by-proof (ADR-005)
        if v == undecided:
            return PlanCheck(undecided,              // разрыв цепочки ≡ остаток
                residue=Residue(gap=i,
                                missing=unprovenConjuncts(plan[i].pre, plan[i-1].delta),
                                impasseClass=classify(plan[i].pre)))   // → подцель (§42)
        cert = and(cert, link)
    return PlanCheck(accept, certificate=cert)       // сертификат хранится в M4
```

### 3.2 Исполнение действия с мониторингом (PLANEX, §52)

```
function act(a: ActionContract, args, cell: TaskCell) -> ActEvent:
    ground = groundArgs(a.ioSchema, args)            // grounding — за строку бюджета
    charge(cell, cost(ground)); assert cost(ground) <= registry.groundingBudget
    pv = eval3(a.pre, cell.slice)                    // трёхзначное предусловие
    if pv != accept:
        return abort(a, verdict=pv,                  // reject-by-proof / undecided
                     residue=Residue(missing=unmetConjuncts(a.pre)))
    out = execute(a.executor, ground, cell)          // тело Q; cell бюджетирует (INV-TC2)
    if not checkDelta(a.delta, out):                 // постусловие не подтвердилось
        replan(a, out)                               // переисполнение звена / перепланирование
    return ActEvent(domainHash, problemHash, plannerHash,
                    certificate=cell.planCertificate, witness=out.witness, ...)
```

### 3.3 Атомарный своп версии действия (бисимуляция, §82)

```
function swapAction(reg: ActionRegistry, name: Symbol, new: ActionContract):
    old = reg.actions[name]
    assert new.ioSchema == old.ioSchema              // интерфейс неизменен (уровень §68)
    eq = bddEquiv(old.pre,  new.pre,  old.validatedClass)   // сильная проверка:
     and bddEquiv(old.delta.add, new.delta.add, old.validatedClass)   // полная таблица
     and bddEquiv(old.delta.del, new.delta.del, old.validatedClass)   // на классе
    if not eq:
        rejectByProof(counterexample=diff(old, new)) // контрпример хранится (§21)
    shadowRun(new, corpus=regressionCorpus(name))    // слабая эквивалентность — только
                                                     // ранжирование риска, не критерий
    swapAtomic(reg.actions, name, new)               // атомарно (как fnlPromote, DESIGN-12)
    log(SwapEvent(name, old.versionHash, new.versionHash, certificate=eq))
    // своп по выборочной эквивалентности запрещён — проверяется компилятором журнала
```

## 4. Инварианты

- **INV-AR1 (реестровая монополия):** контур исполняет только действия из реестра текущего domainHash; вызов вне реестра — reject-by-proof на границе.
- **INV-AR2 (проверка до исполнения):** план с verdict ≠ accept не исполняется; при undecided исполнение заменяется спауном подцели-TaskCell по остатку (§42/§52), не «попыткой».
- **INV-AR3 (декларируемая дельта):** исполнитель не изменяет ничего вне add/del контракта (допущение фрейма проверяется телеметрией — нарушение ≡ типизированный отказ, граница №13).
- **INV-AR4 (три хэша):** ни один BRC-акт не закрывается без тройки (domainHash, problemHash, plannerHash) в ActEvent; трасса без полной тройки — нарушение аудита.
- **INV-AR5 (grounding бюджетирован):** стоимость конкретизации списывается с клетки до execute; потолок k≤20 на параметр (§38); превышение — reject-by-budget.
- **INV-AR6 (сильный критерий свопа):** замена версии действия только при BDD-эквивалентности контракта на validatedClass; своп по корпусной (слабой) эквивалентности — нарушение, детектируется аудитом журнала.
- **INV-AR7 (инвариант домена):** для каждого действия доказано: P ∧ invariants{Q}R ⟹ invariants сохраняются (частичная корректность по §80; инвариант уровня §68).
- **INV-AR8 (вариант ≡ бюджет):** циклическое применение действия убывает по variant; смерть TaskCell по бюджету ≡ доказанная частичная корректность прерванной ветви (сертификат пройденного префикса сохраняется).

## 5. Приёмочные тесты

- **AT-AR1:** план с разрывом цепочки (Rᵢ₋₁ ⊉ Pᵢ на контрпримере) → verdict undecided, остаток содержит индекс разрыва и недостающие конъюнкты; спаунится подцель правильного класса импасса (INV-AR2).
- **AT-AR2:** план с доказуемой цепочкой → accept с BDD-сертификатом; повторная проверка сертификата из M4 — O(1) (INV-AR2, L2).
- **AT-AR3:** исполнитель, изменяющий состояние вне add/del (подсадочная мутация) → детекция телеметрией, типизированный отказ, событие в журнале (INV-AR3).
- **AT-AR4:** попытка BRC-акта без полной тройки хэшей (инструментированный журнал) → блокировка закрытия акта (INV-AR4).
- **AT-AR5:** grounding действия с параметром k=21 → reject-by-budget до execute (INV-AR5, §38).
- **AT-AR6:** своп версии действия с BDD-эквивалентным контрактом на validatedClass → атомарная замена, контур не останавливается; своп различающегося контракта → reject-by-proof с хранимым контрпримером (INV-AR6).
- **AT-AR7:** действие, нарушающее инвариант домена на граничном входе, → отказ регистрации в реестре на этапе χ-акта добавления (INV-AR7, §58).
- **AT-AR8:** клетка, умершая по бюджету в середине цикла, → сертификат пройденного префикса цепочки сохранён в M4, ветка закрыта вердиктом reject-by-budget с witness (INV-AR8, ADR-005).
- **AT-AR9:** воспроизводимость: повторный прогон по (domainHash, problemHash, plannerHash, seed) → побитово тот же ActEvent-трейл (NFR-04, §81).

## 6. Бюджеты и эксплуатация

- groundingBudget, пороги своп-корпуса и validatedClass каждого действия — в configHash домена (версионируются, §81); калибровка потолка grounding по классам доменов — кандидат на сравнение по корпусам (FR-15, см. SYSTEM-SYNTHESIS §4).
- Проверка плана — за счёт бюджета клетки **до** execute; сертификат переиспользуется при повторном плане на том же domainHash (кэш свидетельств подцелей, §46).
- Реестр изменяется только χ-актами (добавление/своп/удаление действия) через M4/Φ-гейты (§58); tombstone старых версий, lineage в DESIGN-05.
- Телеметрия: доля планов с verdict=undecided и распределение остатков по классам импассов — вход гомеостата (H-022); доля свопов с сильным сертификатом — процедурный аудит (запрет слабых свопов, INV-AR6).

## 7. Открытые вопросы

- **Холодный старт домена:** реестр без регрессионных корпусов — первый своп допускается только χ-актом владельца с golden-набором (аналог холодного старта FNL, DESIGN-12 §7); пререгистрируется отдельно.
- **Стоимость BDD-эквивалентности дельт** на широких validatedClass: пределы класса (размер таблицы × число классов) — замер в EXP по DESIGN-13 после H-017.
- **Взаимодействие с REFLEX-таблицами (§66):** PROMOTED-навык как executor REFLEX_TABLE — требуется согласование validatedClass навыка и validatedClass действия (кандидат на уточнение AT-AR6).
- **Остаток → подцель:** полнота классификации недостающих конъюнктов по типам импассов Soar (§42) — общий кандидат пререгистрации, не блокирует DESIGN-13.
