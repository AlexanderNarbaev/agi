# DESIGN-05: Память — слои, консолидация, забывание, восстановление

**Статус: normative** · Уровень: состояние во времени. Заменяет ранние пятиуровневые схемы конкретными хранилищами, алгоритмами и бюджетами. Связи: рабочая память питает DELIBERATION (DESIGN-03 §3.2), консолидация — producers (DESIGN-04 §5), коллективный слой — Noosphere (ROADMAP этап 5).

## 1. Слои и их физическая реализация

| Слой | Содержимое | Хранилище | Время жизни | Бюджет |
|---|---|---|---|---|
| M0 Рабочая | state текущего BRC-цикла (DESIGN-03 §3.2) | in-memory, per-request | миллисекунды–секунды | 64 КБ/запрос |
| M1 Эпизодическая | трейсы PipelineTrace, события среды, коррекции | PostgreSQL (R2DBC), таблица `episodes` | 30 дней горячие, далее свёртка | ротация по объёму |
| M2 Семантическая | стабилизированные знания: сам BIR-реестр артефактов | BirRegistry (Avro + диск) + PostgreSQL lineage ledger | бессрочно, версии | бюджеты DESIGN-01 §6 |
| M3 Процедурная | навыки/Capabilities как исполняемые артефакты | то же (M2 и M3 физически едины — обе суть BIR-артефакты; различие логическое: M2 отвечает «что истинно», M3 — «что делать») | бессрочно, версии | — |
| M4 Коллективная | Noosphere: опубликованные артефакты других узлов | CRDT-реплика (этап 5) + локальный кэш | по политике узла | кэш с LRU |

Ключевое упрощение относительно ранних схем: **знания и навыки — одна субстанция** (BIR-артефакты), поэтому M2/M3 не дублируют хранилища. Эпизоды — единственный «тёплый» слой с быстрым ростом и обязательной ротацией.

## 2. Рабочая память (M0)

```text
WorkingState = BitSet(k_total) + map[slot → provenance]
```

- Слоты: вход запроса, выход последнего BRC-шага, факты из memory_recall, ответы внешних инструментов (помечены `external`).
- `update(state, bits)` — запись только в выделенные слоты вызванной Capability (ioSchema); произвольная запись запрещена — ловится контрактным тестом.
- Между запросами M0 не сохраняется; «контекст диалога» восстанавливается из M1 (последние N трейсов, N — конфиг), а не из скрытого состояния.

## 3. Эпизодическая память (M1) и recall

```text
memory_recall(ctx):
  q ← encode(ctx)                      // тот же PERCEPTION-кодировщик домена (INV-P1)
  кандидаты ← top-K по расстоянию Хэмминга до q среди свёрток эпизодов
  return [ (fact_bits, provenance, ts) ]
```

- Эпизод хранит: вход-хэш, witness-цепочку (не полный payload — экономия), verdict, версии артефактов.
- Локальный индекс recall — встроенный (префиксные бакеты по Хэммингу); при подключённом внешнем rag-system текстовый recall делегируется ему (DESIGN-03 §6), но булев recall остаётся локальным всегда.
- Забывание — политикой, не утечкой: эпизоды старше горизонта сворачиваются в агрегаты (частоты, типичные witness), сырые удаляются; персональные — по tombstone-процедуре (право на забвение): payload заменяется заглушкой, структура и хэши сохраняются для воспроизводимости.

## 4. Консолидация (CLS-цикл, «сон»)

По аналогии гиппокамп→неокортекс (FOUNDATIONS §3.4): ежесуточное офлайн-окно (`learn.nightly-window`):

```text
consolidate():
  1. episodes_window ← эпизоды суток
  2. candidates ← контрпримеры, отказы, повторяющиеся witness-паттерны (частота ≥ 3)
  3. corpus_delta ← candidates после анонимизации и правил DESIGN-04 §5
  4. for domain in affected_domains:
       new ← TsetlinTrainer.refine(current[domain], corpus_delta)
       gate: Φ(new) ≤ Φ(current) и fidelity не хуже на golden
       → promote | reject (событие в ledger обоими исходами)
  5. свёртка эпизодов по §3
```

Инварианты:

- **INV-M1.** Консолидация никогда не меняет ACTIVE-артефакты на месте — только выпускает новые версии через promote.
- **INV-M2.** Окно консолидации — единственное время массового переобучения; аварийное внеочередное переобучение требует ручного триггера и записывается в WAL.md.
- **INV-M3.** Ночной цикл идемпотентен: повторный запуск на тех же данных не порождает новых версий (детерминизм seed + сравнение хэшей corpus_delta).

## 5. Журнал событий и восстановление

Event Sourcing (минимально необходимый объём):

- События: `UnitPromoted/Rejected/Frozen`, `QuarantineEntered/Exited`, `CorrectionLogged`, `ConsolidationRun`, `MaLevelChanged`, `GenesisAuthorized` (CONSTITUTION V).
- Журнал: PostgreSQL `event_journal` (R2DBC), append-only; Kafka используется только для межсервисного транспорта, не как источник истины.
- Восстановление состояния = реестр артефактов (M2/M3, на диске) + журнал для аудита «почему эта версия активна». Полное воспроизведение журнала для восстановления не требуется — снапшот реестра атомарен; журнал отвечает на вопрос «почему», не «что».
- Персональные payload'ы в событиях не пишутся (только хэши и ссылки) — tombstone-процедура §3 применима без разрушения журнала.

## 7. Коллективная память (M4) — границы этапа 5

- Транспорт: CRDT (G-set — факты, OR-set — теги, PN-counter — кредиты вклада), подписи ключом узла.
- Импорт чужого артефакта = импорт снапшота: проверка подписи → Guardrail-аудит (статья I) → статус CANDIDATE → обычные гейты → ACTIVE. Чужой артефакт никогда не попадает в рантайм напрямую.
- Отзыв: событие `Revoked` в CRDT → локальный карантин импортированного.
- Детальная политика доверия — ROADMAP этап 5 + FOUNDATIONS §7; до этапа 5 M4 реализован заглушкой (только локальный кэш, без синхронизации).

## 8. Приёмочные тесты

1. M0: property-тест «запись только в свои слоты» (контракт ioSchema).
2. Recall: известный эпизод находится в top-K (K=5) на golden-наборе эпизодов; tombstone: после забвения payload недоступен, воспроизводимость цепочек сохранена.
3. Консолидация: идемпотентность (два прогона — одна версия); promote только при Φ-улучшении (инжекция ухудшающего кандидата → reject).
4. Восстановление: kill -9 посреди ночного цикла → реестр консистентен, журнал отвечает «почему».
5. Импорт M4: чужой артефакт с нарушением статьи I отвергнут Guardrail-аудитом до рантайма.
