# DESIGN-03: Контур запроса — считывание ввода, размышление, преобразование в вывод

**Статус: normative** · Уровень: сквозной контур. Связывает DESIGN-01/02 с внешним миром. Определяет три стадии обработки любого запроса и границы с внешними системами (LLM, retrieval-сервисы, MCP-инструменты).

## 1. Три стадии

```
   ┌─────────────┐      ┌───────────────┐      ┌────────────┐
   │ PERCEPTION  │ ───▶ │ DELIBERATION  │ ───▶ │ RENDERING  │
   │ ввод → биты │      │ BRC-размышл.  │      │ биты → акт │
   └─────────────┘      └───────────────┘      └────────────┘
        ▲                                                │
        └─────────────── обратная связь среды ◀──────────┘
```

Принципы:

1. **Разделение ответственности.** Стадии — отдельные компоненты с Avro-контрактами; подмена одной стадии (напр., другой кодировщик) не трогает остальные.
2. **Булева сердцевина.** Между стадиями передаются только биты и помеченные структуры; вся «нечёткость» (текст, числа) локализована на краях — в кодировщиках и декодировщиках.
3. **Детерминизм контура.** При фиксированных версиях артефактов и входе — идентичный выход; вся недетерминированность внешних сервисов изолируется (§6).
4. **Наблюдаемость.** Каждый переход логируется схемой `PipelineTrace` (вход-хэш, версии артефактов, witness-цепочка, бюджеты): любой ответ восстановим и объясним post hoc.

## 2. PERCEPTION — считывание ввода

Задача: превратить внешний вход (текст, состояние игры, телеметрию) в битовый вектор фиксированной схемы.

### 2.1. Кодировщики (encoders) — реестр, версионируются как Capabilities

| Тип входа | Кодировщик | Метод | Выход |
|---|---|---|---|
| Категориальный | `onehot` | 1-из-N | N бит |
| Числовой | `quantile` | квантильные бины по обучающей выборке (SPEC-001 FR-B3) + термометрический код: бит i = 1 ⟺ x > q_i | B бит, монотонный порядок |
| Текст | `lexicon` | баг-оф-слов по фиксированному словарю домена + n-граммы (n≤2) | бит/лексема |
| Текст (общий) | `embed-hash` | внешний эмбеддинг (§6) → проекция в биты: LSH-подпись эмбеддинга (фиксированные гиперплоскости, seed в конфиге) | 256–4096 бит |
| Состояние игры | `world-grid` | каналы сетки (блок/сущность/инвентарь) — уже дискретны | прямой битмап |

Инварианты кодирования:

- **INV-P1.** Кодировщик — чистая функция с версией; `encode(x, v)` при фиксированной v детерминирован. Квантильные границы вычисляются офлайн и хранятся в артефакте, а не вычисляются «на лету».
- **INV-P2.** Схема битов (какой бит что значит) — часть ioSchema Capability (DESIGN-02 §3); несогласованность схем = ошибка сборки контура, ловится контрактным тестом.
- **INV-P3.** Каждый кодировщик имеет обратимую диагностику: для любого выставленного бита можно назвать его смысл (используется BRC при объяснении).

## 3. DELIBERATION — размышление

Задача: из битового входа и контекста памяти получить решение с **доказательством**. Формализм — BRC (Boolean Reasoning Chain): цепочка шагов, где каждый шаг — оценка BirUnit/BirNet с witness-битами.

### 3.1. Шаг BRC

```
BrcStep = (unitId, version, inputHash, outputBits, witness, rule?)
```

- `witness` — подмножество входных битов, реально повлиявших на выход (для CLAUSESET — литералы сработавшего клауза; для BDD — путь к терминалу; для TT — все k бит). Witness вычисляется механически, не «объясняется» постфактум.
- `rule` — читаемая форма (для CLAUSESET: «ЕСЛИ … ТО …»), генерируется `toHumanReadable()` (DESIGN-01 §3.3).

### 3.2. Цикл размышления

```text
deliberate(query_bits, ctx, budget):
  state ← query_bits ∪ memory_recall(ctx)      // DESIGN-05 §3
  chain ← []
  loop while budget.steps > 0:
    action ← router.evaluate(state)            // какая Capability вызывается
    if action == ANSWER: break
    step ← capabilities[action].evaluate(state)
    chain += BrcStep(...)
    state ← update(state, step.outputBits)     // рабочая память такта (DESIGN-05 §2)
    budget.steps--
  verdict ← answer_capability.evaluate(state)  // финальный ответ + conf (DESIGN-02 §4)
  return (verdict, chain)
```

- **Бюджеты обязательны**: макс. шагов (дефолт 5, конфиг `BRC_MAX_STEPS`), макс. wall-clock, макс. вызовов внешних инструментов. Исчерпание → лучший частичный результат с пометкой, не зависание (DESIGN-02 §6).
- **Проверка цепочки**: Guardrail-шаг — специальная Capability, оценивающая каждый промежуточный `state` на предмет запретов (статья I); срабатывание → цепочка обрывается, возвращается отказ с witness-обоснованием. Это и есть EthicalFilter 2.0: не монолит, а BIR-композиция в цикле (EXP-006).
- **Контрпримеры**: если две Capabilities в цепочке противоречат (BDD-анализ: `bdd(A) AND NOT bdd(B)` выполним), контрпример-вектор добавляется в цепочку как явный шаг `CONFLICT(witness)` — и далее по лестнице DESIGN-02 §4.3.

### 3.3. Свойства

- **Воспроизводимость**: цепочка + версии артефактов = полный рецепт ответа; интеграционный тест воспроизводит ответ по цепочке.
- **Полный аудит**: цепочка хранится в ledger для запросов, помеченных `audit: true`, и для всех отказов Guardrail (всегда).
- **Нет магии**: размышление — не LLM-«мысли», а последовательность проверяемых булевых шагов. LLM (если задействован внешне) — только на краях (§6).

## 4. RENDERING — преобразование размышления в вывод

Задача: из `(verdict, chain)` получить действие в мире: текст, команду игре, вызов инструмента, сигнал контроллеру.

| Тип выхода | Декодер | Метод |
|---|---|---|
| Дискретное действие (игра, контроллер) | `action-map` | прямое отображение битов выхода на команду по схеме |
| Текст (шаблонный) | `template` | verdict + witness → шаблон с подстановкой правил/контрпримеров; всегда содержит обоснование из chain |
| Текст (свободный) | `llm-render` (внешний, §6) | LLM получает **только** verdict + witness + формат; запрещено менять verdict; результат проходит Guardrail повторно |
| Вызов инструмента | `tool-call` | MCP-вызов по белому списку Persona (§5) |

Инварианты:

- **INV-R1.** Декодер не может изменить решение: verdict бит-в-бит переносится в выход (для `llm-render` — проверяется Guardrail-повтором и property-тестом на парафраз).
- **INV-R2.** Отказ — тоже вывод: обрыв по запретам рендерится как объяснимый отказ (какое правило, какой witness), не как молчание.
- **INV-R3.** Каждый выход несёт `PipelineTrace` (хэш) — получатель может запросить расшифровку.

## 5. Внешние интерфейсы: фасад, прокси, MCP

### 5.1. OpenAI-совместимый фасад (сохраняется)

`POST /v1/chat/completions` остаётся точкой входа для совместимости с индустрией (клиенты, SDK). Внутри: messages → PERCEPTION(`lexicon`/`embed-hash`) → DELIBERATION → RENDERING. Расширения ответа: `x-matrix-trace` (хэш цепочки), `x-matrix-confidence` (калиброванная), `x-matrix-refusal` (witness при отказе). Стриминг — по шагам BRC (каждый шаг — событие), что совместимо с SSE-протоколом OpenAI.

### 5.2. Прокси над собственными API (направление развития)

Собственные API (verify, guard, capabilities, memory) публикуются двумя способами:

1. **REST-прокси** `/matrix/*` — тонкий слой над внутренними сервисами, единая аутентификация (ключ инстанса), rate-limit, трейсинг. Все внутренние вызовы (включая фасад §5.1) идут **через прокси**, а не напрямую — одна точка аудита и бюджетов.
2. **MCP-сервер** (`matrix-mcp`): те же операции как MCP-инструменты (`matrix.verify`, `matrix.guard_check`, `matrix.memory_recall`, `matrix.persona_ask`) — стандарт индустрии для агентных клиентов; единственный способ внешнего агента вызвать MATRIX.

Правило: новые возможности сначала появляются как внутренний сервис → прокси → MCP-инструмент; прямых путей нет.

### 5.3. Вызовы MATRIX → внешние инструменты

Persona вызывает внешние MCP-инструменты (поиск, калькулятор, retrieval) только через белый список своего `accessPolicy` (DESIGN-02 §5.1) и только как шаг BRC с бюджетом. Ответ инструмента кодируется PERCEPTION-кодировщиком и входит в state с пометкой provenance `external`.

## 6. Внешние зависимости и их изоляция

| Зависимость | Роль | Договор |
|---|---|---|
| Внешний LLM (через DJL/ONNX или API) | учитель для дистилляции (офлайн); `llm-render` (онлайн, опционально) | недоверенный: выход всегда проходит Guardrail; версии и golden-векторы — CONSTITUTION VII.2 |
| rag-system (внешний проект) | retrieval-движок: индексация, BM25/векторный/графовый поиск | **внешний сервис по контракту** (REST/MCP): MATRIX отправляет запрос, получает фрагменты с цитатами; принципы гибридного поиска заимствованы, код и данные — не разделяются; MATRIX работает без rag-system (деградация: retrieval заменяется локальным индексом памяти, DESIGN-05 §4) |
| Внешние MCP-инструменты | расширение возможностей Persona | белый список + бюджеты + Guardrail на входе и выходе |

Инвариант изоляции: недоступность любой внешней зависимости не останавливает ядро — контур деградирует до локальных Capabilities с пометкой `DEGRADED` в трейсе.

## 7. Приёмочные тесты

1. Контрактные тесты Avro на всех стыках стадий (CI).
2. Воспроизводимость: ответ по сохранённой цепочке BRC совпадает бит-в-бит.
3. Отказ Guardrail: каждый запрет статьи I имеет тестовый кейс с witness-объяснением.
4. Бюджет: запрос-«бомба» (циклические вызовы) завершается `BUDGET_EXHAUSTED` ≤ заданного времени.
5. Изоляция: тест с отключённым rag-system/LLM — контур отвечает в режиме `DEGRADED`.
6. `llm-render`: property-тест «вердикт не изменён» + Guardrail-повтор срабатывает на инъекции в ответе LLM.
