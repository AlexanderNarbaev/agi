# DESIGN-01: Вычислительная единица — внутреннее устройство гибридного «нейрона»

**Статус: normative** · Уровень: атомарный. Реализует SPEC-002 этап A. Нормативные ограничения — CONSTITUTION II; этот документ — их алгоритмическое воплощение: структуры данных, псевдокод, сложности, бюджеты. Термин «нейрон» в коде не используется: класс называется `BirUnit` (исторический термин MPDT = «булева функция с метаданными», GLOSSARY).

## 1. Определение

Вычислительная единица (unit) — неизменяемый (в рантайме) объект:

```
BirUnit = (id, arityIn: k, arityOut: m, form, payload, header)
```

- `id` — UUID + generation (generation растёт только при офлайн-переобучении, создающем новый артефакт; рантайм-объект иммутабелен).
- `form ∈ {TT, CLAUSESET, BDD}` — одна из трёх форм BIR (SPEC-002 §1). Единица хранит **одну первичную форму**; остальные материализуются компилятором по требованию и кэшируются.
- `header` — Avro `BirHeader`: provenance (producer, корпус, версия Φ), fidelity (если форма получена lossy-конверсией), хэш payload (SHA3-256), статус жизненного цикла.

**Контракт рантайма (единственный):**

```java
BitSet evaluate(BirUnit unit, BitSet input);  // |input| = k, |result| = m
```

Детерминизм: одни и те же `(unit, input)` → один и тот же выход. Никакого состояния, скрытого от header. Обучение — только офлайн, производит **новый** артефакт (CONSTITUTION II.2).

### Жизненный цикл (машина состояний артефакта)

```
DRAFT → CANDIDATE →(Φ-гейт + fidelity-гейт)→ ACTIVE →(замещён лучшим)→ SUPERSEDED
  │                     │                          │
  └────(провал гейтов)──┴──→ REJECTED              └──→ FROZEN (вручную: аксиомы безопасности)
```

- `ACTIVE` — доступен рантайму; `FROZEN` — ACTIVE + запрет замещения (аксиомы статьи I, genesis-ядро); мутация FROZEN — ошибка компиляции и событие безопасности.
- Переходы фиксируются в lineage ledger (CONSTITUTION V) событиями `UnitPromoted / UnitRejected / UnitFrozen`.

## 2. Форма TT (таблица истинности)

### 2.1. Представление

Функция f: {0,1}ᵏ → {0,1}ᵐ, k ≤ K_MAX = 20. Таблица — `m` битовых массивов по 2ᵏ бит, упакованных в `long[]`:

```
words(k) = 2^k / 64            // k=20 → 16384 long = 128 КБ на выходной бит
TT = long[m][words(k)]
```

Инвариант адресации: входной вектор x ∈ {0,1}ᵏ читается как двоичное число `idx = Σ xⱼ·2ʲ` (бит j — младший/старший порядок фиксирован схемой Avro и единообразен во всём коде: **j — младший**).

### 2.2. Алгоритм evaluate

```text
evaluate_tt(TT, x):
  idx ← Σⱼ xⱼ · 2^j                      // O(k)
  for o in 0..m-1:                       // O(m)
    out[o] ← (TT[o][idx >>> 6] >>> (idx & 63)) & 1
  return out
```

Сложность: время O(k + m), память O(m·2ᵏ/8) байт. k=20, m=8 → 1 МБ на единицу.

### 2.3. Блочно-параллельная оценка (ключ к пропускной способности)

Для пакета из B входов таблица не читается поэлементно: формируем B индексов и собираем выходы gather-доступом. Для **слоёв одинаковых единиц** (одинаковые k, общий вход) применяем битовый параллелизм «64 входа за проход»: каждое слово TT — это 64 ответа на 64 разных входа; свертка слоя — XOR/AND-операции над `long` (Vector API на массивах >1024 слов). Целевой ориентир, публикуемый JMH (METRICS): ≥10⁸ оценок/с/ядро для k≤16, m=1.

### 2.4. Когда TT

k ≤ 20 и функция «плотная» (доля единиц в таблице ∈ [0.05, 0.95]). Разреженные/высокоарные — CLAUSESET или BDD. TT — единственная форма, маппируемая на FPGA LUT 1:1 (SPEC-002 FR-D2), поэтому единицы, помеченные `substrate: FPGA`, обязаны иметь материализованную TT.

## 3. Форма CLAUSESET (клаузы, DNF)

### 3.1. Представление

DNF: f(x) = ⋁ᶜ₌₁..C clause_c(x), где клауза — конъюнкция литералов над ≤ k переменными (k не ограничена; дефолт-лимит 4096 литералов на единицу, CONSTITUTION II.1).

```java
record Clause(long[] posMask, long[] negMask) {}  // два битмаска по k бит:
// posMask: переменная входит как x_i; negMask: как ¬x_i; пересечение масок = ∅
record ClauseSet(int k, Clause[] clauses) {}       // m=1; мультивыход — m ClauseSet'ов
```

`clause_c(x) = 1 ⟺ (x & posMask_c) == posMask_c AND (~x & negMask_c) == negMask_c` — 4 машинных операции на слово. Память: C · 2 · k/8 байт.

### 3.2. Алгоритм evaluate

```text
evaluate_cs(CS, x):
  for c in clauses:                       // O(C · k/64)
    if match(x, c.posMask, c.negMask): return 1
  return 0
```

Ранний выход при первом сработавшем клаузе. Порядок клауз — по убыванию эмпирической частоты срабатывания (переупорядочивание = офлайн-оптимизация, семантику не меняет; проверяется BDD-эквивалентностью, §5).

### 3.3. Обучаемость

CLAUSESET — первичная форма обучения: автоматы Цетлина назначают каждому литералу состояние s ∈ [1..2N] (включён/исключён, DESIGN-04 §3). Интерпретируемость: клауза читается как правило «ЕСЛИ x₃ ∧ ¬x₇ ∧ x₁₂ ТО 1». Каждая ACTIVE-единица этой формы обязана экспортировать читаемый список правил (`toHumanReadable()`) — используется в отчётах fidelity и аудите.

### 3.4. Полнота и потолок

DNF полна: любая булева функция представима. Потолок — число клауз C растёт экспоненциально для «плотных» функций (паритет, арифметика) — именно поэтому плотные k≤20 уходят в TT, а композиция мелких единиц (DESIGN-02) покрывает структурированные функции большей арности.

## 4. Форма BDD (бинарная решающая диаграмма)

### 4.1. Представление

ROBDD с фиксированным глобальным порядком переменных π (один на проект, конфиг `bir.bdd.var-order`; смена порядка = пересборка всех BDD, офлайн-операция). Узел:

```java
record BddNode(int var, int low, int high) {}  // low/high — индексы узлов; 0/1 — терминалы
```

Инварианты каноничности: (а) нет узла с low == high (редукция), (б) unique-table: не существует двух узлов с одинаковым (var, low, high). При соблюдении обоих **два BDD равны как функции ⟺ равны их корневые индексы** — проверка эквивалентности O(1) после построения.

### 4.2. Операции

```text
apply(op, u1, u2):           // op ∈ {AND, OR, XOR, ...} — рекурсия Шеннона с computed-cache
  if (u1,u2,op) in cache: return cached
  v ← max(var(u1), var(u2))  // порядок π: берём «верхнюю» переменную
  lo ← apply(op, cofactor(u1,v,0), cofactor(u2,v,0))
  hi ← apply(op, cofactor(u1,v,1), cofactor(u2,v,1))
  if lo == hi: return lo
  return mk(v, lo, hi)       // через unique-table
```

Построение из TT: рекурсивное разложение Шеннона по π — O(2ᵏ) обращений к таблице. Построение из CLAUSESET: последовательный `apply(OR, acc, bdd(clause_c))`, где `bdd(clause)` — цепочка из |literals| узлов. Размер может взрываться (умножение, симметричные функции при плохом π) → компилятор объявляет бюджет узлов (дефолт 10⁶); превышение = lossy-конверсия запрещена, фиксируется отказ, форма остаётся первичной.

### 4.3. Роль: верификатор, а не исполнитель

BDD в рантайме исполняется редко (путь O(k), но константный фактор хуже TT). Его назначение — **точные доказательства** (SPEC-002 §1):

- эквивалентность двух артефактов: `root(bdd(A)) == root(bdd(B))`;
- выполнимость/противоречие: `root == 0` (противоречие — база SAT-доказательств Guardrail, цель G1);
- подсчёт моделей: `#sat` за O(|BDD|) — мера «ширины» запрета/разрешения;
- контрпримеры: путь от корня к терминалу 1 в `bdd(A) AND NOT bdd(B)` = witness-битовый вектор для BRC (DESIGN-03 §3).

## 5. Компилятор форм

| Конверсия | Тип | Проверка |
|---|---|---|
| TT → BDD | точная | тривиально (построение детерминировано) |
| TT → CLAUSESET | точная | минимизация эспрессо-типа; BDD-эквивалентность в CI |
| CLAUSESET → BDD | точная (в бюджете) | — |
| CLAUSESET → TT | точная, только k ≤ 20 | прямое перечисление 2ᵏ |
| BDD → TT | точная, только k ≤ 20 | прямое перечисление |
| BDD → CLAUSESET | точная (пути к терминалу 1) | может быть экспоненциальной — бюджет клауз |
| любая lossy (k > 20 → TT-проекция и т.п.) | **запрещена без fidelity** | fidelity = доля совпадений на выборке ≥10⁶ входов; < 0.9 → артефакт REJECTED (SPEC-001 FR-B6) |

Инвариант компилятора (SPEC-002 INV-3/INV-5): lossy без записанной fidelity — ошибка компиляции; все точные конверсии гоняются через BDD-эквивалентность в CI с мутационным тестом.

## 6. Макет памяти и бюджеты (целевое железо: Ryzen 9 9955HX, RTX 5070 не используется)

| Форма | Память на единицу | Бюджет единиц в JVM (64 ГБ) |
|---|---|---|
| TT, k=16, m=1 | 8 КБ | ~5·10⁶ |
| TT, k=20, m=1 | 128 КБ | ~4·10⁵ |
| CLAUSESET, C=100, k=128 | 3,2 КБ | ~1,5·10⁷ |
| BDD | зависит; сторож 10⁶ узлов = ~24 МБ | по бюджету узлов глобально |

Реестр (`BirRegistry`) ведёт суммарный учёт байт по формам; превышение бюджета процесса → вытеснение по LRU только для кэшированных (не первичных) форм.

## 7. Интерфейсы модуля `matrix-bir`

```java
interface BirUnit { BitSet evaluate(BitSet in); BirHeader header(); }
interface BirCompiler { BirUnit convert(BirUnit src, Form target); }   // бросает LossyWithoutFidelity
interface BirVerifier { boolean equivalent(BirUnit a, BirUnit b);      // точно, через BDD
                        BitSet counterexample(BirUnit a, BirUnit b); } // null ⟺ эквивалентны
interface BirRegistry { BirUnit register(BirUnit u);                   // отказ без lineage (INV-4)
                        Optional<BirUnit> promote(UUID id); }          // Φ-гейт
```

ArchUnit-правила: рантайм-модули зависят только от `BirUnit`/`BirRegistry`; `BirCompiler` и producers — отдельный офлайн-градл-модуль, недоступный рантайму (SPEC-002 INV-1).

## 8. Приёмочные тесты этого документа

1. jqwik: для случайных f (k ≤ 16) eval(TT) ≡ eval(BDD) ≡ eval(CLAUSESET) на всех 2ᵏ входах.
2. jqwik: `convert(f, X→Y→X)` сохраняет семантику для всех точных пар форм.
3. JMH: нс/вызов по формам опубликован; регресс >10% блокирует релиз.
4. Мутационный тест компилятора: намеренно битая конверсия ловится CI-проверкой эквивалентности.
5. FROZEN-единица: попытка замещения → исключение + событие безопасности в ledger.
